## Seam 1 — `/identity` response and `/auth` request shapes — CONTRADICTION

**F1 (agree).** The shapes are identical everywhere they appear: root `CLAUDE.md` assignment text; `01/api-connector-design-rationale.md:71` ("Endpoints, methods, and JSON bodies for `/auth` and `/identity` are fixed by the assignment") and `:73` (the seven PII fields "match the assignment exactly"); `02/connector-security.md:7-8`; `03/PLAN.md:23` ("per the assignment's fixed JSON contracts"); `05/pii-governance.md:7` lists the same five address subfields; `05/multi-db-strategy.md:115-122` carries them as columns. Nobody drifted on the fixed contract.

**F2 (contradiction — 01 vs 02).** 01's contract summary tells 03 to build `Authenticate(username, password) → token` and `FetchIdentity(token, phone, name) → PII` with "the calling code (onboarding flow)" using both (`api-connector-design-rationale.md:40,72`) — the token is returned from one method to the caller and passed into the next. 02 requires the opposite: the token "is not passed up the call stack beyond the vendor-call function" and its scope "runs from the `/auth` response to the immediately following `/identity` call and no further" (`connector-security.md:20`). 03 receives both as "build against this". Owner: Naomi. Smallest fix, one document (`api-connector-design-rationale.md` contract summary): state that the two-method shape is the vendor adapter's internal interface and the exported operation is a single identity lookup that performs the auth-then-fetch inside the adapter, so the token never crosses the adapter boundary.

**F3 (contradiction — 01, 02, assignment).** The documents cannot all be true about who holds the vendor token between our `/auth` and our `/identity`. The assignment says `/auth` "retrieves an `access_token`" for its caller. 01 builds on that: "a short-lived token stands in for the password everywhere past the first screen" (`ux-notes.md:27`), i.e., held across two user-facing requests; `personas-use-cases.md:33` says the same. 02 says the token is "fetched fresh from `/auth` for each `/identity` call, held only inside that single request's execution scope" (`connector-security.md:19`), is "Not returned to our own API callers" (`:23`), and the end-user's vendor password is "Never persisted, never cached, held only for the vendor call" (`handoff-04-secrets.md:25`). Our `/identity` body is fixed as `{"phone","name"}` with no credential field. So on a `/identity` call the connector has neither a cached token, nor the user's password, nor a token from the caller — unless the caller presents one, which `:23` forbids. `connector-security.md` §6 (`:58-60`) discusses "a vendor `access_token` obtained from one person's `/auth` call" being used at `/identity`, which presumes exactly the caller-presented flow `:23` rules out. This is the ambiguity Ingrid's S8 finding 2 (`decisions/second-review-security-docs.md:33`) brushed against without resolving. Owner: Marcus (01's UX follows the assignment; 02's restriction is the added constraint). Smallest fix, one document (`connector-security.md` §1): one paragraph stating what our `/auth` returns to its authenticated internal caller (the vendor token pass-through, or an opaque handle) and that our `/identity` accepts it as the vendor credential for that call; rewrite `:23` from "not returned to our own API callers" to "returned only to the authenticated `connector:identity-lookup` caller, never to end users, never persisted server-side". If 02 instead keeps `:23`, then the assignment's `/auth` has no purpose in this design and 01's two-screen flow must be withdrawn — which is why the fix belongs in 02.

## Deletion gap — derived data — GAP (joint 02/04/05)

**Statement.** A subject-deletion request reaches `user_profile` and, by cascade, `user_credential` (`pii-governance.md:51`). It does not reach application logs, metrics, connector traces, ingress access logs, or crash dumps, none of which has a `source` column, a clock, or a key (`pii-governance.md:70`). 05 records this as unmodelled and names the upstream control: "if PII never enters a log, there is nothing to delete from it — which makes 02's never-log list the real control here" (`:72`). 02's list (`handoff-04-secrets.md:38-48`) and 04's enforcement (`observability.md:21-27`) are where that control lives; 04's log-retention window is explicitly not designed (`observability.md:41`) and each of 04 and 05 assigns it to the other (F37). `04/backlog.md` Story 6 (written during this pass) holds a placeholder awaiting this ruling.

**Does the current never-log list achieve "PII never enters a log"?** Not quite. It is close on intent — items 3, 4, 8 and 9 cover PII field values, vendor error bodies, request bodies and query fragments, and 04's metrics rule (`observability.md:15`) keeps PII out of labels — but three paths remain: (a) database driver error text, which on Postgres carries the failing row or key value and which 03 routes to logs as wrapped errors (F50) — the largest hole, and one no item on the list names; (b) `username`, absent from the list although it is typically an email address and appears in `ErrDuplicateUsername` driver detail — `connector-security.md:36` hedges only on the *vendor* username; (c) the audit log itself, permitted by design (`sub`, scope, opaque record id, timestamp — `handoff-03-auth.md:46-52`), which is pseudonymous rather than PII-free and, after a profile deletion, is the only remaining record that a given record id was looked up by a given caller — acceptable, but its retention window is the one nobody has set. Panic traces and Go's `net/http` server logs do not include request bodies, so item 8 holds there.

**Evaluation of 05's proposed resolution.** Correct in direction: the upstream control is the cheapest and the only one that makes derived-data deletion unnecessary rather than merely scheduled. It is sufficient only once (a) and (b) are added to the list and (a) is given its site in 03's translation layer. For (c), a deletion request cannot and should not purge audit entries; the resolution is a retention window on the audit stream, set by 05 as policy (the same table shape as `pii-governance.md:30`, one more row: audit log, clock = entry timestamp, window proposed, basis "unknown — legal"), enforced by 04 as a log-sink retention policy (`observability.md` §"Audit-log access", the Loki or external-platform sink already named at `:31`). That answers `04/backlog.md` Story 6: the enforcement site is a log-sink retention policy owned by 04, with the window a row in 05's retention table; no DAO or connector mechanism is needed.
