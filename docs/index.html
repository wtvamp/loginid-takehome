Drive the real API yourself

The assignment asked for three things: a multi-database DAO, a secured REST service to search and retrieve profiles, and a connector to a third-party identity provider. All three are running right now on a Kubernetes cluster. The demo console is a single page served by the API binary itself, on the same origin, so it holds no secret and needs no CORS. It makes real calls with a real token and prints the request as a curl line beside the raw response.

Running the console, step by step

About four minutes. Nothing you type is stored: the credential lives in the browser tab and dies with it.

Open the console

Go to loginid-takehome.uplifttech.org/demo. You will see one credential box at the top and five numbered panels below it, each with its own Run button.

Mint your first token

Paste the QA search client id into QA client id and its secret into QA client secret, then press Mint token. A green chip appears reading profile:search ✓ live. The page shows you the exact request it just made.

POST /auth/token
Authorization: Basic <client-id>:<client-secret>
Content-Type: application/x-www-form-urlencoded

grant_type=client_credentials

There is no scope parameter to send. The scope is a property of the credential, stored server-side, so a caller cannot ask for more than it was granted. Tokens last ten minutes; if one expires mid-review the page tells you to mint another rather than showing you a bare 401.

Repeat for the other two credentials

Paste the read-own pair, mint; paste the read-any pair, mint. You now hold three live tokens, one per scope, and three green chips. Clearing the fields does not clear the tokens.

Panel 1 — masked search beside full read

Leave the search box at its default, Review Demo, and press Run. Three fictional records come back: Review Demo One, Two and Three. In the left-hand response, phone and region are masked and highlighted as such. The page then re-reads the same record with the read-any token, and the right-hand response shows those fields in full.

The point is that authorisation is graduated, not a switch. The same row, the same handler, two different callers, two different shapes of truth.

POST /profiles/search   Authorization: Bearer <profile:search token>
{"name": "Review Demo"}

GET /profiles/{id}      Authorization: Bearer <profile:read:any token>

Panel 2 — the two identical 403s

Press Run. The page requests two record ids the read-own credential was never granted: one that exists and one that almost certainly does not. Both come back 403 with the same 65-byte body, and the page compares them byte for byte in front of you and prints PASS.

If "you may not see this" and "this does not exist" looked different, an attacker could enumerate which customers are real by reading error messages. They do not look different.

Panel 3 — no token at all

Press Run with nothing minted. 401. There is no anonymous back door, including on the search path.

Panel 4 — the reason-code enum

Press Run. A full read is attempted twice with the read-any token: once carrying reason_code=support_ticket, which is on the server's closed list and is accepted, and once carrying reason_code=made_up_reason, which is rejected.

An unmasked read of someone's home address should require a stated, checkable purpose that gets written to the audit log. A free-text field would let the caller write anything; a closed enum will not.

Panel 5 — tripping the rate limiter, for real

Run this one last. The page fires real requests one at a time until the API answers 429, then stops. The limiter is shared across everyone using that QA credential, so if a colleague is on the page at the same moment you will both feel it. That is stated on the page rather than hidden behind a per-visitor sandbox.

Prefer a terminal? Every request above is printed on the page as a copyable curl line, so the console doubles as documentation for the API.

    Software architecture

    What runs in the namespace

    Two Go binaries in three images. Watch the requests: a client mints a token at the issuer, calls the verifier, which checks the JWKS in-cluster and reads Postgres; the verifier alone may reach the connector; Vault feeds every pod its secrets at start. Hover a node for what it does.

    client requestJWKS / Vaultdatabasedenied by NetworkPolicy

    Q1 · Data access

    DAO for user_profile and user_credential

    One Repository interface, three backends. A conformance suite runs identical assertions against real Postgres, CockroachDB, and SQLite containers in CI, including CockroachDB's serialization retry. Errors by SQLSTATE, never by message text.

    Q2 · REST + auth

    Search and retrieve, secured

    OAuth2 client credentials mint RS256 tokens with per-client audiences; the verifier checks issuer, audience, and JWKS with bounded staleness. Masked search; full reads need read:own or read:any with a closed reason code; scope and policy denials are byte-identical 403s.

    Q3 · IDP connector

    /auth and /identity to a vendor

    Vendor tokens fetched, used once, discarded. Uniform-timing failures, per-identity and overflow backoff; the failure-ratio limiter fired live in review. Reachable only from api-service.

    AI architecture

    How the work was actually organised

    LoginID asked which AI tools were used and how. The honest answer is longer than a tool name, so this section gives the whole design: the layers, the model chosen for each seat and why, the rules that kept the agents from simply agreeing with each other, and a plain statement of which parts are Anthropic's documented patterns and which parts this project invented.

    The tool
    Claude Code

    Anthropic's agentic command-line tool, chosen because the deliverable is itself an argument about AI-architecture judgement. Using the tool that is the subject of the question makes the workflow inspectable: every session was recorded, and those recordings are published further down this page.

    The briefs
    one root file, five track files

    A root brief carries the assignment, the track boundaries and the working rules. Each of the five track directories carries its own brief, written to be self-sufficient: a fresh agent with no history can pick up that track from those two files alone. Context is retrieved when it is needed rather than all loaded at once, which is how a thirty-hour project stays inside a context window.

    The sessions
    six top-level processes, not one

    The project manager ran as one process. Each of the five track leads ran as its own separate process in its own terminal window, loading only its own brief and its own persona. They spoke to each other by message, but handed work over as files. A message signals that something is ready; it never carries the content.

    The hires
    eighteen specialists, spawned by their lead

    Each lead hired three or four specialists as sub-processes of its own session. Hires returned prose to their lead; leads wrote the files. Hires never spawned further agents, so the tree is exactly three deep and no work was ever orphaned under an agent nobody was watching.

    The operator
    an agent on another machine, holding the credentials

    Cluster and DNS credentials were never in this project's reach. A separate long-running agent on a different machine held them, took written requests, verified each one against the live cluster before acting, and refused anything the human had not authorised.

    Which model sat in which seat, and why

    One expensive seat where a wrong call propagates; capable, cheaper models everywhere the work is bounded.

    SeatModelReasoning
    Orchestrator (PM)Fable 5.1Holds the only cross-track state. A boundary misjudged here costs five agents their day, not one.
    Data-ops leadOpus 5Owns the schema and the database interface every other track builds against. The most expensive decision to reverse late.
    Four other leadsSonnet 5Design and delivery against a brief that is already concrete. Capable is enough; the ceiling is not the bottleneck.
    Eighteen hiresSonnet 5Bounded, single-purpose seats: one attack tree, one cold read, one objection.
    Research fan-outHaiku 4.5Narrow, verifiable, throwaway lookups run in parallel. Exploration noise never re-enters the coordinator's context, only the condensed answer does.

    The security lead wrote that reasoning up before any of it ran, then recorded where the harness refused to cooperate: there is no per-agent effort setting, so the planned middle tier collapsed upward. The plan says so rather than pretending the design survived contact intact.

    Why the agents were given different personalities

    Not decoration. A countermeasure against a specific failure.

    Five leads and a manager, all started from the same base model, land in the same temperament by default: serious, careful, thorough. Agreement between agents who think alike is not evidence that a decision is good. It is evidence that nobody in the room was built to disagree.

    So variance was engineered. Thirteen archetypes, each with a stated blind spot. No archetype more than twice across the whole organisation and never twice inside one team. Every team had to contain its own lead's temperament opposite. At least three hires had to be playful and bold, because not one lead was. Each hire's brief states plainly what it pushes back on and where its own judgement fails.

    The effect is visible in the record: the adversary keeps finding attacks, the minimalist keeps deleting scope, and the newcomer keeps asking the question everyone else had stopped asking.

    Six protocols

    The patterns the teams actually ran

    Each is a small protocol with named seats and a required artefact. Every run ends in a dated decision file recording the positions, the rebuttals, the ruling, and which model each seat ran on. Chat is never the record.

    Honesty about the claim

    Did any of this actually help?

    The security track put that question to its own debate protocol rather than asserting an answer, and the ruling went against the broad claim. What follows is what the record supports, what it does not, and the failure most worth stealing.

    What the evidence supports
    • A seat whose brief is structurally different produces findings the previous seat could not. The alternatives seat deleted two attack paths outright by removing a cache, where every prior seat had proposed hardening it.
    • A reader with no stake in the text catches what its author cannot. Cold reads of finished hand-offs returned real gaps every time they ran.
    • Independent review caught a rate-limit control that was a silent no-op for the broadest scope. Neither the author of the fix nor the objector it answered had seen it, because both were reasoning inside the question as posed.
    What it does not support

    That multi-agent debate beats one strong session in general. Nobody ran that comparison. The defensible claim is a mechanism, not a statistic: self-review interrogates the answer it already committed to, rather than the frame that produced the question. The losing side of that debate is preserved in the repository beside the winning one.

    Null results are counted in the same tallies as the hits, at the skeptic's insistence.

    The failure worth stealing

    Independence decayed silently. A reviewer assigned at planning time had, by the time the review ran, authored the very content she was set to check, through two intervening debates. Nothing flagged it; the roster still said she was independent.

    The lesson generalises well past AI: independence is a property to verify at the moment a review runs, not a role assigned once and trusted to hold. It was caught before that review ran, and the reviewers were reassigned.

    The three rules that made it auditable

    Everything names its author

    Every commit, pull request and ticket transition names the persona who did the work and the seat they sat in. Not "the team", not "Claude". Any line of code traces to the agent that wrote it and the reviewer that passed it.

    Hand-offs are files

    A hand-off has to let the receiver act without re-deriving the sender's reasoning. That gets tested by giving it to an agent who was not in the conversation and asking what they cannot do with it.

    Done means deployed and reviewed

    No story closed on a passing test. It closed when the product owner exercised it at the public URL. Nineteen stories failed that review before they passed it.

    The receipts

    Watch the agents work, then read every word

    Unedited screen recordings of the terminal while the organisation ran, screenshots of the operator agent working on the live cluster, and a complete archive of every session: each message, each tool call, each result, with credentials redacted. None of it is a reconstruction.

    A security lead briefing four specialists at once

    The adversary, the architect, the tinkerer and the skeptic each report in their own voice, then hold, waiting to be called into a seat. Twenty-two seconds.

    An infrastructure team arguing about scope

    The scope guard cuts a row from the secrets inventory as two hypotheticals deep for a take-home; the enthusiast makes the opposite case on the developer loop. The lead rules. Thirty-six seconds.

    The manager running five tracks at once

    Reports arriving from the engineering and infrastructure leads, a consistency pass flagging five stale restatements across tracks, and the operator agent being contacted on another machine. Two minutes.

    Hitting the usage limit, and what the agents did about it

    The organisation runs out of budget mid-debate. The agents record exactly where they stopped, restate the rule that nobody interrupts the human directly, and hold. One minute.

    What the record shows

    Six patterns the day kept repeating

    Each caught by a review step, each closed with a check that fails in CI or at startup instead of in production.

    Config named, never set

    Three times a binary read an environment variable no manifest set. Now every mode declares its required variables, refuses to start without them, and CI diffs manifests against that list.

    A pattern not carried forward

    Five times a control on one component was missing on an identical new one: NetworkPolicy allow-lists, Forbid on a CronJob, a ServiceAccount per workload. Each got a test tying the new component to the rule.

    Verification that skips

    CI was green for hours while every Postgres and CockroachDB test silently skipped. Fixtures now fail under CI and the containers are always present.

    The detector can fail too

    "Diff against origin before declaring done" returned a false clean for untracked files. Five artifacts stranded; a ?? line is now unshipped work.

    Arithmetic outlives its assumption

    An alert at window-plus-one-interval fired on every healthy cycle; a rolling-day skip rate was meaningless at a daily schedule. Both became functions of one interval constant.

    Fail loud, always

    Vault Agent has two retry loops; one exits, the other retried forever and hung a pod in Init for seven minutes. The forced-failure test found it; the pod now crash-loops in thirty-six seconds.
