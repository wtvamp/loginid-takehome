+type k8sManifestDoc struct {
+	Kind     string `yaml:"kind"`
+	Metadata struct {
+		Name string `yaml:"name"`
+	} `yaml:"metadata"`
+	Spec struct {
+		Template struct {
+			Spec struct {
+				Containers []struct {
+					Image string `yaml:"image"`
+					Env   []struct {
+						Name  string `yaml:"name"`
+						Value string `yaml:"value"` // only ever read for APP_MODE; every other var's value is deliberately never inspected — some are secretKeyRef-sourced with no literal to read at all
+					} `yaml:"env"`

+			} `yaml:"spec"`
+		} `yaml:"template"`
+	} `yaml:"spec"`

+func parseDeployments(t *testing.T, path string) []k8sManifestDoc {

+			}

+		}
+		if doc.Kind == "Deployment" {

What would change my mind: a minimum shape check (URL parses, has a scheme; issuer looks like a URI) in `RequiredAuthEnvVars`'s callers, even a weak one — it doesn't need to hit the JWKS endpoint at startup. **2. The "single source of truth" is not actually wired to the authn code it's meant to gate.** `internal/config/config.go:136-143` reads these env vars directly in `Load()`; `RequiredAuthEnvVars` in the same file is a hand-written, parallel switch statement with no structural link back to `Load()`'s field list. Someone can add a new `os.Getenv("AUTH_FOO")` to `Load()` or to authn middleware without ever touching `RequiredAuthEnvVars`, and nothing — not the startup check, not the manifest test — will notice the enforcement has gone blind. What would change my mind: a test that asserts every field `Load()` populates from an `AUTH_`/`CONNECTOR_JWT_` env var appears in some `RequiredAuthEnvVars` entry (or an explicit allowlist of intentional exceptions), closing the loop in the other direction. **3. Manifest test's `checked == 0` guard is a floor, not a per-deployment guarantee.** `serviceForImage`'s substring match `continue`s silently on any unrecognized image; the fatal only fires if literally zero deployments matched. Fail-loud-on-startup itself I don't object to — a crash-loop naming the missing var is strictly better than silent 401s, and I don't see it as a meaningful new availability vector since anyone with configmap/secret write access already owns the pod. Objections 1 and 2 unanswered as of this review; 3 is minor, flag only.
