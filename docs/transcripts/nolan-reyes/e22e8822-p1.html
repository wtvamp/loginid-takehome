package postgres

import (
	"context"
	"database/sql"
	"errors"

	"github.com/jackc/pgx/v5/pgconn"
)

// sqlstateSerializationFailure is the SQLSTATE CockroachDB (and Postgres,
// though Postgres at READ COMMITTED never produces it) returns when a
// transaction must be retried, per multi-db-strategy.md §4.
const sqlstateSerializationFailure = "40001"

const maxRetries = 5

// withRetry is the unexported helper inside this package that every write
// method runs its statement inside (§4, "Where the wrapper sits"). It is
// NOT in the composite and NOT above the interface boundary — it wraps a
// single transaction attempt and retries only when engine is
// "cockroachdb" and the failure is a genuine SQLSTATE 40001. On
// "postgres" it calls fn exactly once. Search never calls this — it's
// read-only and never encounters 40001 (§4).
func withRetry(ctx context.Context, db *sql.DB, e engine, fn func(*sql.Tx) error) error {
	return retryLoop(e, func() error {
		return runOnce(ctx, db, fn)
	})
}

// retryLoop is the pure engine-conditional retry policy, separated from
// transaction management so it's unit-testable without a live *sql.DB.
func retryLoop(e engine, attempt func() error) error {
	attempts := 1
	if e == engineCockroach {
		attempts = maxRetries
	}

	var lastErr error
	for i := 0; i < attempts; i++ {
		lastErr = attempt()
		if lastErr == nil {
			return nil
		}
		if e != engineCockroach || !isRetryable(lastErr) {
			return lastErr
		}
		// Retryable on CockroachDB: loop and try again. No backoff sleep
		// here — a serialization failure is not a load signal the way a
		// connection error is, and 05's contract does not ask for one;
		// keeping the retry bounded (maxRetries) is what prevents an
		// unbounded loop.
	}
	return lastErr
}

func runOnce(ctx context.Context, db *sql.DB, fn func(*sql.Tx) error) error {
	tx, err := db.BeginTx(ctx, nil)
	if err != nil {
		return err
	}
	if err := fn(tx); err != nil {
		_ = tx.Rollback()
		return err
	}
	return tx.Commit()
}

// isRetryable reports whether err is a genuine SQLSTATE 40001, not a
// string match on any error message.
func isRetryable(err error) bool {
	var pgErr *pgconn.PgError
	if errors.As(err, &pgErr) {
		return pgErr.Code == sqlstateSerializationFailure
	}
	return false
}

**PR #6 review — retry/transaction, pattern-matched against production** **1. No backoff — bounded at 5, no sleep.** This is the one that pages someone at 2am, not the connection error. A serialization failure under real contention isn't independent random noise — it's usually two or more transactions colliding on the same hot rows (a popular username lookup, a batch retention sweep running concurrently with live writes). Zero backoff means all colliding transactions retry on the very next tick, in lockstep, and collide again. I watched this exact shape at the card-issuing platform, not on CockroachDB but on a Postgres advisory-lock retry: no jitter, five retriers synchronized to the millisecond, forever re-colliding until the deploy that added jitter went out. Bounded-at-5 caps how long any *one* caller spins, but under sustained contention it just means five callers fail fast and the client sees elevated error rates instead of elevated latency — better than a hang, but the comment "not a load signal" undersells it. **PR #8 review — SQLite single-writer assumption** Setting `MaxOpenConns(1)` genuinely does what it says: it stops this package's own goroutines from opening a second connection and hitting `SQLITE_BUSY` against each other. That part holds regardless of how many goroutines call into the repository. But it doesn't eliminate contention — it moves it from "SQLite returns a busy error" to "`database/sql`'s pool queues the checkout." If `api-service` calls this DAO from multiple concurrent request handlers (which it will — that's the whole point of a web service), every second-and-later goroutine blocks on `db.Conn`/checkout, not on a SQLite error you can retry, but silently, inside the pool, until either a connection frees up or the caller's context deadline fires. At that point the caller gets `context deadline exceeded`, indistinguishable from a genuinely slow query, and there's no retry-on-busy path to catch it because there's nothing to catch — you just timed out waiting in line. That's the same shared-fate shape I flagged on the Go-layout debate, just one layer down: instead of one binary's outbound call starving another binary's inbound handler, here it's one request holding the single SQLite connection (say, `DeleteExpired` mid-sweep with a large `maxRows`, or `CreateProfileWithCredential`'s multi-statement transaction) and every other concurrent request queues behind it for the duration.
