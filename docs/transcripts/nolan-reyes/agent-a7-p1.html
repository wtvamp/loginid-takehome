Re-reviewed PR #26 at commit f93b19d. Straight answer: the Reserve/Settle redesign genuinely closes the race I flagged — it doesn't just move it. But there's one place it moves partway, and one new failure mode worth calling out before this gets called done. **1. Does Reserve/Settle close the race — yes, verified in the actual lock structure, not just the design intent.** `internal/api/touchcounter.go`: `Reserve` takes `c.mu`, checks `len(w.touched)+w.reserved >= c.cap`, and if it passes, increments `w.reserved` — all under the same lock, before returning. A second concurrent `Reserve` for the same `sub` blocks on `c.mu`, and when it acquires it, sees the first call's `w.reserved` already booked. There is no window between "capacity check passes" and "reservation becomes visible" — they're the same critical section. `TestInProcessTouchCounter_ConcurrentReservesNeverExceedCap` fires 20 real goroutines under `-race` at a cap of 100 with page size 50 (10x overshoot potential if the race weren't closed) and asserts `granted*pageSize <= capLimit`. That's the right test for the failure mode I described — it doesn't just check the interface shape, it fires actual concurrent load. This is the same defense-in-depth I'd want after the card-issuing platform's token cascade: don't trust a design review, prove it under `-race` with real goroutines. **2. Sweep mechanism — safe, but only because it's folded into the same lock, not because it's independently synchronized.** `sweepLocked` runs inside `Reserve`'s critical section (`c.mu` already held), sweeps at most once per `c.window` duration, and only deletes windows stale by `2*c.window` — a full window's grace period past normal rollover. Since `currentWindow`, `sweepLocked`, and the reserve/settle bookkeeping all share the one mutex, there's no separate race to introduce. The one edge case: a reservation that's still outstanding (mid-DAO-call) when its window ages past `2*c.window` (48h on a 24h window) gets swept out from under it — `Settle` then finds no window and no-ops. That's not a locking bug, it's a business-logic edge case so far outside realistic request latency it doesn't concern me. Fine as-is. **3. Every Reserve has a matching Settle on every exit path — checked both handlers line by line, this holds, but by discipline, not by construction.** Search handler (`handlers.go` ~745–797): Reserve happens after rate-limit check, before Authorize; Settle is called on Authorize error, Authorize denial, DAO error, and success — four paths, four Settle calls, all present. GetProfile handler (~878–924): same pattern, gated correctly behind `if reserved` since Reserve is conditional on `ScopeReadAny`. I traced all of them; none leak on the paths that exist today. But — this is the reservation equivalent of the check-then-act bug, one layer up: **there is no `defer`-based release.** Every Settle call is manually placed at each `return`. That's fragile in exactly the way "the happy path handles it" claims usually are: the first time someone adds a new early return in this handler — a new validation check, a new audit branch — and forgets the Settle call, that request's `pageSize` (or 1) worth of budget is booked and never released for the rest of that sub's 24h window. Same failure shape as an unrecovered panic between Reserve and the first Settle call: nothing in this diff recovers from that panic, and even if a recover-middleware exists elsewhere in the repo (not in this diff, didn't confirm either way), recovering from the crash doesn't retroactively call Settle — the reservation is still burned until window rollover. I've seen this exact shape before, not with reservations but with connection-pool checkouts that leaked past a panic because release was inline instead of deferred; it's a slow leak that only shows up as "why is this one client's cap silently lower than it should be" days later, not an immediate incident. I'd want a `defer func(){ if !alreadySettled { Settle(...) } }()` right after a successful Reserve, or acceptance of the manual-Settle-per-branch discipline explicitly in the PR description as a known trade-off with a code-review checklist item attached. Either is fine; silence on it is not. **Verdict:** the concurrency race from my original review is closed, correctly, and the test proves it under real concurrency rather than trusting the design narrative.
