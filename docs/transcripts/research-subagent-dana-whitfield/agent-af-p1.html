## Separating Credentials from User Profiles

A best practice is to segment authentication information away from the Users table into a separate Logins table with a required foreign key from Logins to Users. This separation provides several benefits:

1. **Cleaner Data Representation**: It provides a cleaner way of representing users in a system who do not have credentials to login, avoiding the need to allow NULL values for usernames and password salts/hashes.

2. **Performance Optimization**: Creating a separate Logins table lets you keep credential information in as thin a table as possible, which helps with indexing and lazy selects since the Logins table will usually have significantly more reads than writes.

## Broader PII Separation Strategies

For more comprehensive PII protection, organizations can physically separate PII into a dedicated database to be more convincing for GDPR/CCPA audits than table-level separation. This approach can include regional deployment flexibility where compliance with different jurisdictions is needed.

## Data Security Architecture

A comprehensive approach to data security combines encryption, access control, and secure credential management to protect sensitive information throughout its lifecycle in the system. This includes implementing row-level security mechanisms that dynamically filter data based on the authenticated user's identity, ensuring individuals only access information relevant to their roles and permissions.

Based on the search results, here's an overview of the key differences between CockroachDB and PostgreSQL regarding UUID primary keys, hotspots, sequential IDs, and upsert operations:

## UUID Primary Keys & Hotspot Issues

Sequential primary key patterns that work fine in traditional databases like PostgreSQL create hotspots for reads and writes in the distributed system of CockroachDB. When you insert data with sequential primary keys, all new data gets written to the same range on disk, which usually resides on a single node, creating a "hotspot" where one node becomes overwhelmed with write traffic while others sit idle.

CockroachDB recommends UUID primary keys for optimal data distribution across nodes, as using serial/auto-increment keys can lead to write hotspots. When using UUIDs, you're generating random primary keys that hit all ranges roughly equally, allowing you to take advantage of parallelism and distribute requests throughout the cluster instead of concentrating them in a hotspot on a single node.

## Key Differences Between Sequential and UUID Keys

SERIAL is provided in CockroachDB only for PostgreSQL compatibility; new applications should use UUID with the gen_random_uuid() function, which generates 128-bit values and more uniformly scatters them across ranges. CockroachDB's serial type uses unique_rowid() generating 64-bit integers, unlike PostgreSQL's serial which is int4 with a sequence.

## UPSERT vs ON CONFLICT

CockroachDB supports both UPSERT and INSERT ON CONFLICT commands. Whereas INSERT ON CONFLICT always performs a read, the UPSERT statement writes without reading, making it faster—Cockroach Labs recommends using UPSERT instead of INSERT ON CONFLICT DO UPDATE when inserting or updating columns on tables without secondary indexes.

UPSERT is CockroachDB-specific syntactic sugar that uses the primary key as the conflict index and adds a clause for each field not in the conflict index. CockroachDB has made INSERT ON CONFLICT DO UPDATE and UPSERT behave like PostgreSQL when inserting rows that conflict with each other, though the behavior does not always match PostgreSQL when insert rows also conflict with existing rows in the table.

## SQLite JSON Support

SQLite's JSON1 support is built-in since version 3.38.0, and JSON is stored as TEXT (or sometimes BLOB), and queried or modified using SQLite's JSON1 extension.

More recently, SQLite 3.45.0 (January 2024) added JSONB, a binary representation stored in a BLOB.

## SQLite vs PostgreSQL JSONB

Key differences in storage and performance:

- **Storage Format**: SQLite stores JSON as plain TEXT — the raw JSON string is kept exactly as written with no binary encoding, so every json_extract call re-parses the string. PostgreSQL JSONB stores JSON in a decomposed binary format that strips whitespace, reorders keys, and deduplicates object keys on write; reads are faster because no parsing is required.

- **Lookup Performance**: The PostgreSQL JSONB format claims to offer O(1) lookup of elements in objects and arrays. SQLite's JSONB has O(N) time complexity for most operations in SQLite, just like text JSON.

- **Binary Compatibility**: The "JSONB" name is inspired by PostgreSQL, but the on-disk format for SQLite's JSONB is not the same as PostgreSQL's. The two formats have the same name, but are not binary compatible.

- **Indexing**: PostgreSQL JSONB has a richer operator set — the @> containment operator, the ? key-exists operator, and GIN indexes that index every key and value in a document. SQLite expression indexes cover point lookups on specific paths; PostgreSQL GIN indexes cover arbitrary key and value searches across the entire document.

## Password Storage Requirements

Verifiers must store passwords in a form that is resistant to offline attacks, and passwords must be salted and hashed using a suitable password hashing scheme.

## Salt Requirements

The salt value must be at least 32 bits in length and arbitrarily chosen to minimize salt value collisions among stored hashes. Both the salt value and the resulting hash must be stored for each password.

## Approved Hashing Algorithms

Approved algorithms include PBKDF2, Argon2, and bcrypt, all designed to make offline cracking computationally expensive.

## Cost Factor Considerations

Password hashing schemes take a password, a salt, and a cost factor as inputs and generate a password hash. Their purpose is to make each password guess more expensive for an attacker who has obtained a hashed password file, thereby making the cost of a guessing attack high or prohibitive. The chosen cost factor should be as high as practical without negatively impacting verifier performance and should be increased over time to account for increases in computing performance.

## Additional Storage Recommendations

A reference to the password hashing scheme used, including the cost factor, should be stored for each password to allow migration to new algorithms and work factors.
