## Key Best Practices

**Base Image Choices:**

Start with distroless for most services, drop to scratch if you need the absolute minimum, and use alpine only when you need a shell for debugging. Distroless is the sweet spot for most production services.

**Multi-Stage Build Benefits:**

Multi-stage builds reduce image size by up to 97% compared to traditional monolithic builds. Images can be as small as 5-20 MB instead of 300+ MB, with reduced attack surface and no shell or package manager.

**Scratch vs. Distroless Comparison:**

- **Scratch:** Scratch has no shell, no tools, no users — just your binary. If your application needs to make HTTPS calls, you must copy /etc/ssl/certs/ca-certificates.crt from the builder stage.

- **Distroless:** Distroless adds CA certificates, timezone data, a nonroot user, and /tmp, still with no shell or package manager, and is the sweet spot for most production services.

**Security Considerations:**

A scratch-based Go image typically reports zero OS-level CVEs, and fewer tools in the image means attackers have less to work with if code execution is achieved. Never run containers as root, and distroless provides a nonroot user (UID 65532).

**General Build Strategy:**

Key practices include using the smallest base for runtime, pinning base image versions, ordering for cache efficiency with dependency files before source code, and running as non-root.

## What Not to Log

Never log sensitive data like passwords and tokens, even at debug level, since debug logs can be left on in more places than intended. Common keys to redact include: password, token, authorization, bearer, secret, api_key, access_token, refresh_token, ssn, credit_card, and cvv.

Additionally, avoid logging full request/response bodies as they contain auth headers and form data.

## Best Practice for Redaction

Sanitize before the log call is made, not after. The recommended approach is to use the `ReplaceAttr` function in `HandlerOptions`: Use ReplaceAttr in HandlerOptions to redact sensitive keys before emission by switching on common sensitive keys and returning a redacted string value.

Custom handlers enable filtering, transformation, and redaction of sensitive fields, which is mandatory for passwords, tokens, and PII to meet security and compliance requirements.

## General Structured Logging Best Practices

Go's log/slog package brings structured logging into the standard library, letting you log consistent key-value data, attach context like request IDs, and output logs in JSON or text formats. Best practices include: always use structured logging in production, include request/trace IDs for correlation, log at appropriate levels, use child loggers for context, configure log level from environment, and output JSON for log aggregation systems.

## Understanding Error 40001

CockroachDB signals a serialization error with the SQLSTATE error code 40001 and an error message that begins with the string "restart transaction". These errors indicate that a transaction failed due to contention with another concurrent or recent transaction attempting to write to the same data, and the transaction needs to be retried by the client.

## SERIALIZABLE Isolation and Automatic Retries

At the default SERIALIZABLE isolation level, CockroachDB always attempts to find a serializable ordering among all currently-executing transactions. Whenever possible, CockroachDB will auto-retry a transaction internally without notifying the client, and will only send a serialization error to the client when it cannot resolve the error automatically without client-side intervention.

## pgx and Client-side Retry Handling

Go developers using pgx can use the github.com/cockroachdb/cockroach-go/crdb package for automatic retry handling. This is the recommended approach for applications using the pgx driver with CockroachDB.

## Recommended Actions

Under SERIALIZABLE isolation, you should update your application to support client-side retry handling when transaction retry errors are encountered. Additionally, if a statement returns a retry error, you can issue the ROLLBACK TO SAVEPOINT statement to restart the transaction.
