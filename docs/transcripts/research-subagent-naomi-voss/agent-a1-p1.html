Based on the search results, here's information about RFC 6749 Section 4.3 Resource Owner Password Credentials grant flow:

## Overview

The Resource Owner Password Credentials Grant (defined in RFC 6749, section 4.3) can be used directly as an authorization grant to obtain an access token, and optionally a refresh token.

## How It Works

The password grant is suitable for clients capable of obtaining the resource owner's credentials (username and password, typically using an interactive form). The flow involves these steps:

The user provides the client application with their username and password, and the client requests an access token from the service provider's token endpoint using the credentials received from the user.

## Security Considerations

This flow has significant security implications and is not recommended for most use cases. Because credentials are sent to the backend and can be stored for future use before being exchanged for an Access Token, it is imperative that the application is absolutely trusted with this information.

Even if this condition is met, the Resource Owner Password Flow should only be used when redirect-based flows (like the Authorization Code Flow) cannot be used. Examples where this could be useful are legacy applications and command-line interfaces.

Additionally, although it is part of OAuth 2.0, it has been removed in the OAuth 2.1 draft, and there are good reasons for this: When using this flow, the credentials of the user are exposed to the client application.

## RFC 9700 Overview

In January 2025, the IETF published RFC 9700: Best Current Practice for OAuth 2.0 Security. This document describes best current security practice for OAuth 2.0 and updates and extends the threat model and security advice given in RFCs 6749, 6750, and 6819 to incorporate practical experiences gathered since OAuth 2.0 was published and covers new threats relevant due to the broader application of OAuth 2.0.

## ROPC Requirements in RFC 9700

The specification is unambiguous regarding ROPC: Section 2.4 states "The resource owner password credentials grant MUST NOT be used." This is IETF "MUST NOT" — the strongest prohibition in RFC vocabulary.

## Why ROPC Must Not Be Used

ROPC insecurely exposes the user's credentials to the client. It's recommended that you avoid using the ROPC flow and rely on more secure OAuth flows, like the Authorization Code flow, where user consent is required, or the Client Credentials flow for machine-to-machine communication.
