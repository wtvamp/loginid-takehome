# SQLSTATE 40001 Retry Errors in CockroachDB

## What They Are

SQLSTATE 40001 errors are transaction retry errors that occur when CockroachDB cannot complete a transaction due to contention with concurrent operations. All such errors use this standardized SQL error code and include the phrase "restart transaction" in their messages.

## When They Occur Under SERIALIZABLE Isolation

These errors fall into two categories:

**Serialization errors** happen when a transaction cannot be placed into a serializable ordering with other concurrent transactions. Common examples include:
- `RETRY_WRITE_TOO_OLD`: Another transaction with a higher timestamp already wrote to data this transaction needs to modify
- `RETRY_SERIALIZABLE`: A transaction's timestamp was pushed forward, but previous reads are no longer valid at the new timestamp
- `ReadWithinUncertaintyIntervalError`: Clock skew between nodes causes ambiguity about transaction ordering

**Internal state errors** indicate cluster issues like overload, lease transfers, or network problems.

## Automatic vs. Client-Side Handling

**CockroachDB automatically retries** failed transactions internally without client notification whenever possible. However, automatic retry has limits:

According to the documentation, "When a multi-statement transaction is not batched, and takes more than a single round trip, CockroachDB cannot automatically retry the transaction."

Additionally, if result sets exceed the `sql.defaults.results_buffer.size` cluster setting, automatic retry becomes impossible even for batched statements.

**Client-side retry is required** when automatic retry fails. Applications must catch SQLSTATE 40001 errors and restart the entire transaction.

## Key Limitations

The critical constraint is result streaming: once data has been returned to the client, CockroachDB cannot automatically refresh reads at a new timestamp if that timestamp becomes invalid. This makes large result sets incompatible with automatic retry mechanisms.

# CockroachDB Client-Side Transaction Retry Pattern

## Why It's Necessary

CockroachDB implements retries to handle transaction failures caused by contention. The documentation explains that "when you use savepoints, you 'hold your place in line' between attempts" rather than restarting from scratch.

## The Retry Loop Pattern

The documented pattern follows these steps:

1. **BEGIN** the transaction
2. **Create a SAVEPOINT** named `cockroach_restart` (the retry savepoint)
3. **Execute transaction statements**
4. **On retry errors** (error code 40001): rollback to the savepoint and repeat step 3
5. **On success**: release the savepoint and commit

The sequence prevents restarting the entire conflict resolution process, maintaining your position in the transaction queue.

# READ COMMITTED Isolation in CockroachDB

## What It Does

READ COMMITTED is a transaction isolation level that prioritizes high concurrency over strict consistency guarantees. As the documentation explains, it "permits some concurrency anomalies in exchange for minimizing transaction aborts, retries, and blocking."

The key mechanism: statements in READ COMMITTED transactions see data committed before each **statement** begins, rather than data committed before the entire transaction began (as in SERIALIZABLE). This allows concurrent writes to interleave without forcing transaction aborts.

## Client-Side Retries: Not Required

A major advantage is that you **don't need client-side retry logic**. The documentation states: "you do **not** need to implement client-side retries to handle serialization errors under transaction contention. READ COMMITTED transactions never return RETRY_SERIALIZABLE errors."

However, this isn't absolute—transactions can still abort due to deadlocks, constraint violations, or in rare cases where result streaming has begun.

## Key Differences from PostgreSQL

CockroachDB's READ COMMITTED is actually **stronger** than PostgreSQL's version. The documentation notes: "READ COMMITTED on CockroachDB provides stronger isolation than READ COMMITTED on PostgreSQL. On CockroachDB, READ COMMITTED prevents anomalies within single statements."

## Notable Caveats

- **Concurrency anomalies permitted**: non-repeatable reads, phantom reads, lost updates, and write skew
- **Locking reads available**: `SELECT FOR UPDATE` and `SELECT FOR SHARE` can mitigate anomalies but add complexity
- **Schema change limitations**: DDL operations cannot occur within explicit READ COMMITTED transactions
- **Performance tradeoffs**: locking reads perform less optimally than under SERIALIZABLE isolation

## Overview

Package crdb provides helpers for using CockroachDB in client applications. The ExecuteTx function is defined as `func ExecuteTx(ctx context.Context, db *sql.DB, txopts *sql.TxOptions, fn func(*sql.Tx) error) error`

## Purpose

ExecuteTx is used when a multi-statement transaction is being run. It's a transaction retry helper that wraps your transaction logic.

## Usage Example

A basic usage involves calling ExecuteTx with your transaction logic inside a closure, such as: `err := crdb.ExecuteTx(ctx, db, nil, func(tx *sql.Tx) error { _, err := tx.ExecContext(ctx, "UPDATE accounts SET balance = balance - 100 WHERE id = 1") return err })` By default, transactions retry up to 50 times with no delay between attempts.

## Customization

You can customize retry behavior using context options, such as using `crdb.WithMaxRetries(context.Background(), 10)` to retry up to 10 times.

## Important Constraints

The supplied fn closure should not have external side effects beyond changes to the database, and fn must take care when wrapping errors returned from the database driver with additional context. When wrapping errors inside transaction functions, you should use `%w` or `errors.Wrap()` to preserve retry detection.

## Advisory Locks

Session-scoped advisory locks are not supported. The session-scoped functions pg_advisory_lock, pg_advisory_lock_shared, and pg_try_advisory_lock_shared return an error. However, transaction-scoped advisory locks are supported, including pg_advisory_xact_lock and pg_advisory_xact_lock_shared.

The functions pg_try_advisory_lock, pg_advisory_unlock, pg_advisory_unlock_shared, and pg_advisory_unlock_all are defined for compatibility but silently succeed without any effect.

## SELECT FOR UPDATE

FOR UPDATE with a cursor is not supported. Additionally, SELECT FOR UPDATE and SELECT FOR SHARE statements in CockroachDB do not prevent insertion of new rows matching the search condition (i.e., phantom reads), which matches PostgreSQL behavior at all isolation levels. SELECT FOR UPDATE and SELECT FOR SHARE statements are less optimized under READ COMMITTED isolation than under SERIALIZABLE isolation, often performing an extra lookup join.

## Savepoints

Respect for SAVEPOINTs is not supported. Cursor definitions do not disappear properly if rolled back to a SAVEPOINT from before they were created.

These limitations are important considerations when using the pgx driver with CockroachDB through the `database/sql` interface.

I have enough to answer thoroughly and cite primary sources. --- **Verdict up front:** No — one Go `postgres` package cannot honestly serve both engines with zero engine-awareness. Wire-protocol/SQL-surface compatibility is real, but transaction and error semantics diverge in ways that leak into the DAO. The caveat is narrow and nameable, though: the divergence is confined to (a) whether the DAO needs a retry wrapper at all, and (b) a couple of error-code edge cases — not a full re-architecture. **1. Retryable transaction errors — yes, materially different by default.** CockroachDB defaults to SERIALIZABLE and returns SQLSTATE 40001 ("restart transaction") on serialization conflicts that PostgreSQL's default READ COMMITTED never produces (Postgres only emits 40001 at REPEATABLE READ/SERIALIZABLE) ([PostgreSQL 13.2 Transaction Isolation](https://www.postgresql.org/docs/current/transaction-iso.html), [13.5 Serialization Failure Handling](https://www.postgresql.org/docs/current/mvcc-serialization-failure-handling.html)). CockroachDB auto-retries internally when it can, but this has a hard limit: once a multi-statement transaction spans more than one round trip, or once results have started streaming to the client (or exceed `sql.defaults.results_buffer.size`), automatic server-side retry is impossible and the client gets 40001 and must retry itself ([Transaction Retry Error Reference](https://docs.cockroachlabs.com/docs/stable/transaction-retry-error-reference)). Cockroach Labs' own docs prescribe a client-side `SAVEPOINT cockroach_restart` retry loop for exactly this reason ([Advanced Client-Side Transaction Retries](https://docs.cockroachlabs.com/docs/stable/advanced-client-side-transaction-retries)), and ship `cockroachdb/cockroach-go`'s `crdb.ExecuteTx` (default 50 retries, no delay, configurable via `crdb.WithMaxRetries`) specifically to wrap this ([pkg.go.dev crdb](https://pkg.go.dev/github.com/cockroachdb/cockroach-go/crdb)). This helper exists *because* the plain `database/sql` path is insufficient for CockroachDB SERIALIZABLE — there is no Postgres analog needed for a default-config Postgres DAO. **2. Isolation levels.** Postgres: READ COMMITTED (default), REPEATABLE READ, SERIALIZABLE — full standard set. CockroachDB: SERIALIZABLE (default) and READ COMMITTED, GA since 24.1 ([Read Committed Transactions, v26.2](https://docs.cockroachlabs.com/docs/v26.2/read-committed)). Switching CockroachDB's DAO connections to READ COMMITTED does change the answer — under it, CockroachDB "never returns RETRY_SERIALIZABLE errors" and the retry loop becomes unnecessary for ordinary contention, though transactions can still abort on deadlocks, constraint violations, or in rare streaming-related cases (same page). Notably Cockroach's READ COMMITTED is stated to be *stronger* than Postgres's (it prevents anomalies within a single statement), so "READ COMMITTED" is not a drop-in semantic match either — another place a shared implementation can't assume identical behavior even when the isolation-level *name* matches. **3. Constraint-violation error codes — mostly aligned, with one documented sharp edge.** Both engines use SQLSTATE 23505 (unique_violation) and 23503 (foreign_key_violation) and CockroachDB explicitly implements the Postgres error-code table (`pkg/sql/pgwire/pgcode/codes.go`). But `cockroachdb/cockroach#42858` documents a real historical inconsistency: creating a duplicate FK constraint returned 23503 in one CRDB version, 42830 in another, and 42710 in Postgres — closed by PR #43210, but it's evidence that constraint-related SQLSTATEs have not always agreed and version-pinning matters when writing the sentinel-error translation layer. Constraint *names* and message structure also aren't guaranteed portable: Postgres embeds the actual constraint name and a `DETAIL:` line with the offending key; CockroachDB error text and structure has historically diverged (see `cockroach#16196`, "returning Incorrect Error Code for FOREIGN_KEY_VIOLATION"). **Practical implication for the DAO:** match on SQLSTATE code, never on message text or constraint-name substring, and pin a CockroachDB version when asserting 23505/23503 behavior. **4. Go driver considerations.** `pgx`/`lib/pq` work against CockroachDB largely unchanged for basic CRUD (CockroachDB implements the pg wire protocol) — this is CockroachDB's own compatibility claim, so treat it as vendor-asserted, not independently verified here ([PostgreSQL Compatibility](https://docs.cockroachlabs.com/docs/stable/postgresql-compatibility)). But `cockroachdb/cockroach-go` exists precisely because plain `database/sql` + pgx is *not* sufficient for transactional workloads under SERIALIZABLE: `crdb.ExecuteTx` (and `crdbpgx` for pgx-native pools) exists to solve the retry-loop problem in #1, which Postgres code never needs. **5. Other divergences that leak into a shared implementation**, all vendor-documented, all under CockroachDB's [PostgreSQL Compatibility](https://docs.cockroachlabs.com/docs/stable/postgresql-compatibility) / [Known Limitations](https://www.cockroachlabs.com/docs/stable/known-limitations) pages: - **Session-scoped advisory locks** (`pg_advisory_lock`, `pg_try_advisory_lock_shared`) error out on CockroachDB; only transaction-scoped (`pg_advisory_xact_lock`) work. `pg_try_advisory_lock`/unlock functions silently no-op instead of erroring — a DAO relying on advisory locks for de-dup/leader-election would fail silently on CockroachDB, not loudly. - **Savepoints**: CockroachDB's `ROLLBACK TO SAVEPOINT` doesn't fully match Postgres semantics for cursors defined before the savepoint. - **`SELECT ... FOR UPDATE`**: not usable with cursors on CockroachDB; under READ COMMITTED it's less optimized (extra lookup join) than under SERIALIZABLE. - **`ON CONFLICT DO UPDATE` under contention**: behaves within the same retry-error framework as #1 — a contended upsert under CockroachDB SERIALIZABLE can itself throw 40001, something a Postgres-only code path (READ COMMITTED default) never has to plan for. - **Transaction priorities** (`SET TRANSACTION PRIORITY`) are a CockroachDB-only concept with no Postgres equivalent, sometimes used to reduce retry likelihood for specific transaction classes — an option unavailable on the Postgres backend, so a shared abstraction has to no-op it there rather than expose it uniformly. **Could not verify:** - Whether the `#42858` FK-constraint SQLSTATE inconsistency also applies to ordinary duplicate-*data* FK violations (23503) rather than duplicate-*constraint-definition* DDL, versus current CockroachDB versions — the closed issue documents a DDL-time case, not confirmed for INSERT-time FK violations on current CockroachDB. - Exact current-version message/DETAIL-field structure diff between CockroachDB and Postgres for 23505/23503 (i.e., whether CockroachDB populates a `Detail`/`ConstraintName` field identically to `pgconn.PgError` from `pgx`) — not directly confirmed from a primary source in this pass. - Whether `crdbpgx.ExecuteTx` (pgx-native variant) has behaviorally diverged from `crdb.ExecuteTx` (database/sql variant) in ways relevant to a `database/sql`-only DAO — only the database/sql variant was confirmed in detail. **Bottom line for the design doc:** the DAO can share one Go package and one `Repository` interface across both engines, but only if it (a) always writes through a `crdb.ExecuteTx`-style retry wrapper — a harmless no-op-cost pattern on Postgres, load-bearing on CockroachDB SERIALIZABLE — or explicitly documents that the CockroachDB backend runs at READ COMMITTED to drop that requirement; (b) translates constraint violations to shared sentinel errors by SQLSTATE code only, never by message/constraint-name string matching, and version-pins the CockroachDB target given the historical code-inconsistency precedent; and (c) treats advisory locks, cursor-scoped `FOR UPDATE`, and transaction-priority hints as Postgres-only or CockroachDB-only capabilities that the shared interface must not expose uniformly. That's the named caveat: "yes, one package, but it must carry an engine-aware retry/error-translation seam — it cannot be a thin PostgreSQL-only implementation pointed at two connection strings."
