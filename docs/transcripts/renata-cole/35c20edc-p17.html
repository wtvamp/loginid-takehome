I can't construct an interleaving that gets you zero logs (under-count) or two logs (over-count) for the same transition — the mutex is doing the actual work here, the boolean is just carrying the decision out of the lock. This is the right shape; I've seen the "check-then-log outside the lock without capturing the decision inside it" version of this bug before and it's not present here. One real but minor consequence, not a bug: under a flaky-not-fully-down network, two concurrent duplicate fetches (already an accepted trade-off per `KeyForKid`'s own doc comment) can have one fail and one succeed within the same moment, producing a "failed" log immediately followed by a "recovered after 1 failure" log. That's inherent to the already-accepted duplicate-fetch design, not something this PR introduces. It's the same class of coupling I flagged on PR #30 for the retry-floor assumption — implicit contract between two things that live in the same file today but nobody's obligated to notice they're coupled tomorrow. An attacker flooding fabricated kids during a real outage gets bounded extra fetch *attempts* (capped by `jwksMaxTrackedUnknownKids`, already reviewed on PR #30), but not bounded extra *log lines* beyond the one-per-streak — because none of those attempts move `consecutiveFailures` back to 1 once the streak's already started. That's not a regression, it's a boundary the fix doesn't claim to cover, but I'd rather Renata and the PM hear it named now than assume "we fixed cold-start logging" covers every crash-loop shape. The scenario this PR *does* fix — a pod that's up and serving traffic, whose first real verification request hits an unreachable JWKS endpoint — is a genuine improvement, and it's the scenario that actually happened in the live incident (the task description says the pod log showed the startup line, meaning it stayed up and took traffic). `log.Printf`'s default output goes to stderr unbuffered per call, so it should survive being captured by the container runtime's log pipe even under a subsequent fast kill; I have no reason to think the line gets lost between being written and being scraped, unlike a buffered/async logging library where I would ask that question. **5.
