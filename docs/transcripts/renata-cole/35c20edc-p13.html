143	// resolveSigningKeyPath enforces LT-32's issuer-mode requirement: in
144	// "issuer" mode, JWT_SIGNING_KEY_FILE must name a regular file this
145	// process can actually read at least one byte of, checked now rather than
146	// left for whatever code first tries to sign a token — a startup failure
147	// here is the only thing that distinguishes "issuer mode with no key"
148	// from "issuer mode with a key", and the whole point of the
149	// physical-absence criterion is that those two must never be confused for
150	// one another. In "verifier" mode the variable is not read at all: the
151	// verifying binary has no legitimate use for a signing-key path, set or
152	// not.
153	//
154	// This checks openable-and-non-empty at startup, not "will still be a
155	// valid key when S7 reads it" — a Secret rotated to empty or a volume
156	// re-provisioned later isn't something a one-time startup check can see
157	// (Nolan Reyes, PR #18 review). That's S7's problem to solve when it
158	// exists, not this story's: LT-32 only owns making a *missing* key loud
159	// at startup, not monitoring a *present* key's ongoing validity.
160	func resolveSigningKeyPath(appMode string) (string, error) {
161		if appMode != "issuer" {
162			return "", nil
163		}
164		path := os.Getenv("JWT_SIGNING_KEY_FILE")
165		if path == "" {
166			return "", fmt.Errorf("config: APP_MODE=issuer requires JWT_SIGNING_KEY_FILE to be set")
167		}
168		fi, err := os.Stat(path)
169		if err != nil {
170			return "", fmt.Errorf("config: APP_MODE=issuer set but JWT_SIGNING_KEY_FILE %q is not accessible: %w", path, err)
171		}
172		// os.Open succeeds on a directory as readily as on a regular file —
173		// no error, nothing distinguishing the two. JWT_SIGNING_KEY_FILE
174		// pointed at a mount directory instead of the file inside it (an easy
175		// Kubernetes subPath-vs-mount-root mistake, and exactly the class of
176		// misconfiguration this story exists to catch) would otherwise pass
177		// this check and only fail later, whenever S7's signing code first
178		// tries to read it — deferring the failure this check exists to make
179		// immediate (Oren Castellan, PR #18 review).
180		if fi.IsDir() {
181			return "", fmt.Errorf("config: APP_MODE=issuer set but JWT_SIGNING_KEY_FILE %q is a directory, not a file", path)
182		}
183		f, err := os.Open(path)
184		if err != nil {
185			return "", fmt.Errorf("config: APP_MODE=issuer set but JWT_SIGNING_KEY_FILE %q is not readable: %w", path, err)
186		}
187		defer func() { _ = f.Close() }()
188		// Read one byte rather than open-close: an empty file (a Secret
189		// mounted but never populated) opens without error and would
190		// otherwise pass silently.
191		var buf [1]byte
192		if _, err := f.Read(buf[:]); err != nil {
193			return "", fmt.Errorf("config: APP_MODE=issuer set but JWT_SIGNING_KEY_FILE %q is empty or unreadable: %w", path, err)
194		}
195		return path, nil
196	}

// migrationSQL reads a goose-format migration file and returns just the Up
// section's SQL — the real deliverable in migrations/{shared,postgres}/,
// not a duplicated copy of the schema. Applying the actual migration files
// in tests is what keeps this test harness honest: if the migrations
// drift from what the Go code expects, the integration tests fail, not
// just a hand-maintained fixture.
func migrationSQL(t *testing.T, path string) string {
	t.Helper()
	b, err := os.ReadFile(path)
	if err != nil {
		t.Fatalf("reading migration %s: %v", path, err)
	}
	content := string(b)
	upStart := strings.Index(content, "-- +goose Up")
	downStart := strings.Index(content, "-- +goose Down")
	if upStart == -1 || downStart == -1 {
		t.Fatalf("migration %s missing +goose Up/Down markers", path)
	}
	return content[upStart+len("-- +goose Up") : downStart]
}

// splitSQLStatements splits a migration's Up section into individual
// statements on ";" — used only for migrations that must NOT run as one
// multi-statement transaction (see the 00002 phone-CHECK migration's own
// comment). "--" comment lines are stripped first: this file's own
// prose comments use ordinary English semicolons ("...split; see the
// cockroachdb migration's own comment."), which a naive split-on-";"
// would otherwise cut mid-sentence and misidentify as a statement
// boundary. None of the actual SQL statements' string literals contain a
// ";", so splitting the comment-free text is safe — this is not a
// general-purpose SQL parser.
func splitSQLStatements(sqlText string) []string {
	var codeOnly strings.Builder
	for _, line := range strings.Split(sqlText, "\n") {
		if idx := strings.Index(line, "--"); idx != -1 {
			line = line[:idx]
		}
		codeOnly.WriteString(line)
		codeOnly.WriteString("\n")
	}

	var out []string
	for _, stmt := range strings.Split(codeOnly.String(), ";") {
		if strings.TrimSpace(stmt) == "" {
			continue
		}
		out = append(out, stmt)
	}
	return out
}

## 05 Data Ops — DDL review, LT-51 `oauth_client`

Reviewed against the universal half of `ddl-review-checklist.md` and the LT-51 ruling. **One real defect, one design gap, two notes.** Everything else is right, and the constraint naming here is more thorough than my own schema's — every constraint including the primary key is named.

### 1. `ck_oauth_client_granted_scopes_single` does not do what it says — please fix

```sql
CHECK (array_length(granted_scopes, 1) = 1)
```

**`array_length('{}'::text[], 1)` returns NULL**, not 0 — an empty array has no dimension 1. And a CHECK constraint fails only on FALSE; **NULL passes.** So `granted_scopes = '{}'` satisfies this constraint, and a client with *no* scope is insertable by exactly the rule written to prevent it.

The comment says the intent is "exactly one scope, not merely a nonempty set." As written it is neither: it rejects two or more, and admits zero.

```sql
CONSTRAINT ck_oauth_client_granted_scopes_single
  CHECK (cardinality(granted_scopes) = 1
         AND granted_scopes[1] IS NOT NULL
         AND length(trim(granted_scopes[1])) > 0)
```

`cardinality` returns 0 for the empty array, so `0 = 1` is FALSE and the row is rejected. The two extra clauses close the neighbouring hole: `ARRAY[NULL]::text[]` and `ARRAY['']::text[]` both have cardinality 1 and would otherwise pass, giving a client one scope that is not a scope.

This is the A6 rule landing on a new table: **the accepted set is what the expression accepts, not what the comment says it accepts.** Worth checking by insertion rather than by reading — `INSERT … granted_scopes = '{}'` is a two-line test.

### 2. `updated_at` has no mechanism to ever update

Defaulted to `now()` and never touched again by anything in this DDL — no trigger, and unlike the main DAO, no contract clause making the writing layer responsible. Secret rotation and disabling are the two things that will happen to these rows, and both are exactly what `updated_at` exists to record. As it stands it will equal `created_at` for the lifetime of every row, which is worse than not having the column: a reader will reasonably believe it means something.

Either a `BEFORE UPDATE` trigger setting `updated_at = now()`, or an explicit statement that the issuer's write path sets it — with the second recorded somewhere the issuer's author will see it. I don't mind which; I mind that neither exists.

### 3. `name` was already in the ruling — not an amendment

Flagging it was the right instinct, but my LT-51 message specified `name TEXT NOT NULL, non-empty CHECK`. Nothing to approve; it is implemented as ruled.

### 4. `audience` — accepted, with the asymmetry noted

Correct addition and correctly reasoned: `idp-connector` and `api-service` are different audiences, and without a per-client value there is nothing to put in `aud`. Not PII. Approved as an amendment.

One thing to record rather than change: **`granted_scopes` is an array constrained to exactly one element, while `audience` is a scalar** — both are "exactly one," expressed two different ways. That is defensible (scope is conceptually a set that may later admit more; audience is not), but if the single-scope commitment ever relaxes, the scope CHECK is the thing that changes and `audience` is the thing someone will forget to reconsider. A line in the comment naming that would help.

### 5. `client_id` is case-sensitive — say so

`TEXT` primary key with a charset CHECK, so `Client-A` and `client-a` are **distinct rows**. That is normal for OAuth client identifiers and I am not asking for a change — but `user_credential.username` in the main schema is case-*folded* for uniqueness, so a reader moving between the two schemas has every reason to assume the same rule applies here. One comment line prevents someone "fixing" the inconsistency later.

### Passes

Separate `issuer` database with its own version table and DSN, as ruled — the structural-impossibility argument for the cross-database join is recorded accurately. Every constraint named. `secret_state` present with a tying CHECK, and correctly simpler than `user_credential`'s since an Argon2id PHC string is self-describing and needs no `hash_algo`/`hash_cost`. `client_id` charset matches the ruling, and A4 is correctly *not* applied, with the reason stated. `TEXT[]` deliberately PostgreSQL-only, reason recorded. No PII columns, no retention clock, and the contrast with the main schema is written down. `goose Down` present. No `NO TRANSACTION` needed — this is a fresh `CREATE TABLE`, not a `DROP`+`ADD`.

**Verdict:** fix finding 1, resolve finding 2 either way, add the two comment lines, and this is approved from 05.

**2. `GrantLimiter` wiring order — confirmed correct.** `limiter.Allow(ctx, clientID, sourceIP)` runs before `store.Get`, and `TestNewTokenHandler_LimiterDenies_SlowDown429` proves it directly (`store.gotIDs` stays empty when the limiter denies). **Two additional findings from my own read:**

- **A no-Basic-Auth request never reaches `limiter.Allow`.** The handler returns 401 before computing `sourceIP` or touching the limiter at all when `hasBasicAuth` is false. `sourceIP` doesn't require a `client_id` to key by — an attacker sending zero Authorization headers can flood `/auth/token` at line rate, paying only a `ParseForm` + JSON-encode cost, entirely outside this endpoint's own rate limiter. Flagged in the code itself as "for 02's review" — I'm ruling it acceptable for this take-home's single-replica lab scope, but it should be named as a scaling caveat rather than silently assumed to hold at any replica count.

No blocking findings on the three questions asked. Approve, with the two additional notes above as follow-ups, not blockers.
