### One interaction that must not be "fixed"

`oldest_surviving_row_age_seconds` is published **only from a `Drained` result** (`multi-db-strategy.md` §3c — the value is meaningless mid-sweep, when deletable rows remain by construction and the oldest survivor is old). So a sweep that runs but never drains — hitting `maxRows` every batch — emits **no valid sample**, and rule 1 fires.

**That is correct behaviour, not a false positive.** A sweep that cannot drain is not keeping up, which is exactly what should alert. Do not "fix" it by publishing non-drained values: that would replace a true alert with a metric that reports a large age every run and trains everyone to ignore it.

### Addendum — the skip rule's window, and why it needed more than a number (05)

**Theo's deviation is confirmed: rolling 7 days, fire at ≥2 skipped runs.** He is right that "~25% over a rolling day" is structurally meaningless once `I` = 24h — a day holds at most one scheduled run, so the threshold could only ever be 0% or 100%. That was my error: I wrote rule 3 before pinning `I`, and did not revisit it when I did.

**But widening the window alone does not restore what rule 3 was for, and that is worth stating rather than quietly accepting.** Rule 3 exists as the *early* warning — it should fire while the sweep is still completing, before rules 1 or 2 trip. At `I` = 24h it cannot: two skips spread across seven days already lets a row reach `W + 2I`, which is exactly `RetentionWindowExceeded`'s threshold, and two *consecutive* skips reach `W + 3I` and trip it outright. A skip-count rule at this interval fires **with** rule 2, not before it. Any threshold low enough to lead it (≥1 skip in 7 days) fires on a single node restart and gets muted.

**So the early warning has to key on duration, not skips** — and the data for it is already persisted in `retention_sweep_run` (A7, `05-data-ops/multi-db-strategy.md` §3d):

- **`RetentionSweepDurationApproachingInterval`** — low severity. Fires when `finished_at - started_at` exceeds **0.5 × I** on any run in the last 7 days. This is the genuine leading indicator: run duration climbing toward the interval is *why* skips start, and it is observable while every run still completes. At take-home volumes it should never fire; it is a canary for growth, not a current condition.
- **`RetentionSweepSkipping`** — low severity, as Theo has it: `sum(missed_slots)` over a rolling **7 days ≥ 2**. Kept as the backstop for skips with causes other than duration — node pressure, failed pods, a suspended `CronJob` — which the duration rule cannot see.

Both remain non-suppressing on rules 1 and 2, per the original ruling.

**If `I` ever changes, all four thresholds move together** — `2I` for rule 1, `W + 2I` for rule 2, `0.5I` for the duration rule, and the 7-day window for the skip rule, which is `7I` and should be written as such. One more argument for deriving everything from a single `sweep_interval_seconds` constant rather than committing the arithmetic to the rule file: the failure this addendum corrects was exactly a hardcoded assumption surviving a change to the value it depended on.

### Addendum — where the metric comes from (05, after Amber's inventory)

Prometheus scrapes `api-service`, not the `CronJob`. The sweep is a short-lived pod and the scraper a long-lived one; they never overlap, so the sweep must **persist** its per-class result for `api-service` to read. Specified as contract amendment **A7**, `05-data-ops/multi-db-strategy.md` §3d — a `retention_sweep_run` table, written twice per run, read by `api-service` with the same runtime credential (all DML, no new grant), DDL in the three per-backend migration directories, self-pruned at 30 days, explicitly **not** a `RetentionClass` and explicitly **never** writing to `deletion_log`.

**One correction to the requested shape, which changes what the alert rules can key on.** A `skipped_reason` column cannot work: under `concurrencyPolicy: Forbid` a skipped run **has no pod**, so nothing executes that could write a row explaining itself — the column would be NULL on every row that exists. Skips are instead recorded by the *next* run as **`missed_slots`** (the gap since the last `finished_at`, divided by `I`, minus one). The three alert rules are unaffected in substance, and gain a cleaner source:

- **`RetentionSweepNotReporting`** keys on the age of the latest non-NULL `finished_at` per class — a genuine absence of rows, not a stale scrape.
- **`RetentionWindowExceeded`** keys on `oldest_surviving_at` from the latest **drained** row; the table's tying CHECK (`drained OR oldest_surviving_at IS NULL`) makes a non-drained value unrepresentable rather than something the rule has to filter defensively.
- **`RetentionSweepSkipRate`** becomes `sum(missed_slots)` over a rolling day against expected runs — **computable from the table alone**, with no dependency on scraping Kubernetes `CronJob` events, which is what LT-44 5a's skip-visibility requirement was reaching for.

A third distinguishable state falls out that none of the three rules previously had: a row with a NULL `finished_at` means the sweep **started and died**, as opposed to never having been scheduled. Worth a low-severity rule of its own if Theo wants it — a crashing sweep and an unscheduled one need different fixes, and today both look like silence.
