## Objection — LT-51 refinement The identical-response-body requirement for `invalid_client` (criterion 3, PO-script step 3) closes the obvious side channel — an attacker can't distinguish "unknown `client_id`" from "known `client_id`, wrong secret" by reading the response — but it doesn't close the one that actually matters for an authentication endpoint: **timing**. If the lookup succeeds, it runs Argon2id against the submitted secret before deciding — deliberately slow, because that's the whole point of Argon2id. That asymmetry is a textbook timing oracle: an attacker who can measure response latency (trivially, over many requests, even through network jitter) can enumerate valid `client_id`s without ever reading a byte of the response body the criteria so carefully made identical. ## Objection — LT-41 refinement Same principle I raised on LT-51's `/auth/token`, but a harder version of it, and unaddressed here: the F3 criterion ("fails closed with a generic error that doesn't distinguish no-token/bad-token/vendor-rejected") only covers response *content*.
