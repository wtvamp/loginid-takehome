11	## Constraints, not up for re-derivation (PM's ruling)
12	
13	- **One static HTML page, embedded in the `api-service` binary via `go:embed`.** Not a separate service, not a separate deploy artifact.
14	- **Served at `GET /demo` on the verifier**, same origin as the API it demonstrates — no CORS work, and critically, **no secret is ever baked into the page itself**.
15	- **The visitor pastes a QA client id and secret** (the same QA clients already seeded for review, `qa-client-credential`) **that live only in the browser tab** — never persisted, never sent anywhere but this origin's own `/auth/token`.
16	- **The page mints a real token and drives the real endpoints** — no simulated/fake responses. Every action shows the request as a literal `curl` line next to the raw response.
17	- **Required panels/flows:**
18	  1. Masked search beside full read (the `read:own`/`read:any` scoping distinction, side by side).
19	  2. The two `403`s beside each other with a byte-equality check on the response bodies (demonstrating the anti-enumeration identical-content design).
20	  3. The `401` (no/invalid token).
21	  4. The `reason_code` enum: one accepted value, one rejected value, shown together.
22	  5. The rate limit tripping (a real burst against the real limiter, shown live, not staged).

35	## Acceptance criteria
36	
37	- [ ] `GET /demo` serves a single HTML page embedded via `go:embed` in the `api-service` binary — no separate deploy artifact, no separate service.
38	- [ ] **Architecture stated explicitly, per Marcus's review (item 1):** the page's JS calls the real `/auth/token` and protected endpoints **directly from the browser** (same-origin `fetch`, using a token the browser itself obtained) — `api-service`'s server-side code never sees the plaintext QA secret at all; it only ever serves static content at `/demo`. This is the design, not an implementation detail left implicit — if any future change introduces a server-side proxy step instead, that handler would need its own never-log coverage on the request body specifically (a new criterion at that point, not assumed covered by "the page" the way this one is).
39	- [ ] The page never contains a secret value in its own source/markup/JS — the QA client id/secret are entered by the visitor into the page at runtime and held only in browser memory/DOM state for that tab, never written to `localStorage`/`sessionStorage`/a cookie, and never logged by the client-side JS to the console.
40	- [ ] **Marcus's seat, credential-handling criterion:** the page's own JS never sends the pasted client secret anywhere except this origin's own `/auth/token` endpoint, exactly once per mint, over HTTPS — enforcement site: read the shipped JS directly, confirm no other network call ever references the secret variable, and confirm the token (not the secret) is what's held and reused for subsequent calls.
41	- [ ] **Added per Marcus's review (item 2), a real gap — browser autofill/password-manager save prompts.** "Memory-only, never localStorage" covers what the application does, not what the browser's own chrome does: a plain credential-shaped `<input>` can trigger a "save this password?" prompt, putting the QA secret into the visitor's OS-level password store indefinitely — completely outside this design's control once that happens. Enforcement site: the secret input uses `type="password"`, `autocomplete="off"` (falling back to `autocomplete="new-password"` if a given browser ignores `off`, which some do), and a field `name`/`id` that doesn't pattern-match what password managers heuristically look for (avoid `password`/`secret` as the literal attribute value; something like `qa-token-input` is safer).
42	- [ ] `/demo` and its own requests are excluded from audit-log bodies — the page's own static-asset serving and the visitor's direct browser-to-API calls (per the architecture criterion above) shouldn't pollute the audit trail with demo traffic the same way a real caller's would, or should be clearly distinguishable if they do.
43	- [ ] The never-log lint (LT-49) covers this story's own new code paths, the same as everywhere else in this project — no exemption for "it's just a demo page."
44	- [ ] The static `/demo` handler sits behind the same rate limiters as everything else `api-service` serves — no special-cased bypass for the demo route.
45	- [ ] No authentication bypass anywhere in this story's own code — the demo page is a client of the real, fully-enforced API, not a backdoor or a relaxed-auth mode reachable only from `/demo`.
46	- [ ] All required panels/flows present and each drives the **real** endpoint, not a canned/fake response: masked-vs-full read, the two 403s with a byte-equality check shown in the UI, the 401, the reason_code accept/reject pair, the rate limit tripping live.
47	- [ ] Every action displays the literal `curl` command alongside the raw response — a viewer could copy the `curl` line and reproduce the call themselves.
48	- [ ] Warren's visual criteria (palette/type scale, system fonts only, left-to-right request→response layout, highlighted masked fields, the six-color legend, responsive at phone width, no raw JSON, one-sentence-per-panel copy from Imogen) are all met — enforcement site: Warren's own visual review at the live URL, a precondition to the PO review, not a substitute for it.
49	- [ ] No CORS configuration anywhere in this story's diff — same-origin service of the page is what makes this unnecessary; if a PR adds CORS handling, that's a signal the page isn't actually being served same-origin as designed.
50	- [ ] Tests (Renata's, per the story's own engineering ownership): confirm `/demo` serves the embedded page, confirm the embed doesn't accidentally bundle any real secret file matching the never-log-list's field names, confirm the route exists in both `verifier`/default `APP_MODE` and doesn't get exposed on `issuer`/`sweep` modes (this is a demo of the search/retrieve/connector-adjacent surface, not the issuer internals).

**Objection (Tobias Lindqvist) — LT-53, shared-limiter blast radius** Marcus's coverage is thorough on the secret-handling mechanics, but the doc has a real gap on item 5, the live rate-limit trip, and it's a gap Marcus wasn't seated on. The rate limiter is a shared production control on `api-service`, not a per-demo-visitor sandbox. Nothing in the acceptance criteria or the PO review script says what the limiter's scoping key actually is (IP? client_id? global?). If it's IP-scoped and Warren/Naomi are reviewing from the same network as a concurrent third-party visitor (or from behind a shared corporate/VPN egress IP), one visitor's deliberate burst trips the same bucket that gates the reviewer's own session. If it's scoped to the QA `client_id` — which per the story is the *same* seeded QA client every visitor pastes — then it's worse: every visitor shares one identity, so one person's "trip the limiter" panel exhausts the bucket for literally everyone else on `/demo` at that moment, including the PO doing her own functional pass through the exact same panels seconds later. The non-goal correctly forbids special-casing the limiter for the demo, which I agree with — but that's an argument for stating the blast radius, not for silence on it. Item 2 in your prompt is the same root cause restated: if scoping is by client_id, "tainting" the QA client for subsequent reviewers isn't a hypothetical, it's the designed behavior of a shared-identity rate limit being exercised by an adversarial-by-design panel. Concretely missing: an acceptance criterion or PO-review step that (a) states the limiter's actual scoping key so this is knowable rather than assumed, and (b) if it's coarser than per-tab, notes the operational fact plainly — e.g. "tripping this panel may transiently rate-limit other concurrent `/demo` visitors and reviewers sharing the same QA client/IP for the limiter's window" — rather than a viewer or reviewer discovering it as a mysterious 429 mid-review. **Counter-proposal:** add one line to the acceptance criteria — "State the rate limiter's scoping key in the panel's one-sentence copy (Imogen) if it is not per-visitor, and add a PO-review step confirming a self-triggered trip clears before the next required panel is run." No code change, no limiter redesign — just make the shared-blast-radius fact visible instead of implicit. Nothing else beyond this and Marcus's items; I don't have a fourth objection.
