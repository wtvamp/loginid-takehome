## Summary

Amber's observability inventory (`04-infra-devops/handoff-amber-observability-inventory.md`) found Prometheus can't scrape the sweep CronJob's stdout — it scrapes HTTP endpoints only, and the CronJob's pod is gone long before any scrape interval could reach it.

This implements the fix agreed for that finding, per amendment A7 (`05-data-ops/multi-db-strategy.md` §3d):

- Three new per-backend migrations (`retention_sweep_run`, not `migrations/shared/` — this is DDL). The row is written **twice** per run (INSERT with `finished_at` NULL at start, UPDATE at completion) so "never started", "started and died", and "completed" are all distinguishable without a separate status column — mirrors the existing `secret_state` pattern. `missed_slots` is computed by the *next* run against the gap since the previous completion, since a skipped run under `concurrencyPolicy: Forbid` has no pod to record its own skip.
- New `internal/sweepstore` package: `Store` writes/reads the table; `NewMetricsHandler` serves a fresh `prometheus.Registry`, rebuilt from the table's current state on every scrape (never a cached poller), failing the scrape (500) rather than serving an empty-but-200 response on a database error.
- `internal/sweep` gained a `RunRecorder` seam (nil-tolerant, matching the existing `MetricEmitter` convention — a recorder failure is logged and never turns a real, successful deletion into a reported sweep failure) and an `interval` parameter for `missed_slots`.
- `cmd/api-service` wires the recorder into `APP_MODE=sweep`, and the `/metrics` server (`:9101`, Service port name `metrics`, agreed with Theo Bergman for his ServiceMonitor/NetworkPolicy in PR #68) into `APP_MODE=verifier`, reusing the existing ping-DB handle.
