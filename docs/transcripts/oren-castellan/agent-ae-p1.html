This PR is 03's fix: the sweep code (cmd/api-service's APP_MODE=sweep mode) must fail loud on an unreachable database instead of hanging, independent of whatever network fix lands. Root cause: `dao.New`/`sql.Open` never actually dial a connection — they just validate the driver/DSN string. So nothing bounded the FIRST real connection attempt, which happened inside `internal/sweep.Run`'s own first `DeleteExpired` call, using a context derived only from `signal.NotifyContext(context.Background(), syscall.SIGTERM, syscall.SIGINT)` — no deadline of its own. A genuinely unreachable database meant an unbounded hang. The fix, in cmd/api-service/main.go's `runSweepMode`: 1. A `log.Printf("api-service: sweep starting, classes=..., interval_seconds=%s", interval)` line fires immediately, before anything touches the database. 2. A NEW bounded connectivity check: opens a separate `*sql.DB` via `sql.Open(driverName, cfg.DBDSN)` (using the existing `sqlDriverNameFor` helper), then calls `pingDB.PingContext(pingCtx)` where `pingCtx` has a `context.WithTimeout(context.Background(), sweepDBConnectTimeout)` (20 seconds). On ping error, logs a classified failure line via a new `classifySweepDBConnectError(err) string` helper (checks `errors.Is(err, context.DeadlineExceeded)` for "connect_timeout", else substring-matches "connection refused" and "no such host" in the error text, else "unknown") and calls `os.Exit(1)` immediately — never proceeding to `sweep.Run` at all. 3. Only if the ping succeeds does execution continue to open `repo` via `dao.New` and call `sweep.Run` as before. 4. New `config.SweepIntervalSeconds` field (purely descriptive env var `SWEEP_INTERVAL_SECONDS`, classified in `config.OptionalEnvVars` — never read by internal/sweep's own logic, just echoed in the startup log line). I already live-verified this against a real unreachable database (a non-routable IP as the Postgres host) and confirmed: the startup line appears immediately, the process fails after exactly 20 seconds with `class=connect_timeout` logged, and exits non-zero. I also re-ran it against a real reachable Postgres to confirm the happy path has no regression. Please focus your review on: 1. Check that `pingDB.Close()` is called on every exit path. 2.
