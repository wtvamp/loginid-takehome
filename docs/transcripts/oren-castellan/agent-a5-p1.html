Theo (04) already fixed the manifest itself in a separate, already-merged PR (#48). This PR is Renata's fix for the other half of that finding: the binary itself let a missing auth config silently start and serve broken requests, with nothing to catch a future recurrence. The PR does three things: 1. Adds `internal/config.RequiredAuthEnvVars(service, mode string) []string` in internal/config/config.go as a single source of truth for which auth env vars a given (service, mode) combination requires. 2. Adds startup validation to cmd/idp-connector/main.go (refuses to start if AUTH_JWKS_URL, AUTH_JWT_ISSUER, or CONNECTOR_JWT_AUDIENCE is unset) and rewrites cmd/api-service/main.go's existing validateAuthConfig to read from the same RequiredAuthEnvVars source — which also fixes a real pre-existing gap: api-service's verifier mode never actually checked AUTH_JWKS_URL (an earlier PR, #42, added the issuer/audience check but missed this one). 3. Adds internal/config/manifest_test.go — a new test that parses the REAL deploy/api-service.yaml and deploy/manifests.yaml Kubernetes manifests with gopkg.in/yaml.v3, and asserts every Deployment sets every env var its own (service, mode) requires, per RequiredAuthEnvVars. This is meant as a structural CI regression guard so this exact class of gap (config supported by code, never wired into one specific manifest) can't recur silently a fourth time. +// RequiredAuthEnvVars is the single source of truth for which auth-related
+// env vars a given (service, mode) combination MUST have set to function
+// correctly — read by both this process's own startup validation
+// (cmd/api-service/main.go's validateAuthConfig, cmd/idp-connector/main.go's
+// equivalent) and, independently, by internal/config's own
+// TestManifestsSetRequiredAuthEnvVars, which parses the actual deployed
+// manifests (deploy/api-service.yaml, deploy/manifests.yaml) and asserts
+// every Deployment sets everything its own (service, mode) requires.
+//
+// Exists because of two separate live-review incidents in one day, both
+// the same shape: a real, correctly-signed token failed verification
+// because a required auth env var was silently absent from a
+// Deployment's manifest, and nothing caught it before a human noticed
+// the symptom in production. cmd/api-service/main.go's own
+// validateAuthConfig (added after the first incident) only checks the
+// binary it lives in — it has no way to know cmd/idp-connector's
+// Deployment was missing AUTH_JWKS_URL/AUTH_JWT_ISSUER entirely (the
+// second incident), because idp-connector never runs that check at all
+// until this same list is wired into its own main() too. And neither
+// check, however complete, can catch a manifest that's simply missing
+// the variable outright before a real request exercises the gap — only
+// a test that reads the manifest text itself can do that ahead of time,
+// which is what this declaration exists to make possible.
+//
+// service is "api-service" or "idp-connector" — the binary, not the
+// Deployment name (api-service and api-service-issuer are the SAME
+// binary in different modes). mode is "verifier"/"issuer" for
+// api-service (matching AppMode's own two values), or "" for
+// idp-connector, which has no mode concept.
+func RequiredAuthEnvVars(service, mode string) []string {
+	switch {
+	case service == "api-service" && mode == "verifier":
+		return []string{"AUTH_JWT_ISSUER", "AUTH_JWT_AUDIENCE", "AUTH_JWKS_URL"}
+	case service == "api-service" && mode == "issuer":
+		// AUTH_JWT_AUDIENCE deliberately absent here — the issuer mints
+		// each token's aud from the per-client oauth_client.audience
+		// column (tokenhandler.go), never from its own config, so
+		// requiring it would reject a valid issuer configuration for a
+		// variable it has no use for (validateAuthConfig's own doc
+		// comment states this same reasoning).
+		return []string{"AUTH_JWT_ISSUER"}
+	case service == "idp-connector":
+		return []string{"AUTH_JWT_ISSUER", "AUTH_JWKS_URL", "CONNECTOR_JWT_AUDIENCE"}
+	default:
+		return nil
+	}

Findings for Renata — PR #53, `fix/idp-connector-config-validation`: 1. **`config.go`: `RequiredAuthEnvVars` default case is the weakest point in this PR.** `internal/config/config.go` (new func, `default: return nil`) means any unrecognized `(service, mode)` pair — a typo'd `APP_MODE` like `"Verifier"` or `"verifer"` in a future manifest edit — silently requires *zero* env vars. Both `validateAuthConfig` call sites and the new manifest test read this same list, so a typo produces no startup failure and no CI failure: exactly the "config supported by code, never wired in" class of bug this PR exists to catch, just moved one level up. The default should either `panic`/return a sentinel "unrecognized" error the caller treats as fatal, or the manifest test should independently assert the *set* of `(service, mode)` pairs it saw is a subset of ones the switch explicitly recognizes (not just `len(required) == 0` → skip, which is what `manifest_test.go` does today at the `if len(required) == 0 { continue }` line — that line can't distinguish "issuer mode legitimately needs nothing extra" from "mode string didn't match anything"). 2. **`manifest_test.go`'s `serviceForImage` substring match will silently stop matching on a digest-pinned image.** It matches on `"/idp-connector:"` / `"/api-service:"` (colon required). A future manifest pinning by digest (`.../idp-connector@sha256:...`) has no such colon and would be `recognized=false`, silently skipped — not caught by the `checked == 0` guard since other deployments still match. Worth a comment or a second match arm for `@sha256:` at minimum, since digest-pinning is a plausible supply-chain hardening move 04 could make later without knowing it silences this test. 3. `serviceForImage`'s false-positive risk you asked about (e.g. `istio/idp-connector:sidecar`) is real in principle but not reachable today — no sidecars in either manifest — so I'd leave it, not block on it; flag as a known limitation in the doc comment. 4. **Call order in `cmd/idp-connector/main.go` is correct** — `validateAuthConfig()` (line 43) runs immediately after `config.Load()` and before the vendor client (`NewHTTPVendorClient`/stub) and `http.ListenAndServe` are constructed, so nothing executes against a bad/empty `AUTH_JWKS_URL` first. 5. **`t.Setenv` isolation is fine** in both `main_test.go` files — each subtest gets its own `t`, `t.Setenv` auto-restores at test end, no `t.Parallel()` used anywhere so no cross-subtest race. 6. Error messages are good — name the exact missing var, consistent with the "loud crash beats silent 401" framing stated in the comments. Net: one real gap (finding 1) worth a line of code before merge; finding 2 worth a one-line comment; the rest is solid.
