78	## Priya Nandakumar's ruling — the alert formula (05)
79	
80	**Answer: skip-visibility alone is not sufficient, a grace term is needed, and — most importantly — skip-visibility must NOT be used as a suppression term.** Three alerts on three properties, none suppressing another.
81	
82	### Why suppression-on-skip is the dangerous option
83	
84	If the alert is silenced whenever a skip signal was emitted, then a sweep that *chronically* overruns — every scheduled run skipped because the previous never finished — emits a skip signal every interval and **suppresses the alert permanently.** The suppression mechanism becomes the failure mode, and it does so precisely when the sweep is failing hardest. A single skip and an endless run are indistinguishable by the presence of a skip signal; they differ only in how many consecutive intervals produce no fresh sample.
85	
86	This is the same error as alerting on the mechanism rather than the property. The property is *"is data surviving past its retention window, and is the sweep still reporting?"* — neither of which is answered by "was a run skipped."
87	
88	### The three rules
89	
90	Let **W** = the class's retention window, **I** = the CronJob interval, **D** = a sweep run's duration.
91	
92	**1. `RetentionSweepNotReporting` — per class.** Fires when no fresh `oldest_surviving_row_age_seconds` sample for that class in **more than 2I**.
93	
94	A single skip produces a gap of exactly 2I (sample at *t*, next at *t*+2I), so it does not fire — that is the grace for the case this question is about. Two consecutive skips produce 3I and it fires. A dead sweep fires. **This is the alert that distinguishes skipped from dead, and it does so without consuming the skip signal at all** — by counting missed samples rather than by trusting an explanation.
95	
96	**Per class, not global**, because the sweep is per class by contract (`multi-db-strategy.md` §3c — `DeleteExpired(ctx, class, olderThan, maxRows)`, one class per call). A class whose step errors while the others succeed would keep the global series fresh and go silent unnoticed.
97	
98	**2. `RetentionWindowExceeded` — per class.** Fires when `oldest_surviving_row_age_seconds{class} > W + 2I`.
99	
100	**The third term is `2I`, not `I`.** One I is the legitimate lag — a row becomes eligible just after a sweep completes and waits a full interval for the next one, so a healthy system reaches W + I routinely and an alert at W + I fires on every normal cycle. The second I absorbs one skipped run. This assumes **D < I**; if D approaches I the sweep is not keeping up and rule 3 is the real signal.
101	
102	**3. `RetentionSweepSkipRate` — low severity, the early warning.** Fires when skipped runs exceed ~25% over a rolling day. **This is where LT-44 5a's skip-visibility signal is consumed** — as evidence in its own right, not as a suppression term on rules 1 or 2. It catches "the sweep is completing but only just" before either of the others trips.
103

116	**If I changes, rules 1 and 2 both change.** They are expressed in terms of I deliberately: a hardcoded 9 days silently becomes wrong the moment the schedule moves to twice daily or weekly. Prefer deriving them from one `sweep_interval_seconds` constant in the rule config over writing the arithmetic out.

1	# Observability + Never-Log Enforcement
2	
3	Design-only. Covers logging, metrics, and tracing for both services, and — the harder half — how `handoff-04-secrets.md`'s never-log list gets enforced as a mechanism, not just stated as a policy.
4	
5	## Logging
6	
7	Structured logging (`slog`, Go stdlib — no third-party logging library needed for two services this size), JSON output, one line per event. Every log line that touches a request carries `sub` (caller identity), the endpoint, status, and a request id — never the request or response body wholesale. This is the pattern the never-log list requires (hand-off item 8: "full request bodies of `POST /auth` and `POST /identity`... both contain items above by construction") — the enforcement mechanism is that handlers log a small, explicit field set assembled by hand, never `log.Printf("%+v", req)` or equivalent reflection-based dumps of a request/response struct. A struct that contains a password field can't leak through a log statement that never receives the struct.
8	
9	**Enforcement beyond "write it carefully":**
10	- A lint rule (a `golangci-lint` custom check, or a simple `go vet`-style grep in CI) that flags any log call passing a whole request/response struct, a `*http.Request` body, or any variable named/typed to match the never-log list's fields (`password`, `token`, `secret`, `dsn`, `client_secret`). Not foolproof — a determined developer can rename around it — but it catches the accidental case, which is the common one.
11	- Error-path discipline: wrapped errors are logged with `err.Error()` truncated/sanitized where the error type is known to carry sensitive detail (a DB driver error can echo the DSN; a vendor HTTP client error can echo the response body per hand-off item 4) — the wrapping layer strips those before the error reaches a log call, not the log call itself deciding case-by-case.
12	
13	## Metrics
14	
15	Standard RED metrics (rate, errors, duration) per endpoint, via Prometheus client library, scraped by whatever the lab cluster already runs (not stood up new for this take-home). Labels: method, route, status class — never a label with cardinality tied to user data (no `sub` or phone number as a metric label; that turns a metrics backend into an accidental PII store with no access control at all, which is a worse leak than a log line since metrics systems are typically more widely readable).
16	
17	## Tracing
18	
19	Not built out here — a two-service take-home with no running collector doesn't get more credible by naming OpenTelemetry. If ever added, it follows the same field discipline as logging.

21	## The never-log list, operationalized
22	
23	Hand-off's nine items map to two enforcement surfaces, not nine separate mechanisms:
24	
25	1. **Application-level:** the structured-logging discipline above (explicit field sets, the lint check, error-wrapping sanitization) covers items 1, 2, 5, 6, 7 (password, tokens, JWTs, client secrets, DSN) — these never enter a Go `log`/`slog` call in the first place.

30	
31	Per the hand-off's Kubernetes-specific requirements: the log stream carrying `sub`/scope/record-id/timestamp (the "fact of access" the never-log list still permits) is itself sensitive enough to reconstruct who looked up whom, so it gets its own RBAC — a distinct, narrower `Role` bound to an incident-review group, separate from any ServiceAccount's `Secret`-read grant (`./secrets-delivery.md`). Mechanism: if logs go to a cluster-local sink (e.g., Loki), that sink's read API gets its own RBAC/auth in front of it, not the same one guarding `kubectl get secrets`; if logs go to an external platform, the equivalent is a scoped read-only role in that platform, provisioned separately from any cluster credential.

33	## Retention-sweep observability (05's S5 requirement, final)
34	
35	Per `../05-data-ops/pii-governance.md`: the retention sweep must emit, per data class per run, three metrics — rows examined, rows deleted, and **the age of the oldest surviving row in that class**. An alert fires when that age exceeds the class's stated retention window plus one sweep interval. This is the one metric in this document tied to a specific reasoning worth repeating: a sweep job that silently stops running produces no error and no symptom on its own — "rows deleted" can't tell a broken sweep from a legitimately empty one, since both report zero. Oldest-surviving-row age is the one number that keeps climbing when the job is dead and holds steady when it's healthy, which is why it's the alerting signal, not just a nice-to-have metric alongside the other two.
