## Correction to `backlog.md`'s own S8 text, found before drafting

**Three real controls from `connector-security.md`'s attack-tree table (S3 red/blue, already run and ruled) needed fixing relative to `backlog.md`'s S8 acceptance criteria — one truly missing, one named in prose but never promoted to a checkable criterion, one already fixed in this doc but not credited in this section (Desmond's claims check corrected all three of these framings).** The table is the authoritative, already-ratified source:

1. **Leaf 1 (connection-reuse token leak) — named in prose, not promoted to a criterion.** `backlog.md`'s S8 **Description** paragraph already says, almost verbatim, "fresh isolated `Authorization` header per outbound request, never inherited from pooling/keep-alive" — so this isn't an undocumented gap, it's a requirement stated in prose that never became its own checkable acceptance criterion with an enforcement site. The criteria list only has the generic timeout/pool/backoff bullet. Promoted below.
2. **Leaf 5 (credential-stuffing oracle) — a genuine, total gap.** Rate limiting on outbound vendor calls, keyed per calling-API-client **and** per source IP, with a stricter threshold specifically on vendor-auth **failure ratio** (not just volume), paired with exponential backoff per identity attempted. Confirmed by reading `backlog.md`'s S8 text directly: no rate-limiting language anywhere, not even in prose.
3. **Leaf 4 (memory/crash-dump exposure), narrow-scoping half — already fixed in this doc's criteria below, just not credited here until now.** Two sub-controls beyond "never log the token" (which S8's existing criteria already cover): the token excluded from generic request/response dumps used in panic traces/debug output, and the token variable scoped to the narrowest function possible, never passed up the call stack. Both are already present as their own bullets below; this section previously undercounted the fix as covering two gaps instead of three.

Both are added below as acceptance criteria, since the attack-tree table already ruled on them (Residual L on both, after blue's response) — this refinement is transcribing an already-ratified control, not inventing a new one.

## Acceptance criteria (restated from `backlog.md` S8, plus the two additions above)

- [ ] Implements 02's token-lifecycle spec (`connector-security.md`, `decisions/connector-token-lifecycle-redblue.md`) without re-litigating the no-cache-by-default posture.
- [ ] No vendor token is persisted or cached across requests by default; if a future exception is ever justified it requires re-review, not a silent default change — enforcement site: no storage/cache call in the token-fetch path.
- [ ] Every outbound vendor call sets `context.WithTimeout`; the outbound HTTP client uses a bounded connection pool; token-refresh retries back off rather than tight-looping — enforcement site: the HTTP client construction plus a test asserting a timeout fires.
- [ ] **Added (attack-tree leaf 1):** a fresh, isolated `Authorization` header is constructed per outbound vendor request — never inherited from HTTP connection/keep-alive reuse. Enforcement site: a test making two sequential vendor calls with two different presented tokens through the same pooled client, asserting the second call's outbound header matches its own token, not the first call's.
- [ ] **Added (attack-tree leaf 5):** outbound vendor calls are rate-limited keyed per calling-API-client identity **and** per source IP independently, with a stricter threshold on vendor-auth failure ratio specifically (not just raw volume), paired with exponential backoff per identity attempted. Enforcement site: the rate-limit/backoff component plus a test asserting a high-failure-ratio pattern trips the stricter threshold before a high-volume-but-mostly-successful pattern would.
- [ ] The connector's own `/auth`/`/identity` handlers validate an inbound JWT with `aud: idp-connector-service` and `scope: connector:identity-lookup`, distinct from `api-service`'s audience — enforcement site: this handler's own middleware instance, with a test asserting a `loginid-api-service`-audience token is rejected here.
- [ ] `/identity` accepts the vendor token as a request header (not a body field, since the assignment's fixed `{"phone","name"}` body has no credential field), fails closed with a generic error that doesn't distinguish "no token" from "bad token" from "vendor rejected it" in **response content** (same user-enumeration discipline as elsewhere in this project) — per `connector-security.md`'s F3 resolution.
- [ ] **Resolved by 02's ruling (Tobias's objection, routed to Marcus):** apply a uniform response-time floor (~100ms, well under any `context.WithTimeout` budget elsewhere in the chain) across all three failure branches (no-token, bad-token, vendor-rejected) — narrows the trivially-observable timing gap into something requiring statistical analysis over many requests, not full closure. **The remainder is an accepted residual risk, stated explicitly in `connector-security.md` §4, not engineered away further** — full closure (delaying every request to match the vendor's worst-case latency) would be a real availability cost disproportionate to what it protects, since what's disclosed even in the worst case is only that a presented token's shape reached the vendor, never any subject's identity, existence, or PII (§4 already normalizes vendor-rejection reasons so *which* check failed doesn't leak either). This is a different, and correctly different, resolution from LT-51's dummy-Argon2id fix: that leak was a fully-controlled local computation makeable genuinely constant-time; this one involves a third-party network call whose latency distribution isn't this connector's to control. Enforcement site: `connector-security.md` §4's stated floor and residual-risk language, plus a test asserting all three branches return within a bounded time delta of each other (not "both fast" or "both slow" — comparably close, per the floor).
- [ ] The token variable is scoped to the narrowest function possible and never passed up the call stack beyond the vendor-call function itself — per attack-tree leaf 4's control (accepted that Go gives no guaranteed memory zeroing, but the exposure window is narrowed to one function call, not eliminated).
- [ ] Never logs, in any environment or error path: the end-user's vendor password, any vendor `access_token` or full `Authorization` header value, or raw vendor error response bodies (per `handoff-04-secrets.md`'s never-log list) — enforcement site: log-call review against that list, plus confirming the token field is excluded from any generic request/response dump used in panic traces or debug output, not only application logs (leaf 4's "same discipline as application logs" extension).
