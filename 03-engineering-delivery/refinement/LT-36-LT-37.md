**Product Owner:** Naomi Voss (01). **Research team:** Imogen Hale, Desmond Okafor, Tobias Lindqvist. **Engineering:** Renata Cole (03), running both in parallel worktrees. **Source:** `03-engineering-delivery/backlog.md` S3 (LT-36) and S4 (LT-37).

## Why pulled together, as a pair

Both depend only on LT-35 (merged), neither depends on the other, and Renata's running them in parallel worktrees — refining them together avoids two near-identical refinement passes and lets the shared acceptance criteria (conformance suite, sentinel translation) be stated once instead of twice, with only the genuinely backend-specific pieces (retry seam for CockroachDB; case-folding and app-side UUIDs for SQLite) kept separate.

## Acceptance outcome (both stories — no public-URL surface, same as LT-35)

Neither story has user-visible behavior yet — no handlers call these packages. Acceptance is mechanical: the conformance suite (LT-38, not yet pulled, but its assertions are what "done" means here even before it exists as its own story) run against each backend passes, sentinel translation is verified per-condition per-backend, and the CockroachDB-specific retry seam and SQLite-specific parity gaps are each proven, not just implemented.

## Shared acceptance criteria (both LT-36 and LT-37)

- [ ] Implements against LT-35's interfaces with no re-derivation of 05's schema, error-translation, or dialect reasoning — restated from `backlog.md`.
- [ ] Driver errors translate to the seven sentinels (`multi-db-strategy.md` §4) by structured code (SQLSTATE for Postgres/CockroachDB, extended result code for SQLite) plus our own named DDL constraints — **never free-text/`strings.Contains` matching on an error message**, per `decisions/error-semantics.md`'s superseded-but-standing rule and 05's §4. Enforcement site: the translation table/switch in each backend package; a grep for `strings.Contains` against any error string returns nothing in either package.
- [ ] Sentinel translation is proven per-condition, per-backend — not asserted by code review alone. **Pending LT-38, not yet enforceable:** once LT-38 lands, it must exercise every §4 condition against both backends and assert `errors.Is` against the correct sentinel, per `decisions/error-semantics.md`'s "mandatory per-backend translation, verified by an explicit test case per backend." Until then, this criterion cannot be marked accepted, per the hard rule in Non-goals.
- [ ] No raw driver error text (including a Postgres `DETAIL`/`Key (...)=(...)` line or a SQLite extended-code message) is ever wrapped, logged, or returned past the translation boundary — per `decisions/error-semantics.md` F50. Enforcement site: the translation function sanitizes to structured code + our constraint name before anything is wrapped for the log; a test asserting a constraint-violation error's logged/wrapped form contains no literal column value.
- [ ] `Upsert`'s `ON CONFLICT`/`ON CONFLICT DO UPDATE` (or SQLite equivalent) explicitly excludes `created_at` from the update-set list — per 05's Oren-finding-#3 ruling. Enforcement site: the SQL/query statement itself, plus a unit test asserting `created_at` survives a re-hydration `Upsert` unchanged, one test per backend (not one test assumed to cover both).
- [ ] `CreateProfileWithCredential` writes both rows in one transaction with `c.UserID` ignored on input and set from the newly created profile; on any failure, neither row exists. Enforcement site: a unit test per backend that fails the credential write deliberately (e.g. a duplicate username) and asserts the profile row does not exist afterward.

## LT-36-specific acceptance criteria (Postgres + CockroachDB)

- [ ] Every write method (`Create`, `Update`, `Upsert`, `Delete`, `CreateProfileWithCredential`) runs through the `withRetry` wrapper described in `multi-db-strategy.md` §4 ("The write-path retry seam") — an unexported helper inside the `postgres` package, not in the composite and not above the interface boundary. Enforcement site: the wrapper is the single call path every write method uses; grep confirms no write method executes a statement outside it.
- [ ] The wrapper retries only when the implementation's unexported `engine` field (set by `New` from the driver string) is `"cockroachdb"`; on `"postgres"` it calls the function once. Enforcement site: a unit test constructing both engine values and asserting call count under a forced-retryable and a non-retryable condition.
- [ ] The retry wrapper actually retries a genuine SQLSTATE `40001` (serialization failure) against real CockroachDB, not a mocked/simulated one. **Pending LT-38, not yet enforceable:** once LT-38 lands, it must exercise a real retryable condition against a CockroachDB testcontainer/instance, per `backlog.md`'s own acceptance criterion for this story. Until then, this criterion cannot be marked accepted.
- [ ] `Search` opens no explicit transaction and is not wrapped by `withRetry` — it's read-only and per `multi-db-strategy.md` §4's ruling never encounters `40001`. Enforcement site: code review confirming `Search`'s implementation has no `withRetry` call.
- [ ] Fuzzy name search uses `LOWER(name) LIKE ?` matching the GIN expression index, with explicit `%`/`_`/`\` escaping on caller input. Enforcement site: query construction plus a unit test with a search term containing a literal `%` or `_`, asserting it's treated as a literal character, not a wildcard.

## LT-37-specific acceptance criteria (SQLite)

- [ ] `Create` generates the UUID in Go before insert (SQLite has no server-side generation). **Pending LT-38 for the cross-backend proof:** once LT-38 lands, it must assert a populated `ID` comes back structurally identical to the Postgres path (same format, non-empty, DAO-generated either way); until then this package's own unit test (populated, non-empty `ID`) is code-review-verifiable but the cross-backend identity claim is not yet enforced.
- [ ] Search folds case **explicitly** — `LOWER(col) LIKE LOWER(pattern)` — rather than relying on SQLite's default ASCII case-insensitive `LIKE`, so the behavior is asserted by this package's own code, not an accident of the engine default. **Pending LT-38 for the cross-backend proof:** once LT-38 lands, it must assert the same rows in the same order as Postgres for ASCII input (per `multi-db-strategy.md`'s "What Search does on SQLite" section); until then this criterion cannot be marked accepted.
- [ ] The documented non-ASCII case-folding divergence (Postgres `lower()` is locale-aware, SQLite's is ASCII-only) is **not silently accepted as an untested gap** — it must appear as an explicit, named exception in this package's own documentation (a doc comment on the search implementation), not only in `multi-db-strategy.md`'s prose, so a reader of the code alone sees the limitation. Enforcement site: doc comment in the SQLite search implementation, cross-referenced to `multi-db-strategy.md`.
- [ ] `SQLITE_CONSTRAINT_UNIQUE`/`FOREIGNKEY`/`CHECK`/`PRIMARYKEY` map to the same sentinels as the Postgres package's SQLSTATE codes, disambiguated by the same DDL constraint names (not by table/column position, which can drift independently between the two schemas). **Pending LT-38, not yet enforceable:** once LT-38 lands, it must assert sentinel parity across both backends for the same logical condition; until then this criterion cannot be marked accepted.

## Non-goals

- LT-38 (the conformance suite itself) is not this pair's story to write — but its assertions are cited above as the actual enforcement site for several criteria in both. If LT-38 hasn't landed by the time LT-36/LT-37 are otherwise ready, those criteria are pending, not waived — flagged explicitly in the PO review script below, not silently marked done.
- No handler/API-layer work — `internal/api` calling into these packages is a later story.
- No production connection-pool tuning, migration-execution wiring, or observability — infra/DevOps scope.

**Hard rule on story status, not just criterion status (added per Tobias's objection):** LT-36 and LT-37 cannot be marked Done in `backlog.md` while any criterion whose sole enforcement site is LT-38 remains pending. Each story sits in an explicit third state — `implemented, verification pending LT-38` — distinct from both `in progress` and `Done`, until LT-38 lands and every cited criterion actually passes against both backends. This is stated as a rule, not a preference, because a PO under schedule pressure could otherwise read "flag the unverifiable parts pending" as license to mark the story Done overall with a footnote — and a footnote is exactly what gets missed three stories later when 04 reads `backlog.md` to decide what's actually shippable.

## Found by LT-38 before merge (2026-09-12)

LT-38's conformance suite, run against both backends before either PR merged, caught a real gap: neither backend's `Credentials().Create`/`Update` (nor `CreateProfileWithCredential`) actually validated `method_id` against `auth_method.is_active` or `requires_secret` before insert. The FK caught only a totally unknown `method_id`; the CHECK constraint on `secret_state` only validates internal consistency (secret/hash_algo/hash_cost presence), not cross-table consistency with `requires_secret` — `multi-db-strategy.md` §6 items 10 and 11 name this exactly, and state it must be DAO-layer validation because a `CHECK` cannot reference another table. Both backends had skipped writing that DAO-layer check. Fixed in both (`validateMethod` in each package's `credentials.go`, called from `Create`, `Update`, and `CreateProfileWithCredential`), verified against all three backends by `TestConformance_RequiresSecretRelationship` and `TestConformance_IsActiveEnforcement`. This is the conformance suite doing its job — caught before merge, not after.
