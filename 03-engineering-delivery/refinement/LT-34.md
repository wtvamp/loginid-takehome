**Product Owner:** Naomi Voss (01). **Research team:** Imogen Hale, Desmond Okafor, Tobias Lindqvist. **Engineering:** Renata Cole (03). **Source:** `03-engineering-delivery/backlog.md` S1 (LT-34).

## Why this story is pulled first

Per team-lead's recommendation, accepted: this is the walking skeleton — it proves the whole pipeline (build → deploy → publicly reachable) end to end before any feature carries real risk on top of an unproven deploy path. If CI/CD, the two-binary split, or the config surface don't work, every later story inherits that failure; pulling a feature story first would let a deploy-pipeline problem hide behind a feature bug. No objection to the sequencing.

## User-visible outcome (what "done" means at the public URL)

Both binaries are deployed and independently reachable at a public URL, each answering a health probe (`GET /healthz` or equivalent) with:
- HTTP 200
- a JSON body containing at minimum: `status: "ok"`, `service` (`api-service` or `idp-connector`), and an **opaque build identifier** (commit SHA) — per 02's ruling (`api-auth-design.md`), an opaque commit SHA/build id is the one exception allowed on an unauthenticated health endpoint; a full semver/version string naming dependencies is not. No build timestamp beyond what's implicit in the SHA — timestamp wasn't part of 02's exception and isn't needed for the freshness check. **Dependency, not yet confirmed:** `04-infra-devops/ci-pipeline.md` currently only tags the Docker image with the commit SHA at build time; nothing in 03 or 04's docs yet establishes a mechanism (e.g. `-ldflags -X` embedding the SHA into the binary, read by the health handler at request time) for the *running binary* to report it. This story's engineering owner (Renata/03) confirms and implements that mechanism as part of this story, or the build-info criterion is descoped to this story's follow-up.

This is the one user-visible behavior a walking skeleton has — no other endpoint, no DAO, no auth, no connector logic is expected to do anything yet. "Done" is verifiable by any reader with only a browser or `curl` and the URL, without reading any code.

## Non-goals (explicitly out of scope for this story)

- No DAO, no database connection, no `dao.New` implementation — stub handlers only, per the original S1 scope.
- No auth/authz — **now confirmed by 02, `api-auth-design.md`:** health endpoints are unauthenticated infrastructure, outside the API surface 02's threat model covers. The response body may reveal only up/down boolean(s) (optionally per-dependency, e.g. "DB: ok") and the opaque build identifier named above — never a version string, connection detail, stack trace, or anything on `handoff-04-secrets.md`'s never-log list. Enforcement site: code review against `api-auth-design.md`'s health-endpoint clause; nobody adds debug detail to the response body later.
- No connector logic (`/auth`, `/identity`) beyond the binary existing and starting.
- No production-grade observability (structured logging, metrics, tracing) — only enough output to confirm the process started; that's `04-infra-devops`'s `observability.md` scope, not this story's.
- No TLS/custom domain decisions — whatever the CI/CD pipeline's default publicly-reachable URL is (e.g., a platform-provided preview URL) satisfies "public URL" for this story; a custom domain is not a goal here.

## PO review script (what I will actually do to accept this story)

1. Open the PR's linked GitHub Actions run; confirm both the build and deploy jobs are green.
2. `curl -s <public-url-for-api-service>/healthz` and `curl -s <public-url-for-idp-connector>/healthz` (or whatever path engineering names — confirm the actual path from the PR description); confirm both return HTTP 200 and a JSON body with `status`, `service`, and a build-info field. Record both values in the PR thread.
3. **Mandatory freshness check, not conditional:** the PR must include a second, trivial follow-up commit (e.g., a comment or version-string bump) before merge. After that commit deploys, repeat step 2 and confirm the build-info field's value has changed from what was recorded the first time. This is required on every run of this story, not skipped because it's the first deploy — a "present and non-empty" value alone does not prove the pipeline is live, only that some value exists, which a hardcoded or stale one would also satisfy. Both recorded values (before/after) go in the PR thread as the evidence.
4. Skim the PR diff for `cmd/api-service/main.go` and `cmd/idp-connector/main.go`; confirm each is a thin wrapper (no route registration or config-loading logic inlined) per the acceptance criterion above.
5. Confirm the config-loading unit test (DSN/DSN_FILE precedence) is present and passing in the CI run.

If all five pass, the story is accepted and I mark it Done in `backlog.md` (03's file — 04/05's respective backlogs if they also track it) and notify the PM.

## Research team review

**Desmond Okafor — claims check:** Two unsupported claims found: (1) the build-info-injection mechanism was assumed to exist but no 03/04 doc establishes it (`ci-pipeline.md` only tags the Docker image, not the running binary) — fixed by making it an explicit engineering dependency Renata confirms in the PR, not an assumed given; (2) "not part of the API surface 02 designed auth for" was stated as settled when a grep of 02's docs finds no ruling on a health endpoint at all — fixed by rewording as this track's proposal, flagged for 02 to confirm. Everything else (package layout, config vars, thin-wrapper criterion, other non-goals) checked out against `PLANNING.md` and `decisions/go-layout-debate.md`.

**Tobias Lindqvist — objection:** The build-info freshness criterion and PO script step 3 didn't actually match — the fallback for "no prior observation" (present-and-non-empty) would fire on every first review, meaning the one check meant to distinguish "deployed" from "code exists" would never actually run in practice. Counter-proposal accepted: the PR must include a mandatory second, trivial follow-up commit before merge, and the PO checks the build-info value before and after that commit — not a conditional check that reduces to existence-only on the common path.

**Naomi Voss — ruling:** Both fixes applied to the doc as written above. This refinement is accepted and handed off. Update post-hand-off: 02 has since ruled on the health-endpoint auth question (unauthenticated confirmed, body restricted to up/down booleans plus an opaque build id — no version string) — the one remaining dependency is (1) how build-info gets from commit to running binary (ldflags or equivalent — Renata's call, stated in the PR).

## PO acceptance review — run against the live deployed URL

**Reviewer:** Naomi Voss (PO). **Date:** 2026-09-13. **Deploy:** `main@aa739d6`, GitHub Actions run `https://github.com/wtvamp/loginid-takehome/actions/runs/34736267439`.

Ran the review script directly:

```
curl --resolve loginid-takehome.uplifttech.org:443:67.168.194.236 https://loginid-takehome.uplifttech.org/healthz
→ HTTP 200
→ {"status":"ok","service":"api-service","build":"unknown"}
```

**Steps 1, 2, 4, 5 pass:** deploy job green, endpoint returns 200 with valid TLS, the JSON body shape is exactly `{"status","service","build"}` (matches 02's ruling — no version string, no extra fields), and this track's own code-level checks (thin wrappers, config precedence test) were already verified clean against PR #1 earlier in this doc.

**Step 3 (the mandatory freshness check) fails, and it fails for the reason the criterion exists to catch:** `build` is the literal string `"unknown"`, not a commit SHA. Per the PR description, the health handler falls back to `"unknown"` specifically when the `-ldflags -X` injection isn't wired through at build time — which is exactly what's happened: the Docker build (04's Dockerfile, LT-45) isn't passing the commit SHA into the `go build` invocation the way the PR's local-build instructions do. The mechanism that would let this criterion be checked at all — build-info actually varying between deploys — isn't present in the deployed artifact. This isn't a cosmetic miss; it's the one thing this story exists to prove (that the pipeline delivers a genuinely fresh, identifiable build), silently not proven.

**Verdict: LT-34 FAILS acceptance.** Not accepting with a footnote — a story whose entire point is "prove the deploy is real and traceable to a commit" cannot close while the one field that proves that is a placeholder. Per team-lead's read (independently reached the same way before I ran the script), this becomes a small, scoped follow-up PR: wire the commit SHA through the Docker build (`docker build --build-arg`/`ARG`/`ENV` → `go build -ldflags`), owned by whoever touches the Dockerfile — Theo (LT-45) most likely, since the gap is in the image build step, not the Go code itself; Renata's `-ldflags` invocation was already correct locally. LT-34 stays open until a re-deploy shows a real SHA and the mandatory second-commit freshness check (already satisfied in the PR's own two commits) can be re-run against two actually-distinguishable deployed values.
