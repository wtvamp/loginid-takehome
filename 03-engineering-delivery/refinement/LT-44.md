**Product Owner:** Naomi Voss (01). **Research team:** Imogen Hale, Desmond Okafor, Tobias Lindqvist. **Engineering:** Renata Cole (03, sweep-invocation code), Theo Bergman (04, `CronJob` manifest + metrics sink); design inputs: Priya Nandakumar (05, retention windows/clocks/classes), Marcus Ilori (02, seat on subject-deletion audit trail if any).

## Why this one, now

Per team-lead: without this, the README (LT-43, correctly deferred to write last) would have to list PII retention as stubbed — at a company whose own product framing is PII minimization, that's a real, visible gap in the submission, not a cosmetic one. Desmond's LT-43 finding made the case concretely: `DeleteExpired`/`DeleteProfile` exist and are tested on the DAO composite, but nothing schedules or calls either method — a designed-but-not-operational control. This is roughly a half-day story (a `CronJob` calling a `--sweep` mode of the existing `api-service` image, bounded by the already-built `maxRows`, audited) that turns a stub line into a delivered one.

## What this story actually is

Not new DAO methods — `DeleteExpired`/`DeleteProfile` already exist on the composite (05's `multi-db-strategy.md` §3c) and are already tested (LT-38's conformance suite: `TestConformance_DeleteExpired_*`, `TestConformance_OldestSurvivingAt_*`, `TestConformance_Drained_*`, `TestConformance_DeleteWritesExactlyOneDeletionLogRow`, `TestConformance_DeleteExpired_AlreadyCancelledContextDeletesNothing` — all confirmed present during LT-42's full completeness sweep). This story is the **caller**: a scheduled invocation that loops per `RetentionClass` until drained, plus a subject-deletion request path, plus the health metric that tells 04 whether it's actually running.

**Mechanism (team-lead's recommendation, adopted):** a `CronJob` in `04-infra-devops`'s manifests invoking `cmd/api-service`'s existing image in a new `--sweep` mode (or a distinct small entrypoint, `03`'s call) — not a new binary, not a new image build, reusing what's already deployed.

## The three retention classes and windows this sweep must implement (from `pii-governance.md`, cited so this story doesn't re-derive them)

| `RetentionClass` | Clock | Window | Why this clock specifically |
|---|---|---|---|
| `direct` | `updated_at` | 24 months | Proposed POC default, engineering basis only — explicitly **not** a legal ruling (`pii-governance.md`'s own "unknown, needs product/legal ruling" status). This story implements the number as configured, doesn't treat it as settled policy. |
| `idp_cache` | `updated_at` | 30 days | A cache, not a record — re-hydration costs one `/identity` call, so the window trades staleness against re-fetch cost. |
| `idp_cache_orphan` | `created_at`, **deliberately not `updated_at`** | 7 days | Using `updated_at` would let an orphan's own read/re-hydration path reset its expiry indefinitely — the entire reason this class exists as `created_at`-clocked, not a stylistic choice. |

**These are stated as "Proposed" in `pii-governance.md`, not "Ruled," except `user_credential`'s no-independent-window rule.** This story implements the configured numbers; it is not this story's job to decide whether 24 months/30 days/7 days are the right numbers — that's Priya's/legal's call, already flagged as open in the source document.

## Acceptance criteria (restated from `backlog.md` S11)

- [ ] Implements 05's addendum without re-deriving the transaction-boundary or batching reasoning (each `DeleteExpired` call is already one transaction per batch, per the DAO's own implementation).
- [ ] Loops `DeleteExpired` per `RetentionClass` until `Drained` is true, one class at a time, never a mixed/shared predicate — enforcement site: the sweep invocation loop's own structure.
- [ ] `DeleteExpired` is never called with a request-scoped context — the sweep's own job/scheduler context governs it. Enforcement site: the sweep invocation's context construction (the `CronJob`'s own pod lifecycle, not an inbound HTTP request), plus a test asserting an already-cancelled context returns before deleting anything (the DAO layer already has this test per LT-38; this story's own test confirms the *caller* doesn't accidentally pass a request-scoped one).
- [ ] `SweepResult.OldestSurvivingAt` is published to 04's observability **only from a `Drained == true` result** — a non-drained batch reports progress, not health, per `observability.md`'s explicit warning that getting this wrong "means the alert fires on every sweep and gets muted, which is worse than not having it." Enforcement site: the metrics-emission code path, gated on `Drained`.
- [ ] Metrics emitted per class per run: `rows_examined`, `rows_deleted`, `oldest_surviving_row_age_seconds{class="direct"|"idp_cache"|"idp_cache_orphan"}` — matching `observability.md`'s exact label values (not the earlier-corrected, invented `vendor_token_cache`/`idp_identity_cache` names that document itself flagged and fixed).
- [ ] `DeleteProfile` is the only path used for a subject-deletion request; ordinary application deletes still go through `Profiles().Delete` (no log row) — this distinction is preserved, not collapsed for convenience.
- [ ] The `Drained`/`OldestSurvivingAt` coupling gets a one-line doc comment at the field declaration (Oren's note) — already present in the DAO's own code per LT-42's completeness sweep; this story doesn't need to add it again, just not remove or contradict it.
- [ ] **The `CronJob` runs against `api-service`'s existing image** (a `--sweep` mode or distinct entrypoint), not a new image build — matching team-lead's stated "half-day story" framing; a new image/Dockerfile would be disproportionate scope for what this needs.
- [ ] **Bounded by the existing `maxRows` per call** — the sweep doesn't invent a new batching parameter; it uses the DAO's own already-validated `1..10_000` bound.
- [ ] **Audited** — every deletion this sweep performs writes exactly one `deletion_log` row via the DAO's own transaction (already guaranteed by the DAO layer per LT-38's test); this story's job is only to confirm it doesn't bypass that path.
- [ ] **Added per Tobias's objection:** the sweep `CronJob` sets `concurrencyPolicy: Forbid` — Kubernetes' default (`Allow`) would let a slow-running sweep (plausible on the *first* real run, with no prior sweep history and a possible real backlog across all three classes) overlap with its own next scheduled invocation, matching the exact "two schedulers hit the same tables concurrently" risk this project already solved once for the migration `Job` in LT-45 ("only one migration run can reach the migrate stage at a time... enforced by the pipeline's own concurrency group/mutex"), but never carried forward to this `CronJob`. Beyond wasted DB load, two overlapping sweeps for the same class could each independently reach `Drained == true` and each emit `oldest_surviving_row_age_seconds` for that class in the same window — a confusing, duplicate signal undermining the one metric criterion 5's alert rule depends on. `Forbid` silently skips an overlapping run rather than overlapping it — a skipped run must itself be visible in observability (a metric or log line noting the previous run was still active), so a sweep that's perpetually behind schedule doesn't fail silently either.

## Non-goals

- No new DAO methods, no schema changes — `DeleteExpired`/`DeleteProfile` and `deletion_log` already exist and are tested.
- No change to the retention windows themselves (24 months/30 days/7 days) — those are Priya's/legal's numbers, implemented as configured, not re-litigated here.
- No new container image — reuses `api-service`'s existing image in a new invocation mode.
- No subject-deletion-request *API endpoint* — `backlog.md`'s S11 wires the DAO-level `DeleteProfile` path; whether/how an external caller triggers a subject-deletion request (a support-tool button, an API route) is a separate, unscoped question not raised by this story's own criteria.

## Update — implementation (Renata Cole, 03), entrypoint/args agreed with Theo (04) first

**Entrypoint, agreed with Theo before opening the PR:** `APP_MODE=sweep`, a third value alongside `verifier`/`issuer` on the SAME `api-service` binary/image — not a `--sweep` CLI flag, and not a distinct `cmd/sweep-worker` binary. ## PO acceptance review — live pass against build f6f05ac (real bug found, FAIL)

**Reviewer:** Naomi Voss (PO), via direct `kubectl` access, 2026-09-13. Ran the review script's off-schedule trigger (`kubectl -n loginid-takehome create job --from=cronjob/retention-sweep lt44-review-1`) exactly as written.

**Real finding: the retention-sweep Job cannot reach Postgres at all — silently, indefinitely, and undetected by any mechanism this story or LT-49 has built so far.** The triggered Job's pod sat `1/1 Running` for over two minutes with **zero log output** (not even a startup line) and **~1m CPU** (essentially idle, not busy). `pg_stat_activity` on `postgres-0` showed no incoming connection from the sweep pod at all. A `kubectl debug` ephemeral container attached to the pod's network namespace showed exactly one TCP socket, in **`SYN_SENT`** state, addressed to `postgres-0`'s real IP on port 5432, with a nonzero retransmit count — packets going out, nothing coming back. Not a connection refusal (which would show a completed handshake followed by a reset, and would appear in Postgres's own connection log) — a **silent drop**, which pointed straight at `NetworkPolicy`.

**Root cause, confirmed by reading the manifest directly:** `postgres-default-deny`'s ingress allow-list is `podSelector.matchLabels` for `app=api-service`, `app=api-service-issuer`, `app=db-migrate` only. The retention-sweep `CronJob`'s pod template labels itself `app: retention-sweep` (confirmed in the CronJob spec) — a fourth, structurally identical consumer of Postgres that was never added to the policy's allow-list. Exactly the same category of gap Tobias already flagged on LT-52 (NetworkPolicy scoping not carried forward to a new, structurally identical component) and the fourth-in-a-row instance of "a pattern already established elsewhere in the project wasn't carried forward to a new component," per my own ruling above on the `concurrencyPolicy: Forbid` finding — this is a fifth.

**Why this is worse than a normal failed sweep, not just another instance of the same bug:** the Job has no `activeDeadlineSeconds` set, so it would run forever, never completing and never failing — meaning under `concurrencyPolicy: Forbid`, every subsequent scheduled run would be silently skipped forever, since the hung Job never releases the "active" slot. `RetentionSweepNotReporting` (LT-49, Priya's rule 1) would eventually catch this (no fresh sample for 2I — up to 48 hours at a daily schedule), but that's a two-day-late detection of a bug that's actually immediate and permanent, not a legitimately slow sweep.

**Disposition: LT-44 stays In Test, this is a FAIL, not a partial pass.** Fix needed: add `podSelector: matchLabels: app: retention-sweep` to `postgres-default-deny`'s ingress `from` list. Test job (`lt44-review-1`) deleted; no lasting change to the cluster. The concurrent-trigger check (confirm `JobAlreadyActive`) is deferred until after this fix, since testing concurrency against a Job that can never complete would prove nothing.

**Metrics, agreed with Theo:** stdout lines in a `metric_name{label="value"} value` shape (`internal/sweep.StdoutMetricEmitter`) are the complete, final answer for this project's scope — not a placeholder. **`internal/sweep.Run`** loops `DeleteExpired` per `RetentionClass` until `Drained`, one class at a time (never a mixed predicate, verified by `TestRun_EveryClassCalledOnceEachWithItsOwnPredicate`), summing `RowsExamined`/`RowsDeleted` across every batch a class takes to drain. ## 05 note — the sweep interval (I), which every alert threshold is derived from

**Ruling: `I` = 24 hours. One `CronJob`, daily, at an off-round time — `17 3 * * *` (03:17 UTC) rather than midnight.** Nothing on the record stated an interval, and every number in the LT-49 alert ruling is expressed in terms of it, so it needs pinning before Theo writes either manifest.

**Why daily.** The binding constraint is the *tightest* window, not the longest: `idp_cache_orphan` at 7 days. A daily sweep means a row can legitimately outlive its window by at most one interval — 1 day, 14% overshoot — and puts the `RetentionWindowExceeded` threshold (W + 2I) at 9 days against a 7-day window, roughly 29% slack. Both are proportionate. Going sub-daily (6h, say) would buy precision the windows themselves do not justify: they are **proposed POC defaults whose basis column reads *unknown — needs a product/legal ruling*** (`05-data-ops/pii-governance.md`), and tightening the sweep to hours against a number nobody has ratified is false rigor. Going weekly would be wrong in the other direction — `I` = 7d on a 7d window puts the alert threshold at 21 days, three times the window it is supposed to protect. Dead-sweep detection also falls out acceptably: `RetentionSweepNotReporting` fires above 2I, so a stopped sweep surfaces in about two days, leaving five days of margin before orphan rows are meaningfully overdue.

**One schedule for all three classes, not three.** The `CronJob` makes three sequential `DeleteExpired` calls — `idp_cache_orphan`, `idp_cache`, `direct` — in one invocation. Each class is independently batched and transactional, so a run interrupted between classes leaves a consistent database and simply resumes next cycle. The reason to keep it single is the alert config: three schedules would mean three values of `I`, and every threshold in the LT-49 ruling would triple. **Keep `sweep_interval_seconds` a single constant** and derive the thresholds from it rather than writing the arithmetic out.

**03:17 rather than 00:00** because midnight is where every other scheduled job in the world already is, and because an off-round time makes a date-boundary bug distinguishable from a scheduling bug when one eventually appears.

**Three triggers to revisit, each with what it means:**

- **The `idp_cache_orphan` window drops below ~3 days.** `I` must shrink with it — at W = 2d and I = 24h the alert threshold would be 4 days, double the window.
- **`RetentionSweepSkipRate` fires.** That means run duration D is approaching I. Either shrink I or raise per-batch throughput; the skip-rate alert exists to surface this *before* the other two trip.
- **The `direct` class starts dominating run time.** Three sequential calls in one Job means a slow 24-month sweep delays the 7-day one. At take-home data volumes this is irrelevant; if it stops being irrelevant, split the schedules and accept a per-class `I` in the alert config.

## Update — fail-loud on unreachable database (Renata Cole, 03)

**Naomi's live run of the sweep CronJob found the pod sitting `Running` for minutes with one socket in `SYN_SENT` to Postgres (a NetworkPolicy omission, Theo's own fix) and never logging anything at all** — two minutes of silence cost real diagnosis time. Root cause on 03's side: `dao.New`/`sql.Open` never dial (they only validate the driver/DSN), so nothing bounded the first *actual* connection attempt, which happened inside `sweep.Run`'s own first `DeleteExpired` call, using a context derived only from `signal.NotifyContext` (SIGTERM/SIGINT, no deadline of its own) — a genuinely unreachable database meant an unbounded hang, not a fast failure.

**Fixed in `cmd/api-service/main.go`'s `runSweepMode`:**
- A startup log line (`"api-service: sweep starting, classes=..., interval_seconds=..."`) now fires before anything touches the database at all — an operator watching pod logs sees the process reached the DB step immediately, not two minutes of silence.
- A bounded connectivity check (`sweepDBConnectTimeout = 20s`, the middle of the requested 10–30s range) runs via a dedicated `*sql.DB.PingContext`, before `sweep.Run` is ever called — a separate handle from `repo` since `dao.Repository` exposes no `Ping` (05's contract doesn't have one), mirroring the same pattern the verifier's `/healthz` probe already uses.
- On failure, `classifySweepDBConnectError` names the failure class (`connect_timeout`/`connection_refused`/`dns_error`/`unknown`) in one structured log line, and the process exits non-zero immediately — the Job fails fast and frees the `concurrencyPolicy: Forbid` slot for the next scheduled run, instead of occupying it for the CronJob's full `activeDeadlineSeconds`.
- New `SWEEP_INTERVAL_SECONDS` env var (purely descriptive, classified in `config.OptionalEnvVars`) — echoes the CronJob's own schedule in the startup log line so an operator doesn't have to cross-reference the manifest separately; never read by `internal/sweep`'s own logic.

**Coordination with Theo (04) — resolved.** At the time I wrote this, `deploy/manifests.yaml`'s CronJob had `startingDeadlineSeconds: 900` but no `activeDeadlineSeconds` at all, leaving my 20s inner connect-timeout with no stated outer bound (and matching the exact "runs forever, never completing, never failing" gap Naomi's own live-run finding above independently identified as the reason the hung Job never released its `concurrencyPolicy: Forbid` slot). Theo landed `activeDeadlineSeconds: 3600` and `backoffLimit: 1` in the same PR (#63) that fixes the NetworkPolicy gap — comfortably larger than my 20s inner bound plus the sweep's own expected run time. He also set `SWEEP_INTERVAL_SECONDS: "86400"` on the CronJob, matching its real `17 3 * * *` schedule, so the startup log line's `interval_seconds` value is accurate rather than "unset."

**Live-verified, not just unit-tested:** ran the real binary against a genuinely unreachable database (a non-routable IP) — confirmed the startup line appears immediately, the process fails loud at exactly 20s with `class=connect_timeout`, and exits non-zero. Re-ran against a real reachable Postgres to confirm no regression to the happy path. `TestClassifySweepDBConnectError` covers the classifier directly; `TestLoad_SweepIntervalSeconds` covers the new config field. Full `go build`/`go vet`/`go test`/`staticcheck`/`gofmt`/`gitleaks` clean.
