# LT-33 refinement — wire `api-service`'s client credential to call the connector, and the vendor-token pass-through

**Product Owner:** Naomi Voss (01). **Research team:** Imogen Hale, Desmond Okafor, Tobias Lindqvist. **Engineering:** Renata Cole (03). **Source:** `02-ai-security-architecture/backlog.md` S13 (LT-33) — a 02-authored story whose implementation is 03's code, refined here since it's engineering work, same pattern as LT-51.

**Who did the work:** Refined by Naomi Voss (PO); claims check Desmond Okafor; objection Tobias Lindqvist; engineering counterpart Renata Cole.

## Why this one, now

Per team-lead: this is the only story that makes Q2 and Q3 one system — everything up to now proves `api-service`'s own REST surface (Q2) and `idp-connector`'s own inbound contract (Q3) work in isolation, but nothing yet has `api-service` actually call the connector as part of a real flow. It has a real security surface (a client credential `api-service` itself must hold and use correctly), which is why 02 authored the story even though 03 writes the code.

**Checked before drafting: this is genuinely greenfield.** `grep`'d `internal/api` and `cmd/api-service` for any existing connector-calling code — only the `ScopeConnectorIdentityLookup` constant exists (used by the connector's own inbound-audience check, already built and tested in LT-41). No outbound client, no onboarding-flow handler, nothing in `api-service` mints or uses a `connector:identity-lookup` token today.

## What this story actually is

Two related gaps `connector-security.md` and `handoff-04-secrets.md` already resolved at the design level; this story is the implementation:

1. **`api-service` needs its own client credential** (row 10 of `handoff-04-secrets.md`) to authenticate to the connector's inbound auth in the first place — the same `POST /auth/token` mechanism LT-51 built, but `api-service` is itself a *client* of that endpoint here, not the resource server.
2. **The vendor-token pass-through** (`connector-security.md` F3): our own `/auth` returns the vendor's `access_token` to the authenticated internal caller (`api-service`, on the onboarding flow's behalf); `api-service` holds it only for the span between that call and the following `/identity` call, then presents it as a request header (`X-Vendor-Access-Token`, confirmed by name in LT-41's implementation) — never in the body, never persisted, never logged.

## Acceptance criteria (from `handoff-04-secrets.md`/`connector-security.md`, restated for implementation)

- [ ] `api-service` obtains a `connector:identity-lookup`-scoped token from `/auth/token` using its own client credential (`CONNECTOR_CLIENT_ID`/`CONNECTOR_CLIENT_SECRET`, per `PLANNING.md`'s config surface — already named there, never implemented) before calling `idp-connector`'s `/auth` or `/identity`.
- [ ] **Credential holding/rotation (Marcus's ruling — nothing new, points to an existing row rather than re-specifying it):** `CONNECTOR_CLIENT_ID`/`CONNECTOR_CLIENT_SECRET` follow `handoff-04-secrets.md` row 10 exactly — file-mounted secret, `api-service`'s own ServiceAccount, single active secret per client (reissue generates a new one and immediately invalidates the old, no dual-secret overlap window at this scale). No new design here.
- [ ] **Failure mode when the connector is unreachable (Marcus's ruling):** bounded `context.WithTimeout` on the call, a small number of retries with backoff (itself rate-limited independent of any user-triggered retry, so a caller can't abuse it to hammer the connector), then a generic failure surfaced upward ("identity verification temporarily unavailable") — never internal error detail, never a hint at whether the failure is auth/network/vendor-side. **Never falls back to cached or stale identity data** — the same circuit-breaking discipline `connector-security.md` §4 already requires on the connector's own side, applied with equal force here. `api-service` failing to obtain its *own* connector token in the first place (a credential/config problem) is logged/alerted as a distinct failure class from "got a token fine, connector unreachable" (an availability problem) — the former is a config/secret issue, not ordinary downtime.
- [ ] The onboarding flow's vendor-auth step (whatever handler mediates the two-screen flow `ux-notes.md` describes) receives the vendor `access_token` from our `/auth` response and holds it **only** for the span between that call and the following `/identity` call — enforcement site: the handler/service layer that mediates this, not the connector (which stays stateless, per LT-41). No storage, no cache, scoped to the narrowest function possible — same discipline `connector-security.md`'s attack-tree leaf 4 already requires on the connector's own side, applied symmetrically here since `api-service` now holds the same class of secret for the same short window.
- [ ] `/identity` is called with the vendor token as a request header (`X-Vendor-Access-Token`, matching LT-41's already-built expectation), never a body field.
- [ ] **Corrected per Marcus's (02) ruling — the opposite of this criterion's original draft.** `api-service`'s own `connector:identity-lookup` token is a client's own OAuth2 client-credentials access token, not a per-end-user session token — a genuinely different case from the vendor token (which belongs to a specific end-user's onboarding flow and is correctly never cached per `connector-security.md`'s S3 ruling). Standard client-credentials practice, and the correct one here: `api-service` **caches its own connector-scoped token in-memory and reuses it across calls until near expiry**, refreshing shortly before TTL or on a 401 indicating early expiry — not re-minting fresh before every single call. Per-replica in-memory caching only, no shared store needed (multiple valid tokens for the same `client_id` can coexist; independent per-replica authentication is normal for this grant type). Never logged, never persisted to disk — same discipline as every other JWT in this project.
- [ ] Never logs, in any environment or error path: the vendor password, the vendor `access_token`, `api-service`'s own `CONNECTOR_CLIENT_SECRET`, or any full `Authorization`/`X-Vendor-Access-Token` header value — per `handoff-04-secrets.md`'s never-log list, same standard already enforced on the connector's own side (LT-41).
- [ ] `01-product-industry-research-design/ux-notes.md`'s two-screen flow description and this mechanism agree on what the frontend/onboarding-mediating layer actually holds between screens — checked directly: `ux-notes.md:27` already states the token is "held only by this onboarding flow, only for the span between the two calls, and is never persisted past this signup step" (added per Marcus's exact sentence during the earlier consistency-pass fix) — this criterion is **already satisfied by the existing doc**, no coordination needed unless the actual implementation ends up diverging from that description.
- [ ] **Resolved by inspection, per Tobias's objection — a one-line confirmation, not new work.** LT-33 is the first story that gives LT-41's connector rate-limiting a real caller — once wired, every onboarding attempt shares the same `api-service` client identity and (in-cluster) a small, stable set of source IPs, so if the connector's rate-limiting were keyed only on caller-identity+IP (as `backlog.md`'s S8 text reads in isolation), it couldn't distinguish one legitimate user's retry from an attacker enumerating many different people's `name`/`phone` pairs through the same caller. **Checked directly against the actual implementation, not assumed:** `internal/connector/identitylimiter.go`'s `identityRateLimiter` (a distinct component from the caller/IP-keyed `vendorLimiter`, both already built in LT-41) keys on `hashIdentity(callerSub, phone, name)` — the vendor-identity being looked up is already part of the rate-limit key, not just the caller. This means the concern Tobias raised is already correctly resolved by existing code: distinct onboarding attempts (different `name`/`phone` pairs) from the same `api-service` caller get separate buckets, bounded by a capped tracked-identity table (`maxTrackedIdentities`) with a shared, deliberately-stricter overflow bucket once that cap is hit (Marcus's ruling, PR #40 — "fail-toward-stricter under pressure, not fail-open"). **This story's only obligation here is to confirm `api-service` actually passes real, distinct `name`/`phone` values through per onboarding attempt** (trivially true — that's the whole point of the call) — no new correlation-ID mechanism is needed, since the connector's own identity-keyed limiter already does this job.

## Non-goals

- No change to `idp-connector`'s own inbound handlers — already built and tested (LT-41); this story only calls them correctly from the other side.
- No change to the token-issuance mechanism itself — `/auth/token` already exists (LT-51); `api-service` is a new *caller* of it, not a change to how it works.
- No real vendor UI/frontend — the "onboarding flow" here is `api-service`'s own handler/service-layer mediation, not a client-facing UI (out of scope for this backend-focused assignment, per `01-product-industry-research-design`'s track boundary).
- No new client-provisioning UI — `api-service`'s own connector-calling credential is provisioned the same out-of-band way as every other credential in this project (QA clients, signing key, DB credentials).

## Update — implementation (Renata Cole, 03)

New `internal/onboarding` package: `TokenSource` caches api-service's own connector-scoped client-credentials token per-replica, refreshing before TTL (a `refreshMargin` before stated expiry) or on an explicit `Invalidate` — called automatically by `Service.VerifyIdentity` whenever the connector returns an ambiguous 401 (idp-connector's own uniform-response design gives no way to tell whether it rejected our token or the vendor's; `VerifyIdentity` invalidates and retries the whole flow exactly once with a fresh own-token before concluding the vendor credential itself was rejected — a genuinely-bad vendor credential costs exactly 2 connector calls, never more). `HTTPConnectorClient`/`HTTPTokenClient` implement the real outbound HTTP calls (idp-connector's `/auth`+`/identity`, and the issuer's `/auth/token`), mirroring `internal/connector.HTTPVendorClient`'s own discipline: bounded connection pool, fresh headers built per call, no client-level token state. `Service.VerifyIdentity` bounds each connector call with its own `context.WithTimeout` plus a small fixed retry-with-backoff (`connectorMaxRetries`/`connectorRetryBackoff`) on genuine unreachability, collapsing to `ErrIdentityVerificationUnavailable` — never internal detail — while a genuine vendor-credential rejection surfaces as the distinguishable `ErrVendorCredentialRejected`. Own-token-acquisition failure is logged as its own class (`TokenSource.Token`'s own log line), separate from connector-unreachable (`Service.callAuth`/`callIdentity`'s own log lines).

No new public HTTP endpoint: per this story's own non-goals and PO review script item 7, `internal/onboarding.Service` is wired into `cmd/api-service/main.go`'s verifier-mode branch (`newOnboardingService`) for startup-time visibility, best-effort like the existing DAO-repository/pingDB pattern — missing config logs a warning and the binary still starts, rather than crash-looping over a capability nothing yet depends on.

**Vault-delivery indifference (PM relay, Theo's LT-46 in progress):** `CONNECTOR_CLIENT_ID`/`CONNECTOR_CLIENT_SECRET` are now resolved via `CONNECTOR_CLIENT_ID_FILE`/`CONNECTOR_CLIENT_SECRET_FILE` taking precedence over the plain env vars — the same `resolveDSNFrom` pattern `DB_DSN_FILE` already uses — so this code is indifferent to Kubernetes Secret vs. Vault Agent Injector delivery, per Warren's approval. Two new env vars this story adds: `ISSUER_TOKEN_URL`, `IDP_CONNECTOR_BASE_URL` (documented in root `PLANNING.md`'s Service boundaries section). **Flag to Theo:** api-service's verifier Deployment manifest needs these two new vars plus the connector client credential wired in (`deploy/api-service.yaml`) before this capability is actually reachable in-cluster — `newOnboardingService`'s own startup log will say "not available" until then, by design, not silently.

Test coverage: `internal/onboarding/onboarding_test.go` — token caching/refresh/invalidation, the happy path (token flows correctly from `Auth` into `Identity` and nowhere else), own-token-acquisition failure (never calls the connector at all), connector-unreachable (bounded retry count, generic error), vendor-credential-rejected (no wasted retry against a doomed credential), and the ambiguous-401-retries-exactly-once case — against fake `TokenClient`/`ConnectorClient` implementations per `decisions/test-double-strategy.md`. `cmd/api-service/main_test.go` covers `newOnboardingService`'s own fail-open-with-a-log behavior per missing config field. Full `go build`/`go vet`/`go test`/`staticcheck`/`gofmt`/`gitleaks` clean.

## Marcus Ilori's (02) ruling — unenforced connector config is acceptable for now, conditionally

Oren also flagged (and I asked Marcus directly): `CONNECTOR_CLIENT_ID`/`SECRET`, `ISSUER_TOKEN_URL`, `IDP_CONNECTOR_BASE_URL` are validated only at construction time, and nothing calls those constructors from a live request path yet — so misconfiguration today produces a startup log line, never an enforced failure.

**Ruling: acceptable, not a general exception to PR #53's "required config is a control" principle** — that principle exists to stop a control from silently not enforcing while something depends on it working, and nothing depends on this working yet (no live onboarding-flow handler exists). **Hard condition, stated here as a blocking acceptance criterion carried forward to whatever future story wires a live handler to this package: the moment that happens, these four env vars move from "logged, not enforced" to genuinely required** — fail loudly / refuse to start, or fail that request path closed, the same as everything `RequiredAuthEnvVars` already covers. Whoever picks up that story must not rediscover this; it is a Done-blocking requirement of that story, not an implementation detail.

Separately, Marcus noted the underlying gap this surfaced — `RequiredAuthEnvVars`'s "bare non-empty literal" model doesn't understand the `*_FILE`-takes-precedence shape `DB_DSN`/`DB_DSN_FILE` already has, independent of this story — is worth generalizing as its own small follow-up (not blocking this PR): teach `RequiredAuthEnvVars`/its callers "either X or X_FILE must resolve" once, rather than special-casing it per variable as more show up.
