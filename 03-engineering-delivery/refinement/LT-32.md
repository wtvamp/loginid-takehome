# LT-32 refinement — split the token issuer into its own Deployment with isolated signing-key custody

**Product Owner:** Naomi Voss (01). **Research team:** Imogen Hale, Desmond Okafor, Tobias Lindqvist. **Engineering:** Renata Cole (03, `APP_MODE` binary support), Theo Bergman (04, manifest/Deployment split); design owner Marcus Ilori (02, `handoff-04-secrets.md`/F13). **Source:** `02-ai-security-architecture/backlog.md` S12 (LT-32).

**Who did the work:** Refined by Naomi Voss (PO); claims check Desmond Okafor; objection Tobias Lindqvist; engineering counterparts Renata Cole and Theo Bergman.

## Why this one, not LT-39, and why now

Checked the actual dependency chain rather than assuming: `backlog.md` S7 (auth middleware, LT-40) lists "04: `APP_MODE` Deployment split" as a hard dependency — that's this story. S6 (the search/retrieve handlers, LT-39) doesn't list LT-32 or S7 as a formal dependency (it can be built and merged against fakes without either), but a handler that calls `authorize()` on claims nothing has yet populated isn't a **reviewable, working endpoint** — it's code that compiles and can't be correctly exercised end-to-end at the public URL. LT-32 is the actual bottleneck: nothing downstream (S7, and a genuinely working authenticated S6) can be truly deployed and reviewed without it. Confirmed by checking the live manifest directly (`deploy/manifests.yaml` on `main` as of this refinement): no `api-service-issuer` Deployment exists, no JWT signing-key mount — this story hasn't landed in any form yet, it isn't partially done.

Per Jira's own resolved ambiguity (`LOG.md`: "LT-34 blocks LT-32"), LT-32 was gated on LT-34 landing — LT-34 is now implemented and deployed (review pending only on the build-SHA fix, unrelated to this story), so LT-32 is unblocked and ready to pull.

## What this story actually is, restated plainly

Not a new binary, not new business logic — a **Deployment-topology fix** closing a real security gap the consistency pass found (F13): `handoff-04-secrets.md` said the signing key "never touches `api-service`" while the manifest mounted it into every replica of one `api-service` Deployment. RBAC on a `Secret`'s `get` verb does nothing once the volume is already mounted into a running container — so the only real fix is a second Deployment of the same image, selected by `APP_MODE=issuer` vs. the default, with its own ServiceAccount that alone can mount the key.

## Acceptance outcome (no new public-URL behavior yet, but it's the load-bearing gate before any is trustworthy)

This story doesn't add a caller-visible endpoint — `/healthz` still looks the same. "Done" is verified by manifest inspection and a runtime check that the two Deployments' pods genuinely differ in what they can mount, not by curling something new.

## Acceptance criteria (restated from `backlog.md` S12)

- [ ] `api-service` (the Go binary) supports an `APP_MODE` environment variable selecting issuer vs. default (verifying) behavior from one binary/image — no second `cmd/` entrypoint, per `handoff-04-secrets.md`'s explicit "not a third binary" ruling. Enforcement site: `internal/config` reads `APP_MODE`, `internal/app` branches on it at startup.
- [ ] Two Kubernetes Deployments exist in the manifest (`api-service` and `api-service-issuer`), each with its own ServiceAccount. Enforcement site: `deploy/manifests.yaml`, two distinct `Deployment` objects.
- [ ] Only `api-service-issuer`'s pod spec mounts the JWT signing-key `Secret` — **physically absent, not just RBAC-denied, from `api-service`'s pod spec.** Enforcement site: manifest inspection of `api-service`'s volumes/volumeMounts list, which must contain no reference to that `Secret` at all — a reviewer checking RBAC alone would miss a mistakenly-shared mount, per F13's own finding that RBAC doesn't prevent this class of leak.
- [ ] RBAC (`Role`/`RoleBinding`) additionally restricts `get`/`list` on the signing-key `Secret` to `api-service-issuer`'s ServiceAccount specifically — a second, independent layer on top of the physical-absence criterion above, not a substitute for it.
- [ ] The `api-service` (verifying) Deployment holds only the public key material needed to verify, never the private key, regardless of `APP_MODE`'s runtime value — enforcement site: a startup-time check/test asserting the verifying binary's process has no path to the private key even if `APP_MODE` were misconfigured to `issuer` on that Deployment (defense against a manifest typo, not just a design intent).
- [ ] `containerization-design.md`'s single-Deployment mount (the line the consistency pass named) is removed from the design doc and replaced with the two-Deployment description, so a future reader of the design doc sees the corrected shape, not the superseded one.
- [ ] The issuer Deployment's public route (whatever path 02/03 finalize for token issuance — e.g. `/auth/token`) is added to the `Ingress`, routed to `api-service-issuer`, distinct from `api-service`'s existing routes; `idp-connector` remains unrouted, unaffected by this change.
- [ ] **Added per Tobias's objection; confirmed already true by construction, not a new restriction to build.** Theo checked `deploy/rbac.yaml` directly: the CI runner's `Role` grants **nothing** on `secrets` — no `get`/`list`/`create`/anything. If the signing-key `Secret` (or any `Secret`) were added to the CI-applied manifest set, `kubectl apply` would fail loudly with `Forbidden`, the same way it already did for the `Namespace` object earlier in this project — that failure mode is the enforcement mechanism, not a gap. **Decision, now recorded here rather than left to be rediscovered:** the JWT signing-key `Secret` must be provisioned out-of-band (the same pattern already used for `DB_DSN` and the runner's own auth `Secret` — applied by hand alongside `deploy/bootstrap.yaml`, never through the CI-applied manifest set). Whoever implements this story follows that existing pattern; they are not newly restricting anything, the restriction already exists.

## Non-goals

- No change to the JWT scheme itself (claims, TTL, `kid` rotation mechanics) — that's `api-auth-design.md`'s design and S7's (LT-40) implementation, not this story's.
- No auth middleware implementation (JWT verification, rate limiting) — that's S7 (LT-40), which depends on this story but is a separate pull.
- No handler-layer `authorize()` logic — that's S6 (LT-39), also downstream of this and S7.
- No change to `idp-connector` — it has no issuer/verifier split; this story only touches `api-service`.

## PO review script

1. Confirm `deploy/manifests.yaml` (or wherever the PR puts it) has two distinct `Deployment` objects for the `api-service` image, each with its own `ServiceAccount`.
2. Read `api-service-issuer`'s pod spec: confirm the signing-key `Secret` volume mount is present.
3. Read `api-service`'s (verifying) pod spec: confirm **no** reference to that `Secret` anywhere — no volume, no volumeMount, not even an unused one.
4. Read the `Role`/`RoleBinding` scoping `get`/`list` on the `Secret` to the issuer's ServiceAccount specifically, not both.
5. Confirm `containerization-design.md` no longer describes the single-Deployment mount the consistency pass flagged.
6. Once deployed: hit the issuer's route (once 02/03 finalize its path) and confirm it's reachable and distinct from `api-service`'s existing routes; confirm `idp-connector` is unaffected (still unrouted).
7. If feasible, a deliberate negative check: attempt (from outside, with no special access) to read the signing-key `Secret` via the verifying Deployment's own ServiceAccount token — should fail, confirming criteria 3+4 together, not just one or the other.
8. **Added per Tobias's objection, confirmed already satisfied:** read `deploy/rbac.yaml` and confirm the CI runner's `Role` grants nothing on `secrets` at all (verified true as of this refinement — no `get`/`list`/anything); confirm the signing-key `Secret` is applied out-of-band (alongside `deploy/bootstrap.yaml`), never through the CI-applied manifest set, matching the existing pattern for `DB_DSN` and the runner's own auth `Secret`.

## Research team review

**Desmond Okafor — claims check:** Independently verified the dependency-chain reasoning (S7's "Depends on" line names LT-32 by F13 tag), the "LT-34 blocks LT-32" citation (verbatim in `LOG.md`), the F13 quote/mechanism, and the "physically absent, not just RBAC-denied" framing — all confirmed accurate against the source documents, no invented detail, no overreach. No corrections needed.

**Tobias Lindqvist — objection:** This story locks down the issuer Deployment's own boundary (physical mount absence + scoped RBAC) but never checks the *other* ServiceAccount with broad `Secret` access in the namespace — the scoped CI deploy runner from his own earlier LT-45/LT-47 review, which needs `get`/`list` on `Secrets`-by-name to `kubectl apply` and diff against live state. If the signing-key `Secret` is part of what the runner applies, its ServiceAccount can already read the private key regardless of how tightly this story scopes the issuer's own RBAC — a second, unexamined path to the same secret, found by cross-referencing two separately-reviewed documents rather than either one in isolation. Counter-proposal accepted: added a criterion requiring the signing-key `Secret` be provisioned out-of-band from the CI-applied manifest set, or explicitly excluded from the runner's RBAC `resourceNames`, plus a matching PO-script step.
