## Acceptance criteria (restated from `backlog.md` S6, cross-checked against `handoff-03-auth.md` v3)

- [ ] Implements `handoff-03-auth.md` v3's scope vocabulary (`profile:read:own`, `profile:read:any`, `profile:search`) and pagination/rate-limit numbers without re-deriving 02's authz-scoping reasoning.
- [ ] `authorize(sub, scope, target)` runs as an explicit call inside each handler after request parsing, before the DAO call — not a second middleware, per v3's confirmed placement (it needs the parsed target id, which pre-routing middleware doesn't have). `authorize()` checks `caller_referral`/caller-role data against the token-issuer's own datastore, **not against 05's schema** — 05 was never assigned that table.
- [ ] `profile:search` responses carry masked PII fields by default (phone as `***-***-1234`, address reduced to `locality`/`region` only). Unmasked detail requires a separate, separately-audited follow-up call under `profile:read:own` or `profile:read:any` against the specific record id — **this reuses the existing scopes, it does not invent a fourth "expand" flag**; masking is a `profile:search`-response property, not a per-call parameter. Enforcement site: the search-response serialization path is a distinct code path from the read-response one, not the same serializer with a masking flag.
- [ ] **Pagination — clarified per v3's F-pag correction, since `backlog.md`'s original wording could be misread by an implementer:** the API-facing cursor is opaque to the caller — callers cannot construct or walk one by hand — but it may (and in the simplest correct implementation, does) encode the DAO's own `Offset` directly underneath. "Cursor-based pagination only" means **the caller-facing contract is opaque-cursor-only, not that the handler is forbidden from using the DAO's `Offset` field internally.** The actual anti-enumeration control is the cumulative distinct-record-touch counter (next bullet), not the cursor mechanism itself. Default page size 20, hard ceiling 50, enforced in the handler before the DAO is ever called — the DAO's own `Limit` bound (1..100, default 50) is a second, independent backstop only reachable if the handler clamp is bypassed, not a second policy a caller can rely on.
- [ ] A cumulative distinct-record-touch counter per caller per rolling 24h window is enforced, independent of per-minute rate limits, applying to **both** `profile:search` and `profile:read:any` unconditionally — a valid `reason_code` on `read:any` satisfies the per-call `authorize()` check but does **not** exempt the caller from this cumulative cap (v3's explicit fix to an earlier wording that made the counter a no-op for `read:any`). Enforcement site: a counting store incremented once per distinct record id returned, checked before the response is sent.
- [ ] **Resolved by 02's ruling (raised by Tobias's objection, routed to Marcus):** crossing the cumulative counter's threshold **hard-denies** (429) every subsequent `profile:search`/`profile:read:any` call from that caller for the remainder of the rolling 24h window — distinct from the 401/403 pair — **in addition to** alerting, not instead of it. An alert-only reading would make the counter detection rather than a control, recreating the "attribution stands in for volume control" gap 01's S4 objection closed at the product-requirements level. `handoff-03-auth.md` and `api-auth-design.md` updated with this explicit ruling. Enforcement site: the counting store's threshold check gates the request before it's served, returning 429; a separate alert fires regardless of whether the request was already being denied.
- [ ] A search request with no filter field at all is rejected by this handler with a 400 before it reaches the DAO — the DAO itself treats an all-nil `ProfileQuery` as legal, so this handler-layer rejection is the only enforcement site for "no bare unconstrained search."
- [ ] A `profile:search` query rejected for exceeding the result cap unconstrained (e.g. a bare wildcard) is rejected outright, not truncated — enforcement site: the same in-handler call site, checked before the query is built.
- [ ] Unmapped DAO errors never surface `err.Error()` to the client; only the mapped sentinels' safe messages do — per `decisions/error-semantics.md`'s boundary translation function. Authn failures (missing/invalid token) return 401; scope failures and `authorize()` policy denials both return 403 with an identical client-visible body, distinguished only in the audit log.
- [ ] `profile:read:any` requests carry a `reason_code` from the closed enum (`support_ticket`, `fraud_review`, `kyc_reverification`, `legal_hold`) on every call, logged with the audit record — adding a fifth value is a documented change to this enum, not a runtime config toggle.
- [ ] When `api-service` calls `idp-connector` on a caller's behalf, it obtains a `connector:identity-lookup`-scoped token first, using its own `CONNECTOR_CLIENT_ID`/`CONNECTOR_CLIENT_SECRET` credential — distinct from S8's idp-connector-side handlers, which only validate that token, not issue or hold this credential.

## PO acceptance review — joint live-URL pass, 2026-09-13

**Reviewer:** Naomi Voss (PO). Minted real tokens for all three scopes (search, read:own, read:any) using the seeded QA client credentials, fetched directly via `kubectl -n loginid-takehome get secret qa-client-credential` and never pasted anywhere. Against the live URL with the seeded demo profiles:

- `POST /profiles/search` with the search token — 200, masked results (`***-***-####`, region-only), all three seeded profiles returned. **Confirmed.**
- `GET /profiles/{id}` with the read:own token on its allowed profile — 200, full record. On a different profile — **403**. **Confirmed.**
- `GET /profiles/{id}` with the search token (wrong scope) — **403, byte-identical body to the read:own-on-wrong-profile 403 above** — F7's identical-body requirement confirmed live, not just by unit test. **Confirmed.**
- `GET /profiles/{id}` with the read:any token, no `reason_code` — 400. With an invalid `reason_code` — 400, same message. With a valid one (`support_ticket`) — 200, full record. **Confirmed.**
- No token — 401. **Confirmed.**

**Real defect found and reproduced live, not from code alone: the per-minute `RateLimiter` (10 req/min search) does not reliably enforce its stated limit.** `api-service` runs 2 replicas; `RateLimiter` is in-process (per-pod memory) — its own code comment states this is "a deliberate simplification, not hidden — a production multi-instance deployment would need a shared store (Redis) instead," but the deployed manifest runs 2 replicas anyway. Reproduced: a 12-call rapid burst produced zero 429s (load-balanced roughly evenly across both pods, each staying under its own independent count of 10); a subsequent 30-call burst started producing 429s at call 9, at a point with no fixed relationship to the stated "10 req/min." The effective limit is somewhere between 10–20 depending on load-balancer distribution, not a real per-client cap. `TouchCounter` and `GrantLimiter` share the identical in-process, per-pod design (confirmed by reading their source) and almost certainly have the same gap, though I could not exercise `TouchCounter`'s cap live — see below.

**`TouchCounter`'s 2000-distinct-record cap is not exercisable at all with the current demo dataset** — only 3 profiles are seeded (`deploy/demo-data/001-review-profiles.sql`), nowhere near the threshold. This is a limitation of the review environment, not a defect, but it means this specific criterion is unverified live either way.

**Ruling (team-lead):** `api-service` moves from 2 replicas to 1 (matching the issuer Deployment's own replica count) — a security control beats nominal HA for a POC at this scale; Redis remains the documented production-scale path (already stated in the code's own comments), not something to build now. Re-run the rate-limit burst test after Theo's manifest PR redeploys.

**Correction (Tobias's objection, verified before applying) — 1 replica alone does not close this, it only narrows it, and the doc must say so plainly.** Confirmed directly: neither `deploy/manifests.yaml` nor `deploy/api-service.yaml` sets a `Deployment.spec.strategy` field, so Kubernetes' default applies — `RollingUpdate` with `maxSurge: 25%`, which rounds up to 1 additional pod even at `replicas: 1`. Every future merge-to-main deploy (LT-47's auto-deploy-on-merge design) briefly runs **two** `api-service` pods simultaneously while the new one's readiness probe is pending — the exact condition that broke the limiter in this review's live test, recurring on a predictable schedule during every deploy, not eliminated by the replica-count change. **This is a partial mitigation, not a fix.** The only complete closure is the shared store (Redis) the code's own comment already names as the multi-instance answer. Counter-proposal accepted: flagging to Theo that `api-service`'s `Deployment.spec.strategy.type` should be set to `Recreate` (guaranteeing exactly one pod at any time, at the cost of a brief availability gap during deploy — the same trade this ruling already accepted the spirit of, now actually holding through a rollout too), as a cheap second step beyond the replica-count change alone.
