## Why this one, now, and at priority

This is the critical path per team-lead's direction: LT-39's handlers are code-review-passed but deliberately unwired (exposing them before real auth exists would serve unauthenticated PII), LT-32's issuer split is deployed and live at `/auth/token` (currently a 501 placeholder), and LT-34's live-URL story stays open until something real is reachable through auth. This story is what turns all of that into an actual, reviewable, authenticated public endpoint.

## Correction to `backlog.md`'s own story text, found before drafting

**S7's acceptance criterion 6 ("per-client-credential rate limits and the cumulative distinct-record-touch counter ... enforcement site: the rate-limit middleware plus its own test") is stale relative to work already merged.** `backlog.md` was written before LT-39 (PR #26) implemented `RateLimiter` and `TouchCounter` as explicit, tested checks called *inside* each handler (via a `Deps` struct), not as separate HTTP middleware — confirmed by reading `internal/api/auth.go`, `handlers.go`, `ratelimit.go`, `touchcounter.go` directly. Both are already built, both are already tested (including the two hard-deny regression tests from LT-39's own refinement), and both are already wired to whatever `AuthContext` the request context carries.

**What this means for LT-40's actual scope:** this story does **not** rebuild rate limiting or the touch counter. Its job is narrower and already well-seamed: verify the JWT, populate `AuthContext` (via `WithAuthContext`, already exported by `internal/api`) with the token's `sub` and `scope` claims, and wire the resulting middleware into `cmd/api-service`'s router ahead of the already-built handlers. The 90-day-re-approval/lifecycle-revocation machinery (`api-auth-design.md`) and the issuer-side rate limiting (criterion 5, below) are the only genuinely new rate-limit-shaped work this story adds — the resource-API limits are already done.

## Acceptance outcome

"Done" for this story is a working, tested JWT-verification middleware wired into `cmd/api-service`'s router, with LT-39's handlers reachable through it at the live URL. **Corrected per team-lead, per Marcus's actual design:** nothing ever signs with the deployed private key outside the issuer process — there is no "out-of-band token minted directly against the signing key" path, review or otherwise; the private key's only caller is `/auth/token`'s own real grant logic (LT-51). **LT-40 merges and deploys to In Test on its own** (middleware + wiring, verified by unit tests here), **but its live-URL review happens together with LT-51's**, using a real token obtained from `/auth/token` via a dedicated, narrowly-scoped QA client credential seeded in the client store (LT-51's own criteria). LT-40 and LT-51 go Done together, in one PO pass, with a genuinely issued token — not LT-40 alone on a workaround token.

## Acceptance criteria (restated from `backlog.md` S7, corrected per the finding above)

- [ ] Implements 02's token scheme without re-deriving the no-refresh/no-denylist reasoning in `api-auth-design.md` — no refresh tokens (client re-authenticates on expiry); TTL-only revocation (5–15 min), no denylist, an explicitly accepted trade-off, not to be re-litigated.
- [ ] Rejects any token whose `aud` doesn't match this service's audience — enforcement site: the claim-validation step, unit test with a mismatched-audience token.
- [ ] Verifies with the public key only; the private signing key never touches this binary's code path — enforcement site: dependency/import check, no signing-key material referenced anywhere in `internal/api` or the verifier's own binary path (this is already structurally true per LT-32's Deployment split; this criterion confirms the *code*, not just the *Deployment*, never imports signing-key material).
- [ ] **Pins the expected signing algorithm and rejects any token whose header claims a different one**, including `alg: none` and a symmetric-algorithm downgrade using the public key as an HMAC secret (RFC 8725 §3.1) — enforcement site: an explicit algorithm allowlist check in the JWT verification call, never left to the library's default. Unit tests: a token with `alg: none`, a token HMAC-signed using the public key bytes as the secret, both rejected.
- [ ] `kid`-based key rotation: the middleware selects the verification key by the token's `kid` header claim, supporting at least two concurrently valid public keys during a rotation overlap window — enforcement site: a unit test presenting tokens signed under two different `kid`s, both verifying successfully when both keys are configured.
- [ ] The middleware populates `internal/api.AuthContext` (via the already-exported `WithAuthContext`) with the token's `sub` and `scope` claims on success, and returns 401 (via LT-39's existing unauthorized-response path, not a new one) on any verification failure — **this is the actual integration seam with S6's work, not new response-shape design.**
- [ ] The token-issuing endpoint (`APP_MODE=issuer`, currently the 501 placeholder from LT-32) gets its own failed-grant rate limiting and progressive backoff per `client_id` and per source IP, separate from the resource-API limits (which are already built in `internal/api`) — with alerting on a sustained run of failed grants against one `client_id`. This is genuinely new work, not already covered by LT-39.
- [ ] The deadline budget for a request (context propagation into the DAO layer) is sized to cover realistic p99 DAO latency per `decisions/context-propagation.md`'s ruling — stated as a concrete number in this story's implementation, not left as "some deadline."
- [ ] The resource-API rate limiter and touch counter already built in LT-39 are wired to real, JWT-derived `AuthContext.Sub` values once this middleware populates them — **no new implementation, an integration check**: a live-URL test with a real token confirms the 60/10 req/min limits and the touch cap actually apply per real client identity, not per a test fake's hardcoded value.

## Non-goals

- **Real token issuance logic** (actually minting a signed JWT from valid client credentials at `/auth/token`) is explicitly out of scope for this story unless `backlog.md`/02 says otherwise — LT-32 only built the placeholder route and the signing-key custody; this story is the *verifier* side. Flagged as an open question below, since without it there's no way to obtain a real token for the live-URL review other than an out-of-band test token minted directly against the deployed key.
- No change to `internal/api`'s handler logic, masking, or error translation — that's LT-39 (PR #26, code-review-passed, not yet merged to main).
- No change to the object-level `authorize()` policy datastore — still a stated seam (`Authorizer` interface), real implementation is a later story per `handoff-03-auth.md` v3's F8 resolution.
- No client-credential provisioning UI/API for new callers — out of scope for this take-home entirely, per `01-product-industry-research-design`'s track boundary.

## Open question — resolved

**Original question:** `backlog.md` had no story for `/auth/token`'s actual grant logic (validate client_id/client_secret, mint a signed JWT) — LT-32 only built the route as a 501 placeholder, and nothing downstream picked up the real logic. Tobias's objection sharpened this from "a gap this refinement can flag and work around" to "a missing story, not a pending one" — unlike LT-36/37's wait on LT-38, or LT-32's wait on LT-34, this had no ticket and no scheduled end, and treating an out-of-band token as this story's own review method risked quietly weakening "done = deployed and reviewable at a public URL" into "done = reviewable by an engineer with cluster access," without anyone deciding that on purpose.

**Resolution (team-lead):** confirmed as a real gap and a new story, not scope creep and not "out of scope forever." **LT-51** (Epic LT-3, security-graded, linked LT-40 → blocks → LT-51) — OAuth2 client-credentials grant at `/auth/token`, per Marcus's `handoff-03-auth.md` v4 addendum (now landed): HTTP Basic client auth, form-encoded `client_credentials` grant per RFC 6749 §4.4, §5.1/§5.2 token/error responses with an identical `invalid_client` for unknown-client vs. wrong-secret (no oracle distinguishing the two), client store in the issuer's own datastore with Argon2id-hashed secrets, a `jti` claim recommended for audit correlation only (not a revocation mechanism — TTL-only revocation stands per `api-auth-design.md`), and the public key distributed via a JWKS endpoint served by the issuer's in-cluster `ClusterIP` `Service` — no public `Ingress` route for it, since only the verifying middleware inside the cluster needs it. 03-owned code, 02-supplied spec. Refined right after this story.

**Corrected ruling on the review token, replacing the earlier "out-of-band" framing:** there is no path where the private key signs anything outside the issuer process, not even for review. LT-40's live-URL review therefore happens *together with* LT-51's, using a real token obtained from a real `/auth/token` call, authenticated with a dedicated, narrowly-scoped QA client credential seeded specifically for this purpose (LT-51's own criteria, below) — not a workaround token and not a separate acceptance event.

## PO review script

1. Confirm the algorithm-allowlist and `kid`-rotation unit tests exist and pass — read the test names and assertions directly, not just "tests pass."
2. Confirm `AuthContext` population uses the already-exported `WithAuthContext`/`AuthContext` types from `internal/api`, not a parallel/duplicate type — grep for a second definition of anything auth-context-shaped.
3. Confirm the issuer-side rate limiting is a distinct code path from the resource-API rate limiter already in `internal/api/ratelimit.go` — this is genuinely new work, shouldn't reuse or be confused with the existing one.
4. Confirm the context-propagation deadline is a concrete, named number in code (e.g. a constant), not an inline magic value scattered across call sites.
5. **Run jointly with LT-51's review, once both are deployed:** obtain a real token from `/auth/token` using the seeded QA client credential (LT-51's criteria), then hit `/profiles/search` and `/profiles/{id}` at the live URL, confirming a masked response, a 401 on a missing/expired/wrong-audience token, a 403 on a wrong-scope token, and — if enough calls are made — an actual 429 once the touch cap is crossed. This is the live-URL review LT-34/LT-39/LT-40 have all been waiting on; LT-40 and LT-51 go Done together in this one pass, not separately.
