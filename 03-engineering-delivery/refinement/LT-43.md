**Deliberately stubbed, and why — this is the section a cold reader needs, stated plainly, not left to infer:**
- **The third-party vendor (ABC/XYZ) is an in-process `StubVendorClient`**, not a real HTTP integration — `idp-connector` falls back to it when `IDP_ABC_BASE_URL` is unset, logs this explicitly on startup, and this is `backlog.md`'s own stated non-goal for LT-41 ("no real vendor integration"). The assignment names the vendor generically; a real integration was never in scope.
- **The `authorize()` object-level policy hook is a `StopgapAuthorizer`**, not the real caller-referral datastore `handoff-03-auth.md`'s F8 resolution describes — a stated seam, not a hidden gap, per LT-39/LT-40's own non-goals.
- **CockroachDB and SQLite are exercised in CI only, never deployed live** — only Postgres runs in the actual cluster (LT-52's explicit scope limit). A reader should not expect to find CockroachDB running anywhere.
- **No `POST /profiles` write endpoint exists or is planned** — Q2 is search/retrieve by the assignment's own text; a write path was ruled out as scope creep (team-lead + Priya's decision, recorded on LT-39). Review/demo data enters via a version-controlled, idempotent SQL file (`deploy/demo-data/001-review-profiles.sql`) applied as a documented runbook step, not through the API.
- **Rate limiting, the touch counter, and the token-issuer's grant limiter are in-process, single-replica-only** — their own code comments state a shared store (Redis) is needed for a genuine multi-instance deployment; this project runs `api-service`/`api-service-issuer` at 1 replica with `Recreate` rollout strategy specifically so this simplification holds correctly, not silently degrading under a rolling update (a real live-tested bug this project found and fixed, not a hypothetical).
- **`api-service` calling the connector (LT-33)** is in progress as of this writing — the piece that makes Q2 and Q3 one system, not yet merged.
- **The retention sweep (LT-44) — designed and enforced at the schema/DAO level, not yet operationally running.** `DeleteExpired`/`DeleteProfile` exist on the DAO composite and are tested there, but nothing schedules or calls them; no cron/job wires the sweep to run against the live database. `pii-governance.md`'s retention policy is a real, tracked, backlogged story (S11/LT-44), not a silently-abandoned requirement — but a cold reader checking whether retention/deletion actually runs in production would otherwise have to discover its absence themselves.
