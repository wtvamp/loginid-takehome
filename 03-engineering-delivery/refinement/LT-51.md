## Why this one, now

PR #30 (LT-40) has already built the verifier side and the `GrantLimiter` component this story wires to — the only thing standing between the current deployment and a genuinely issued, end-to-end token is this story's actual grant logic. Once it lands, LT-34/LT-39/LT-40/LT-51 all get their joint live-URL review with a real token, per team-lead's ruling.

## What's already built, and what this story actually adds

**Do not rebuild these — wire to them:**
- `internal/api.GrantLimiter` (PR #30) — the failed-grant rate-limiting/backoff interface, keyed independently by `client_id` and source IP, with alerting on a sustained run against one `client_id`. This story constructs a real implementation instance (or reuses `InProcessGrantLimiter`) and calls `Allow`/`RecordFailure`/`RecordSuccess` around the actual grant attempt — it does not design a new backoff scheme.
- The JWKS endpoint (`internal/api/jwks.go` serves the client side; the issuer side serving `/.well-known/jwks.json` is this story's job, but the *shape* — RFC 7517, `kid`-keyed — is already established by what the verifier expects).
- `internal/api.AuthContext`/`WithAuthContext` (LT-39) and the JWT verification middleware (LT-40) — this story's only integration point with them is producing tokens whose claims those already-built and already-tested pieces correctly parse; it doesn't touch either.

**What's genuinely new:** the `POST /auth/token` handler itself — client authentication, the client store, JWT minting, and serving JWKS at the now-fixed path.

## Acceptance criteria (from `backlog.md` S7a, current per `handoff-03-auth.md` v6)

- [ ] `POST /auth/token` implements RFC 6749 §4.4: `grant_type=client_credentials`, form-encoded (`application/x-www-form-urlencoded`), **not JSON** — the one endpoint in this API that follows OAuth2's own wire format rather than this project's usual JSON convention, because it's the one endpoint implementing a named OAuth2 grant. An optional `scope` parameter (space-delimited) requests a subset of the client's granted scopes; omitted means issue the full granted set.
- [ ] Client authentication is **HTTP Basic** (`client_id`:`client_secret` in the `Authorization` header), **not** credentials in the body — keeps the secret out of anywhere that logs request bodies more casually than headers, per RFC 6749 §2.3.1's preferred method.
- [ ] Errors follow RFC 6749 §5.2, **never distinguishing why in body or status**: `invalid_client` (401, `WWW-Authenticate: Basic`) for **any** client-authentication failure — an unknown `client_id` and a wrong secret for a known `client_id` return byte-identical responses. `invalid_scope` (400) if the requested scope isn't a subset of the client's granted scopes. `unsupported_grant_type` (400) for anything but `client_credentials`. Enforcement site: a test comparing the unknown-client and wrong-secret response bodies for equality, not just "both 401."
- [ ] **Timing side-channel closed, not just the response body:** when `client_id` doesn't exist in the client store, the handler still performs an Argon2id comparison against a fixed, pre-computed dummy hash (same cost parameters as real client secrets) before returning `invalid_client` — so the unknown-client and wrong-secret code paths take statistically indistinguishable time. Without this, a fast-reject-on-unknown-client-then-slow-Argon2id-on-known-client asymmetry is a textbook timing oracle that lets an attacker enumerate valid `client_id`s by latency alone, even with byte-identical response bodies — exactly the class of issue the identical-body requirement was meant to close, left half-finished. This is the one endpoint in the API that deliberately follows a named external OAuth2 spec rather than this project's JSON convention, making it the endpoint most likely to be pattern-matched against known real-world timing-oracle bugs by an outside reviewer. Enforcement site: read the handler's unknown-`client_id` branch directly and confirm it calls the same hash-comparison function against a dummy value, rather than short-circuiting before it — a code-review check, not a load test.
- [ ] Client store lives in the issuer's own datastore (per F8, not 05's schema): `client_id`, `name` (accountability — no shared credentials across a team), `client_secret_hash` (**Argon2id, same floor as `threat-model.md` Asset 1** — identical hashing discipline to password storage), `granted_scopes` (provisioned subset of `profile:read:own`/`profile:read:any`/`profile:search`/`connector:identity-lookup`), `status` (active/revoked), `created_at`, `revoked_at`. Rotation: single active secret per client (reissue generates a new one and immediately invalidates the old — no dual-secret overlap window, unlike the signing key).
- [ ] The token-endpoint's own brute-force protection wires to the **already-built** `GrantLimiter` (PR #30) — `Allow` checked before attempting client authentication, `RecordFailure`/`RecordSuccess` called after, keyed by both `client_id` and source IP. Enforcement site: an integration test confirming a sustained run of failed grants against one `client_id` eventually blocks further attempts and fires the alert exactly once per threshold-crossing (not once per subsequent failure) — this is `GrantLimiter`'s own tested behavior, so this test only needs to confirm the wiring, not re-test the limiter's internals.
- [ ] Issued JWT claims (`iss`, `aud`, `scope`, `exp`, `sub`) and the algorithm/`kid` header match exactly what LT-40's verifier middleware expects — enforcement site: an integration test that mints a token here and verifies it through the **actual** middleware from PR #30, not two independently-trusted unit tests that never touch each other.
- [ ] **JWKS served at the now-fixed path `/.well-known/jwks.json`** (the OIDC-discovery convention, ruled 2026-09-13 specifically so this story implements to the doc rather than the doc following already-shipped code), issuer-mode only (`APP_MODE=issuer`), reachable only in-cluster via the issuer's own `ClusterIP` `Service` — **no public `Ingress` route**, live at `AUTH_JWKS_URL=http://api-service-issuer.loginid-takehome.svc.cluster.local/.well-known/jwks.json` (already wired by Theo on the client/consuming side). Enforcement site: the route exists at that exact path and is absent from the public `Ingress`'s rules.
- [ ] The JWKS response may set `Cache-Control: public, max-age=<refresh interval>` as good HTTP practice, but this is **advisory only** — the verifier's own staleness policy (already built, PR #30: max staleness = 3× the refresh TTL, fail closed past that bound, per-`kid` rate-limited refetch on an unknown `kid`) is authoritative, not this endpoint's cache headers. This story does not need to coordinate cache-header values with the verifier's staleness logic; they're independent by design.
- [ ] **A dedicated, narrowly-scoped QA client credential is seeded in the client store, out-of-band** (same discipline as LT-32's signing-key `Secret` — never through the CI-applied manifest set), **for the PO's joint live-URL review of LT-34/LT-39/LT-40/LT-51.** Per Warren's explicit ruling (via the PM): review tooling must never mint a token by signing directly with the deployed private key — that would hand review tooling the same access F13's whole Deployment split exists to restrict to the issuer process alone. The correct mechanism is this: a real client credential, provisioned like any other caller, calling the real endpoint. Scoped to the minimum needed for the review — `profile:read:own` by default; add `profile:search` only if the review specifically needs to exercise search, going through that scope's own provisioning bar like any other caller, not a blanket grant. Enforcement site: the credential's row in the client store, its `granted_scopes` listed explicitly in the hand-off to the PO (not "whatever's convenient"), and confirmation it was created out-of-band.

## Non-goals

- No change to `GrantLimiter`, the JWT verification middleware, or `internal/api`'s existing handlers — all already built (PR #30/LT-39/LT-40); this story only calls into them correctly.
- No refresh-token support, no denylist/revocation beyond `status=revoked` at the client-store level — matches `api-auth-design.md`'s standing TTL-only-revocation design, not re-litigated here.
- No UI/API for self-service client provisioning — clients are provisioned directly against the datastore for this take-home's scale.
- No change to the resource-API's own rate limits or touch counter (LT-39) — this story's `GrantLimiter` wiring is a distinct, separate control, per the interface's own doc comment.

## PO review script

1. Confirm `POST /auth/token` accepts form-encoded `grant_type=client_credentials` and rejects JSON bodies (or at minimum, doesn't require JSON) — read the handler's content-type handling directly.
2. Confirm HTTP Basic client auth — a client presenting credentials in the request body alone (no `Authorization` header) is rejected.
3. Confirm the identical-body test for unknown-client vs. wrong-secret exists and passes.
3a. Read the unknown-`client_id` branch directly and confirm it calls the same Argon2id comparison against a fixed dummy hash before returning `invalid_client`, rather than short-circuiting before it — per Tobias's objection, this closes the timing side-channel the identical-body test alone leaves open.
4. Confirm `client_secret_hash` is Argon2id — read the hashing call, don't infer from a comment.
5. Confirm the `GrantLimiter` wiring test exists (sustained failures against one `client_id` eventually block, alert fires once per threshold-crossing).
6. Confirm the mint-then-verify-through-the-real-middleware integration test exists and passes.
7. Confirm `/.well-known/jwks.json` is live in-cluster and absent from the public `Ingress`.
8. Confirm the QA client credential exists, was seeded out-of-band, and its `granted_scopes` are stated explicitly (not assumed).
9. **The joint live-URL review, once this and LT-40 are both deployed:** (a) seed review data via the runbook step — `deploy/demo-data/001-review-profiles.sql` (idempotent, run under the `migrator` role, never under `migrations/`, obviously fictional values in reserved E.164 ranges) applied by Theo; no `POST /profiles` handler exists or is planned — team-lead + Priya ruled a write endpoint out of scope for Q2, so seeding is the only path to reviewable data. (b) obtain a real token via `POST /auth/token` using the seeded QA credential. (c) hit `/profiles/search` and `/profiles/{id}` at the live URL against the seeded rows — confirming a masked response, a full read with a `reason_code`, 401/403 exactly as LT-39's tests predict, and an actual 429 once the touch cap is crossed. This is the review LT-34/LT-39/LT-40/LT-51 have all been building toward; all four are accepted together in this one pass.

Especially relevant here since this is the one endpoint following a named external OAuth2 spec, making it the most likely target for an outside reviewer pattern-matching against known real-world timing-oracle bugs. Counter-proposal accepted: the unknown-`client_id` path must still run Argon2id against a fixed dummy hash before returning `invalid_client`, with a matching code-review-only PO-script step (no load test needed).

**Naomi Voss — ruling:** Fix applied. This refinement is accepted and ready to hand off. ## Deploy gap found — in team-lead's pre-check, before the PO joint review

**Found by:** team-lead (PM), during the mint pre-check ahead of handing the joint review to the PO. **Not caught by:** this refinement's own acceptance criteria or PO review script, code review, or unit tests — all of which correctly describe what the tokens/verifier *should* do, none of which checked whether the actual deployed manifests set the config surface those criteria assume exists.

**The gap:** the search QA client minted a valid, well-formed RS256 token at the live `/auth/token` endpoint, but the verifier rejected it — `AUTH_JWT_ISSUER`/`AUTH_JWT_AUDIENCE` were never actually set in either Deployment's manifest (the token carried no `iss`; the verifier compared audience against an empty string), and separately, the QA clients had been seeded with `aud: api-service` rather than the design's `loginid-api-service`. Two independent misconfigurations, each alone sufficient to break the joint review.

**Why this matters beyond this one story:** this is the enforcement-site principle (already this project's own standing discipline, from `05-data-ops/decisions/search-query-shape.md` onward) catching itself in the wild — `internal/config` had always supported `AUTH_JWT_ISSUER`/`AUTH_JWT_AUDIENCE` as named config surface (per `PLANNING.md`'s Service boundaries, stated since the design phase), and every refinement doc in this chain (LT-40, LT-51) correctly assumed the manifests set them, because "the config surface exists" and "a manifest actually sets it" were never independently checked against each other. A config variable that's supported by code, named in a design doc, and never actually set anywhere is invisible to a code review, a unit test, and a criteria checklist alike — it only surfaces by trying to use the real deployed thing end to end, which is exactly what this joint review is for.

**Fix in progress:** Theo — PR #41 (sets the manifests correctly, corrects the QA clients' seeded `aud`) plus a runbook update. Renata — adding fail-loud startup validation so a missing/misconfigured `AUTH_JWT_ISSUER`/`AUTH_JWT_AUDIENCE` fails the verifying Deployment's startup instead of silently comparing against an empty string. **The joint review holds until the redeploy verifies** — not resuming on a partial fix.
