# Teardown

What to delete when this take-home's deployment is done with, and who's responsible for triggering it. Written because this deploys to Warren's real, shared production cluster (`decisions/deploy-path.md`), not an isolated sandbox — nothing about a real deployment there has a default end-of-life, so one has to be named explicitly. Per Tobias's (01) objection, accepted during LT-45/LT-47 refinement.

**Re-read against the live namespace, 2026-09-13, backlog closed at 24/24** — the original version of this doc predates LT-46 (Vault), LT-44/LT-49 (the retention-sweep CronJob and its Prometheus objects), and undercounted what actually exists. Every item below was confirmed against the running cluster directly (`kubectl get`), not assumed from what the manifests say should be there.

## What gets deleted, in order

**1. Kubernetes resources in `loginid-takehome` — one command, confirmed as the full blast radius.** `kubectl delete namespace loginid-takehome` removes everything currently running there:
   - Deployments: `api-service`, `api-service-issuer`, `idp-connector` (plus their ReplicaSets/Pods).
   - StatefulSet `postgres` (and its PVC — **the PII this project has been operating on since LT-52 lives here**; confirm no one needs it retained before this step, since deleting the namespace deletes the PVC too, not just the Pod).
   - CronJob `retention-sweep` and the completed `db-migrate` Job.
   - Services: `api-service`, `api-service-issuer`, `idp-connector`, `postgres`.
   - `Ingress/loginid-takehome` (and the `letsencrypt-prod`-issued `loginid-takehome-tls` Secret it manages via cert-manager).
   - The self-signed `Issuer`/`Certificate` pair for Postgres's TLS, and `postgres-server-tls`.
   - `NetworkPolicy`s: `api-service-default-deny`, `api-service-issuer-default-deny`, `idp-connector-default-deny`, `postgres-default-deny`.
   - `ResourceQuota/loginid-takehome-quota`.
   - The six application `ServiceAccount`s: `api-service`, `api-service-issuer`, `db-migrate`, `idp-connector`, `postgres`, `retention-sweep` (Amber's LT-46 provisioning created the last three directly rather than let those workloads run as `default` — see step 2, since each has a bound Vault role that survives this step).
   - The remaining Kubernetes `Secret`s: `qa-client-credential`, `vault-ca-cert` (`postgres-server-tls`/`loginid-takehome-tls` already listed above, since cert-manager manages their lifecycle from the `Issuer`/`Certificate` objects also being deleted here).
   - `ServiceMonitor/loginid-takehome-api-service` and `PrometheusRule/loginid-takehome-retention` (LT-49) — namespaced objects, deleted with everything else in this namespace; no separate step needed, and nothing in `monitoring` is touched (the Prometheus CR's empty `serviceMonitorNamespaceSelector`/`ruleNamespaceSelector` means it simply stops watching a namespace that no longer exists, not an object anyone in `monitoring` has to clean up).
   - `GET /demo` (LT-53, the demo console) — served by the existing `api-service` Deployment via `go:embed` (no separate binary or image) and reached through the same `Ingress/loginid-takehome` already listed above (`/demo` Prefix → `api-service:443`, alongside `/profiles` and `/healthz`). Named here for the runbook's completeness only; it adds nothing to delete beyond what this step and the Ingress line already cover.

**2. Vault — outside Kubernetes entirely, owned by Amber, done after step 1** (the Kubernetes objects reference Vault, not the reverse, so deleting them first is safe and means nothing is still actively authenticating while Vault-side cleanup happens):
   - Five Kubernetes-auth roles and their matching policies: `loginid-takehome-api-service`, `loginid-takehome-api-service-issuer`, `loginid-takehome-db-migrate`, `loginid-takehome-postgres`, `loginid-takehome-retention-sweep` (the sixth workload, `idp-connector`, has a role name reserved but its policy grants nothing — still worth explicitly removing rather than leaving an inert-but-present role behind).
   - The KV v2 paths under `secret/loginid-takehome/`: `db-runtime-credential`, `db-migrator-credential`, `issuer-db-runtime-credential`, `issuer-db-migrator-credential`, `api-service-jwt-signing-key`, `postgres-superuser` — the six application secrets migrated off Kubernetes `Secret`s during LT-46. (The six original Kubernetes `Secret`s these were copied from were already deleted per LT-46's own step 7, before this teardown was ever triggered — nothing left in `loginid-takehome` to remove on that front.)
   - No change needed to the Kubernetes-auth backend (`auth/kubernetes`) itself, the KV v2 mount at `secret/`, or anything under `secret/fmn/`/`secret/mail/` — all pre-existing, shared, and outside this project's footprint entirely (Amber's own provisioning report is explicit that nothing there was touched).

**3. Namespace `loginid-takehome-runners`** (the CI runner-set namespace — separate from #1, don't assume deleting one covers the other) — `helm uninstall loginid-takehome-runners -n loginid-takehome-runners` removes the `AutoscalingRunnerSet`/listener/RBAC Helm installed; deleting the namespace after covers the `loginid-takehome-github-auth` Secret and the `loginid-takehome-deployer` ServiceAccount. This ServiceAccount's `Role` (in `loginid-takehome`, deleted already in step 1) accumulated grants across the project's life beyond its original scope — `apps`, `""` (core), `networking.k8s.io`, `cert-manager.io`, `batch` (`jobs` and `cronjobs`), and `monitoring.coreos.com` (`prometheusrules`, `servicemonitors`) — all namespace-scoped, none reaching anything outside `loginid-takehome`, so nothing here needs unwinding piecemeal; the whole `Role` goes with the namespace in step 1, and this step only removes the identity that used to bind to it. **Also required, and not a Kubernetes step:** uninstall GitHub App `loginid-takehome-arc` (App ID 4926691) from `wtvamp/loginid-takehome` in Warren's GitHub App settings — deleting the Kubernetes Secret does nothing to the App installation itself, which remains valid until explicitly uninstalled.

**4. DNS record** — the `loginid-takehome.uplifttech.org` CNAME (added via Amber/OpenClaw against Bluehost, per the PM's relayed request). Not reversible from this track's tooling; whoever added it removes it the same way.

**5. GHCR images** (`ghcr.io/wtvamp/loginid-takehome/api-service`, `.../idp-connector`, `.../migrate` — the third image, added for LT-52's migration Job, wasn't listed in the original version of this doc) — public images pushed on every merge to main. Low-consequence to leave (no secrets in them, per this track's own container design), but a full teardown deletes the packages too if the repo itself is being taken down.

**6. Not deleted by this teardown:** the GitHub repo itself, the ARC controller (`arc-system`) or the cluster's pre-existing general-purpose runner set (`arc-runners`) — neither was created by this project. Also not deleted: anything in `monitoring` or `logging` (Prometheus, Alertmanager, Grafana, Elasticsearch, Kibana, Filebeat) — all pre-existing shared platform infrastructure this project only ever read from or added namespaced objects into (steps 1 and 2 above already remove everything this project put there); the Filebeat `drop_event` regex fix (`observability.md`) is a platform-level improvement that outlives this project's teardown, not something to revert.
