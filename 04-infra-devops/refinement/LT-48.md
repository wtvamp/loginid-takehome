# LT-48 refinement — S4: local dev-loop, compose profiles for SQLite and Postgres

**Product Owner:** Naomi Voss (01). **Research team:** Desmond Okafor (claims check), Tobias Lindqvist (objection seat). **Engineering:** Theo Bergman (04). **Source:** `04-infra-devops/backlog.md` Story 4 (LT-48), design already done in `04-infra-devops/local-dev-loop.md`.

**Who did the work:** Refined by Naomi Voss (PO).

## Why this one, now

Low-risk, low-effort (`sonnet, low`), fully designed already (`local-dev-loop.md`'s compose sketch), no dependency on anything still in flight — a clean pull between larger stories.

## What this story actually is

Committing `local-dev-loop.md`'s sketch as a real `docker-compose.yml` plus the small supporting pieces it names: `.dev-secrets/` gitignored with an init target/README, the `air` hot-reload target scoped to dev profiles only, and a mock `idp-connector` target for local runs. Not a redesign — the design doc is explicit that this is a sketch to commit, not a proposal to re-litigate.

## Acceptance criteria (restated from `backlog.md` S4)

- [ ] A new developer can run either profile (`docker compose --profile sqlite up` / `--profile postgres up`) from this file alone, without asking what `DB_DRIVER` values are valid — enforcement site: the compose file itself states valid values, no external doc required to start.
- [ ] The `postgres` profile exercises the shared `postgres`-package code path (Postgres, and by extension CockroachDB's shared code) — enforcement site: `api-service-pg`'s `DB_DRIVER: postgres` wiring.
- [ ] Dev credentials never appear in `secrets-delivery.md`'s mechanism or in any real manifest — enforcement site: `.dev-secrets/` is `.gitignore`d, values are placeholder/dev-only, and the file states explicitly (as `local-dev-loop.md` already does) that this isn't the security design.
- [ ] Hot-reload (`air`) has zero effect on the production image build — **the mechanism is named explicitly here (Tobias's objection: `local-dev-loop.md`'s prose asserts "one `air`-based dev target in the compose file" but the sketch's own YAML defines no such service, leaving the actual mechanism to be invented at implementation time, with a plausible-looking wrong answer available — a `dev` build stage added to `cmd/api-service/Dockerfile` itself would leave the production target byte-identical but still touch the file this criterion's own enforcement site says to leave alone).** Fix: `air` runs as its own separate compose service using an unmodified upstream `cosmtrek/air` (or `air-verse/air`) image, bind-mounting the repo source, invoking `go run`/rebuild-on-change against `cmd/api-service` from outside the production image entirely. Enforcement site: `cmd/api-service/Dockerfile` has zero diff from this story (checked via `git diff` against the story's own commits, not just "looks unmodified"), and the `air` service is its own compose entry, not a build-stage variant of the production Dockerfile.
- [ ] **Added — `.gitignore` actually covers `.dev-secrets/`,** checked directly rather than assumed: a placeholder-credential file that *should* be untracked but isn't would be a real, if low-severity, instance of the same "committed secret-shaped value" concern this project polices everywhere else (`gitleaks` in CI, the never-log list). Enforcement site: `.gitignore` entry, confirmed present, plus a `git status` check post-`make dev-secrets-init` showing the four files as untracked.
- [ ] **Added — the `postgres` profile's `postgres` service doesn't collide with the real cluster's own Postgres on a developer's machine** (both default to port 5432) — not a security concern, a "second thing entirely eats a dev's afternoon" concern (this project has already lost time to unrelated-looking failures that were actually port/quota collisions — the LT-46 quota incident is the same *category* of "worked in isolation, collided in combination"). Enforcement site: the compose file's port mapping, or a documented override instructions if a fixed mapping is intentional.

## Non-goals

- No local Kubernetes (`kind`/`minikube`) — explicitly ruled out in `local-dev-loop.md`.
- No CockroachDB profile locally — CI's dedicated job already covers that path; the local loop doesn't need every backend on every save, per the design doc's own reasoning.
- No change to the production Dockerfile or CI pipeline — this story is additive, a new file plus small supporting pieces, not a modification to `containerization-design.md`/`ci-pipeline.md`.
- No production credential handling review — dev credentials are explicitly out of `secrets-delivery.md`'s scope by design, not something this story needs to re-justify.

## PO review script

1. Read the committed `docker-compose.yml` directly against `local-dev-loop.md`'s sketch — confirm it matches (or note deliberate, sensible deviations), not a from-scratch reinterpretation.
2. `docker compose --profile sqlite up` and `docker compose --profile postgres up` each independently, from a clean checkout with no prior `.dev-secrets/` — confirm no undocumented prerequisite blocks either from starting.
3. Confirm `.dev-secrets/` is genuinely untracked (`git status` after `make dev-secrets-init` or equivalent) and appears in `.gitignore`.
4. Confirm `air` runs as its own separate compose service (an unmodified upstream `air` image, source bind-mounted in), not a build-stage variant added to `cmd/api-service/Dockerfile` — `git diff` the Dockerfile against this story's own commits and confirm zero changes, not just an eyeball check.
5. Confirm the `postgres` profile's Postgres service either uses a non-default host port or the file documents the override for a developer who already has something on 5432.

## PO acceptance review — PR #66 (af3d40e), FAIL

**Reviewer:** Naomi Voss (PO), 2026-09-13. This story deploys nothing to the cluster, so I reviewed against a fresh clone (`/tmp/lt48review`), not the live URL. Docker's daemon wasn't running on this machine either (same as Theo's disclosed blocker); started it (`open -a Docker`) and confirmed it live before proceeding — did not skip the live run the way the PR's own disclosure had to.

**Static checks — all PASS.** `git diff` on both Dockerfiles between the pre- and post-merge commits: zero changes, confirmed via the diff itself, not an eyeball check (closing the exact gap Tobias's objection above was written to prevent). No `dev-client`/`dev-secret`/`dev/dev` pattern anywhere under `deploy/` or `04-infra-devops/secrets-delivery.md`. `.gitignore` covers `.dev-secrets/`. `docker-compose.yml` sets `DB_DRIVER: postgres` explicitly on `api-service-pg`.

**Live run — FAIL, the exact recurring pattern this project has hit four times before (LT-33/LT-41's `AUTH_JWT_ISSUER`/`AUTH_JWT_AUDIENCE`/`AUTH_JWKS_URL`, this time in the dev-loop itself).** Ran `./scripts/dev-secrets-init.sh` then `docker compose --profile sqlite up --build`: both `api-service` and `idp-connector` containers **exit immediately** (`Exited (1)`, ~1 second after starting) with:
```
api-service:    AUTH_JWT_ISSUER must be set in verifier mode
idp-connector:  AUTH_JWT_ISSUER must be set
```
Confirmed identically on `--profile postgres` (Postgres itself came up healthy; `api-service-pg` and `idp-connector` both failed the same way). This story's own criterion 1 — "a new developer can run either profile from this file alone, without asking what `DB_DRIVER` values are valid" — is unmet at a level below `DB_DRIVER` entirely: neither profile starts at all. `cmd/api-service/main.go`'s and `cmd/idp-connector/main.go`'s startup checks (the same fail-loud checks LT-33/LT-41 added, correctly still firing) require `AUTH_JWT_ISSUER` (verifier mode also wants `AUTH_JWT_AUDIENCE`; the connector wants `AUTH_JWKS_URL` too) — `docker-compose.yml` sets none of these for any service.

**Root cause, structural, not a one-line env var miss:** the local dev-loop has no issuer/JWKS source at all — no `api-service-issuer` compose service, no static JWKS fixture, nothing for a verifying `api-service`/`idp-connector` to check a token against even if the env vars were set. This is a bigger gap than a missing manifest line; it's a missing piece of the dev-loop's own topology. Fixing it needs one of: (a) a fourth compose service running `api-service` in `APP_MODE=issuer` locally, with `api-service`/`idp-connector` pointed at its `/.well-known/jwks.json` over the compose network; (b) a static, checked-in dev JWKS fixture and a fixed `AUTH_JWT_ISSUER`/`AUTH_JWT_AUDIENCE` pair for local-only use, documented as non-production; or (c) a `--skip-auth`-shaped dev escape hatch, which would need its own explicit non-goal statement given this project's own discipline against exactly that kind of shortcut elsewhere.

**Disposition: LT-48 stays In Test.** Not a partial pass — the file's own quick-start instructions (`docker compose --profile sqlite up`) do not work as written, for either profile, at all. Routing to Theo with the three candidate fixes above; my recommendation is (a), since it reuses the same `APP_MODE=issuer` mechanism this project already built and tested for the real cluster, rather than inventing a second, dev-only auth bypass.

**New, real FAIL found in the `postgres` profile — the DAO never actually connects to Postgres.** `curl http://localhost:8080/healthz` under `--profile postgres` returns `{"db":"down"}`, reproducibly, including from a fully clean state (`rm -rf .dev-secrets .dev-data`, re-run `dev-secrets-init.sh`, bring up `--profile postgres` alone, no prior `--profile sqlite` run in between — ruled out my own test ordering as the cause before reporting this). **Root cause:** `dev-secrets-init.sh`'s `db_dsn` file (used by `api-service`/`api-service-pg`'s *own* DAO connection, distinct from `issuer_db_dsn`) is written unconditionally as `/data/dev.db`, a SQLite path — the script has no profile-awareness, so it can only pick one hardcoded value, and that value is wrong for anyone using `--profile postgres`. This is a genuine regression of this story's own criterion 2 ("the `postgres` profile exercises the shared `postgres`-package code path") — the DAO under that profile never reaches Postgres at all; `DB_DRIVER=postgres` is set correctly on the container, but `DB_DSN_FILE` points to a value that isn't a valid Postgres DSN.

**`dev` profile — PASS**, defaults to SQLite (`DB_DRIVER: ${DB_DRIVER:-sqlite}`), builds via `air`/`GOTOOLCHAIN=auto` (slower first run, downloads the toolchain and Go module cache — expected, not a bug), reaches `db: ok`.

**Disposition (superseded below): LT-48 stayed In Test at this point.** Real progress — the auth-chain fix is solid and independently reproduced — but the `postgres` profile was currently broken by a different, new bug than the one just fixed. Fix needed: `dev-secrets-init.sh` must write a Postgres-shaped `db_dsn` (e.g. `postgres://dev:<password>@postgres:5432/loginid_dev?sslmode=disable`, the main database `docker-entrypoint-initdb.d` already provisions) either unconditionally (since the SQLite driver ignores a well-formed but unused DSN string harmlessly, while the reverse isn't true) or profile-conditionally if the script can detect which profile is active. Routing to Theo. Test artifacts cleaned up (`docker compose down -v` on all three profiles, temp clone removed).
