## What this story actually is

Not a redesign — `observability.md` already specifies every mechanism this story builds:
1. **Logging discipline + lint check** (04): explicit-field `slog` logging, a CI lint rule flagging never-log-list field names/whole-struct log calls.
2. **Ingress-level redaction** (04): search-endpoint `name`/`phone` query fragments never reach an ingress access log.
3. **Audit-log RBAC** (04): a distinct `Role` for audit-log read access, separate from any Secret-read grant.
4. **Retention-sweep metrics + alert** (03 exposes, 04 sinks/alerts): `rows_examined`, `rows_deleted`, `oldest_surviving_row_age_seconds{class}` per LT-44's sweep, only from `Drained == true` results (LT-44's own criterion, unaffected here — this story is the metrics *sink and alert rule*, not re-deriving the emission-gating logic LT-44 already built).
5. **Never-log-list completeness confirmation** (02, Marcus): a sign-off that all 11 items in `handoff-04-secrets.md`'s list map to a named enforcement site, not just a policy statement — the mapping already exists in `observability.md`'s "operationalized" section; this is Marcus confirming it, not this story inventing new coverage.

This is genuinely two-track work, per team-lead's framing: 04 builds the sink, alert rule, ingress redaction, RBAC, and lint check; 03 adds/confirms the metrics-exposure code path at the sweep-invocation layer (LT-44's own code) and a never-log-list enforcement test at the application layer (the lint check's *complement* — a test asserting specific known-sensitive values never appear in captured log output, catching what a static lint rule can miss).

## Priya Nandakumar's ruling — the alert formula (05)

**Answer: skip-visibility alone is not sufficient, a grace term is needed, and — most importantly — skip-visibility must NOT be used as a suppression term.** Three alerts on three properties, none suppressing another.

### Why suppression-on-skip is the dangerous option

If the alert is silenced whenever a skip signal was emitted, then a sweep that *chronically* overruns — every scheduled run skipped because the previous never finished — emits a skip signal every interval and **suppresses the alert permanently.** The suppression mechanism becomes the failure mode, and it does so precisely when the sweep is failing hardest. A single skip and an endless run are indistinguishable by the presence of a skip signal; they differ only in how many consecutive intervals produce no fresh sample.

This is the same error as alerting on the mechanism rather than the property. The property is *"is data surviving past its retention window, and is the sweep still reporting?"* — neither of which is answered by "was a run skipped."

### The three rules

Let **W** = the class's retention window, **I** = the CronJob interval, **D** = a sweep run's duration.

**1. `RetentionSweepNotReporting` — per class.** Fires when no fresh `oldest_surviving_row_age_seconds` sample for that class in **more than 2I**.

A single skip produces a gap of exactly 2I (sample at *t*, next at *t*+2I), so it does not fire — that is the grace for the case this question is about. Two consecutive skips produce 3I and it fires. A dead sweep fires. **This is the alert that distinguishes skipped from dead, and it does so without consuming the skip signal at all** — by counting missed samples rather than by trusting an explanation.

**Per class, not global**, because the sweep is per class by contract (`multi-db-strategy.md` §3c — `DeleteExpired(ctx, class, olderThan, maxRows)`, one class per call). A class whose step errors while the others succeed would keep the global series fresh and go silent unnoticed.

**2. `RetentionWindowExceeded` — per class.** Fires when `oldest_surviving_row_age_seconds{class} > W + 2I`.

**The third term is `2I`, not `I`.** One I is the legitimate lag — a row becomes eligible just after a sweep completes and waits a full interval for the next one, so a healthy system reaches W + I routinely and an alert at W + I fires on every normal cycle. The second I absorbs one skipped run. This assumes **D < I**; if D approaches I the sweep is not keeping up and rule 3 is the real signal.

**3. `RetentionSweepSkipRate` — low severity, the early warning.** Fires when skipped runs exceed ~25% over a rolling day. **This is where LT-44 5a's skip-visibility signal is consumed** — as evidence in its own right, not as a suppression term on rules 1 or 2. It catches "the sweep is completing but only just" before either of the others trips.

### Numbers, at I = 24h

Theo substitutes the real interval; these are the values if the CronJob is daily.

| Class | W | Rule 2 threshold (W + 2I) | Seconds |
|---|---|---|---|
| `idp_cache_orphan` | 7 days | 9 days | 777600 |
| `idp_cache` | 30 days | 32 days | 2764800 |
| `direct` | 24 months (730d) | 732 days | 63244800 |

Rule 1 threshold is **2I = 172800 s** for every class.

**If I changes, rules 1 and 2 both change.** They are expressed in terms of I deliberately: a hardcoded 9 days silently becomes wrong the moment the schedule moves to twice daily or weekly. Prefer deriving them from one `sweep_interval_seconds` constant in the rule config over writing the arithmetic out.

### One interaction that must not be "fixed"

`oldest_surviving_row_age_seconds` is published **only from a `Drained` result** (`multi-db-strategy.md` §3c — the value is meaningless mid-sweep, when deletable rows remain by construction and the oldest survivor is old). So a sweep that runs but never drains — hitting `maxRows` every batch — emits **no valid sample**, and rule 1 fires.

**That is correct behaviour, not a false positive.** A sweep that cannot drain is not keeping up, which is exactly what should alert. Do not "fix" it by publishing non-drained values: that would replace a true alert with a metric that reports a large age every run and trains everyone to ignore it.

## Update — implementation, 03 side (Renata Cole)

**Real Prometheus client-library metrics, not log lines** — LT-44's original `StdoutMetricEmitter` (ad hoc `log.Printf` lines) is replaced by `internal/sweep.PrometheusMetricEmitter`: real `github.com/prometheus/client_golang/prometheus` `Gauge`/`GaugeVec` objects registered in their own private `prometheus.Registry`, satisfying this story's own criterion that these values reach an actual `prometheus.Client` registration. `rows_examined`, `rows_deleted`, `oldest_surviving_row_age_seconds{class}` keep their exact existing names/label values (agreed with Theo before opening this PR) — only `oldest_surviving_row_age_seconds` gated on `Drained == true`, unchanged from LT-44.

**Exposition mechanism, agreed with Theo:** `PrometheusMetricEmitter.Render` writes the registry's current state to an `io.Writer` in real Prometheus text exposition format (via `github.com/prometheus/common/expfmt`) — `cmd/api-service`'s `runSweepMode` calls this once, after every class has been attempted, writing to the pod's own stdout. Stdout, not a Pushgateway push: confirmed with Theo there's no Pushgateway on the real cluster, and standing one up is disproportionate scope for this story — same disposition already reached for LT-44's original three metrics, now extended to cover the real client-library objects too. Theo's sink reads these lines via `kubectl logs` on the CronJob's last pod (PO review script territory), with Pushgateway named as the documented production next step.

**New metric, `sweep_last_run_timestamp_seconds`** — a `Gauge` set unconditionally at the very start of every `Run()` invocation (via a new `MarkRunStarted(now time.Time)` method on the `MetricEmitter` interface, called before any class is attempted, regardless of whether a class later errors or the run is cancelled). Originally proposed to close Tobias's skip-visibility objection directly; **Priya's alert-formula ruling above superseded that plan** — her `RetentionSweepNotReporting` rule already gets the skip-vs-dead distinction from per-class staleness of `oldest_surviving_row_age_seconds` itself, deliberately property-based rather than mechanism-based, and is explicit that an alert consuming a "did a process start" signal is exactly the error her design avoids. **Confirmed with Theo (reconciling this before finalizing, not shipping in silent tension with Priya's ruling): `sweep_last_run_timestamp_seconds` is kept as a supplementary, kubectl-logs-level debugging signal only — deliberately not wired into any of the three alert rules.** It's still useful for a human diagnosing a specific incident (distinguishing "no process even started this cycle" from "a process started but errored before any class drained," a distinction neither of Priya's rules needs to fire correctly but that narrows root-causing once something has already fired).

**Never-log-list enforcement test (03's other criterion):** `internal/api/neverlog_test.go` and `internal/connector/neverlog_test.go` — both redirect the standard library's package-level logger to a buffer and drive REAL request paths (the token-issuer's opportunistic-rehash-persist-failure branch with a distinctive client secret; a real search+get flow through the actual `StdoutAuditLogger` with seeded PII; the connector's `/auth`/`/identity` handlers across all their outcomes with a distinctive vendor username/password/access-token) rather than asserting against the log-call source text the way 04's static CI lint check does. Verified each test can actually fail: injected a real leak into `tokenhandler.go`'s rehash-failure log line, confirmed the test caught it, reverted. Covers never-log-list items 1, 2, 3, 6, and 11 (`handoff-04-secrets.md`'s eleven-item list) at the application layer; items 4, 7, 8, 9, 10 are either DAO/ingress-layer concerns already covered elsewhere or not exercised by a real call site in this track's own code.

Full `go build`/`go vet`/`go test`/`staticcheck`/`gofmt`/`gitleaks` clean.
