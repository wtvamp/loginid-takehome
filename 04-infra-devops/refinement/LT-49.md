## Priya Nandakumar's ruling — the alert formula (05)

**Answer: skip-visibility alone is not sufficient, a grace term is needed, and — most importantly — skip-visibility must NOT be used as a suppression term.** Three alerts on three properties, none suppressing another.

### Why suppression-on-skip is the dangerous option

If the alert is silenced whenever a skip signal was emitted, then a sweep that *chronically* overruns — every scheduled run skipped because the previous never finished — emits a skip signal every interval and **suppresses the alert permanently.** The suppression mechanism becomes the failure mode, and it does so precisely when the sweep is failing hardest. A single skip and an endless run are indistinguishable by the presence of a skip signal; they differ only in how many consecutive intervals produce no fresh sample.

This is the same error as alerting on the mechanism rather than the property. The property is *"is data surviving past its retention window, and is the sweep still reporting?"* — neither of which is answered by "was a run skipped."

### The three rules

Let **W** = the class's retention window, **I** = the CronJob interval, **D** = a sweep run's duration.

**1. `RetentionSweepNotReporting` — per class.** Fires when no fresh `oldest_surviving_row_age_seconds` sample for that class in **more than 2I**.

A single skip produces a gap of exactly 2I (sample at *t*, next at *t*+2I), so it does not fire — that is the grace for the case this question is about. Two consecutive skips produce 3I and it fires. A dead sweep fires. **This is the alert that distinguishes skipped from dead, and it does so without consuming the skip signal at all** — by counting missed samples rather than by trusting an explanation.

**Per class, not global**, because the sweep is per class by contract (`multi-db-strategy.md` §3c — `DeleteExpired(ctx, class, olderThan, maxRows)`, one class per call). A class whose step errors while the others succeed would keep the global series fresh and go silent unnoticed.

**2. `RetentionWindowExceeded` — per class.** Fires when `oldest_surviving_row_age_seconds{class} > W + 2I`.

**The third term is `2I`, not `I`.** One I is the legitimate lag — a row becomes eligible just after a sweep completes and waits a full interval for the next one, so a healthy system reaches W + I routinely and an alert at W + I fires on every normal cycle. The second I absorbs one skipped run. This assumes **D < I**; if D approaches I the sweep is not keeping up and rule 3 is the real signal.

**3. `RetentionSweepSkipRate` — low severity, the early warning.** Fires when skipped runs exceed ~25% over a rolling day. **This is where LT-44 5a's skip-visibility signal is consumed** — as evidence in its own right, not as a suppression term on rules 1 or 2. It catches "the sweep is completing but only just" before either of the others trips.

### Numbers, at I = 24h

Theo substitutes the real interval; these are the values if the CronJob is daily.

| Class | W | Rule 2 threshold (W + 2I) | Seconds |
|---|---|---|---|
| `idp_cache_orphan` | 7 days | 9 days | 777600 |
| `idp_cache` | 30 days | 32 days | 2764800 |
| `direct` | 24 months (730d) | 732 days | 63244800 |

Rule 1 threshold is **2I = 172800 s** for every class.

**If I changes, rules 1 and 2 both change.** They are expressed in terms of I deliberately: a hardcoded 9 days silently becomes wrong the moment the schedule moves to twice daily or weekly. Prefer deriving them from one `sweep_interval_seconds` constant in the rule config over writing the arithmetic out.

### One interaction that must not be "fixed"

`oldest_surviving_row_age_seconds` is published **only from a `Drained` result** (`multi-db-strategy.md` §3c — the value is meaningless mid-sweep, when deletable rows remain by construction and the oldest survivor is old). So a sweep that runs but never drains — hitting `maxRows` every batch — emits **no valid sample**, and rule 1 fires.

**That is correct behaviour, not a false positive.** A sweep that cannot drain is not keeping up, which is exactly what should alert. Do not "fix" it by publishing non-drained values: that would replace a true alert with a metric that reports a large age every run and trains everyone to ignore it.

### Addendum — the skip rule's window, and why it needed more than a number (05)

**Theo's deviation is confirmed: rolling 7 days, fire at ≥2 skipped runs.** He is right that "~25% over a rolling day" is structurally meaningless once `I` = 24h — a day holds at most one scheduled run, so the threshold could only ever be 0% or 100%. That was my error: I wrote rule 3 before pinning `I`, and did not revisit it when I did.

**But widening the window alone does not restore what rule 3 was for, and that is worth stating rather than quietly accepting.** Rule 3 exists as the *early* warning — it should fire while the sweep is still completing, before rules 1 or 2 trip. At `I` = 24h it cannot: two skips spread across seven days already lets a row reach `W + 2I`, which is exactly `RetentionWindowExceeded`'s threshold, and two *consecutive* skips reach `W + 3I` and trip it outright. A skip-count rule at this interval fires **with** rule 2, not before it. Any threshold low enough to lead it (≥1 skip in 7 days) fires on a single node restart and gets muted.

**So the early warning has to key on duration, not skips** — and the data for it is already persisted in `retention_sweep_run` (A7, `05-data-ops/multi-db-strategy.md` §3d):

- **`RetentionSweepDurationApproachingInterval`** — low severity. Fires when `finished_at - started_at` exceeds **0.5 × I** on any run in the last 7 days. This is the genuine leading indicator: run duration climbing toward the interval is *why* skips start, and it is observable while every run still completes. At take-home volumes it should never fire; it is a canary for growth, not a current condition.
- **`RetentionSweepSkipping`** — low severity, as Theo has it: `sum(missed_slots)` over a rolling **7 days ≥ 2**. Kept as the backstop for skips with causes other than duration — node pressure, failed pods, a suspended `CronJob` — which the duration rule cannot see.

Both remain non-suppressing on rules 1 and 2, per the original ruling.

**If `I` ever changes, all four thresholds move together** — `2I` for rule 1, `W + 2I` for rule 2, `0.5I` for the duration rule, and the 7-day window for the skip rule, which is `7I` and should be written as such. One more argument for deriving everything from a single `sweep_interval_seconds` constant rather than committing the arithmetic to the rule file: the failure this addendum corrects was exactly a hardcoded assumption surviving a change to the value it depended on.

### Addendum — where the metric comes from (05, after Amber's inventory)

Prometheus scrapes `api-service`, not the `CronJob`. The sweep is a short-lived pod and the scraper a long-lived one; they never overlap, so the sweep must **persist** its per-class result for `api-service` to read. Specified as contract amendment **A7**, `05-data-ops/multi-db-strategy.md` §3d — a `retention_sweep_run` table, written twice per run, read by `api-service` with the same runtime credential (all DML, no new grant), DDL in the three per-backend migration directories, self-pruned at 30 days, explicitly **not** a `RetentionClass` and explicitly **never** writing to `deletion_log`.

**One correction to the requested shape, which changes what the alert rules can key on.** A `skipped_reason` column cannot work: under `concurrencyPolicy: Forbid` a skipped run **has no pod**, so nothing executes that could write a row explaining itself — the column would be NULL on every row that exists. Skips are instead recorded by the *next* run as **`missed_slots`** (the gap since the last `finished_at`, divided by `I`, minus one). The three alert rules are unaffected in substance, and gain a cleaner source:

- **`RetentionSweepNotReporting`** keys on the age of the latest non-NULL `finished_at` per class — a genuine absence of rows, not a stale scrape.
- **`RetentionWindowExceeded`** keys on `oldest_surviving_at` from the latest **drained** row; the table's tying CHECK (`drained OR oldest_surviving_at IS NULL`) makes a non-drained value unrepresentable rather than something the rule has to filter defensively.
- **`RetentionSweepSkipRate`** becomes `sum(missed_slots)` over a rolling day against expected runs — **computable from the table alone**, with no dependency on scraping Kubernetes `CronJob` events, which is what LT-44 5a's skip-visibility requirement was reaching for.

A third distinguishable state falls out that none of the three rules previously had: a row with a NULL `finished_at` means the sweep **started and died**, as opposed to never having been scheduled. Worth a low-severity rule of its own if Theo wants it — a crashing sweep and an unscheduled one need different fixes, and today both look like silence.

## Correction — mechanism superseded by Amber's observability inventory (not this work wasted, redirected)

**The stdout-exposition mechanism above (§147–157) cannot be the final sink — Prometheus does not ingest stdout at all**, and a `CronJob` pod is typically gone before any scrape could catch it regardless. This was a reasonable assumption at the time (no Pushgateway on the cluster, and stdout was already this project's working pattern for LT-44's original metrics) but Amber's read-only inventory (`handoff-amber-observability-inventory.md`, requested after Warren asked whether the cluster already had an observability stack) confirmed the real constraint directly against the live Prometheus CR rather than assuming one didn't exist.

**Not wasted work — most of it carries forward directly:** the real `prometheus.Gauge`/`GaugeVec` objects, the exact metric names/label values, the `Drained`-gating, and the never-log-list enforcement tests are all unaffected and still correct. **What changes:** `PrometheusMetricEmitter.Render`'s destination. Instead of writing to the sweep pod's own stdout (unreachable by any scraper), the sweep must persist its per-class `SweepResult` to the database (Priya's addendum, per the corrected 03-side criterion above), and `api-service` — the one always-up pod — reads that persisted state and serves it on its own `/metrics` HTTP port for a `ServiceMonitor` to scrape.

**Correction (Tobias's objection): `sweep_last_run_timestamp_seconds` does NOT carry forward as the rule-1 signal — it's a different metric from the one the alert actually needs, and conflating them was my own error in an earlier draft of this correction.** `sweep_last_run_timestamp_seconds` is set unconditionally at the *start* of every `Run()` (via `MarkRunStarted`), regardless of whether the run succeeds — a "last attempted" signal. Priya's `RetentionSweepNotReporting` rule needs the age of the latest non-NULL **`finished_at`** per class from the `retention_sweep_run` table (§ below) — a "last completed" signal, keyed per class, not a single process-wide "last started" gauge. These are genuinely different metrics with different failure semantics (a sweep that starts and hangs mid-class would keep `sweep_last_run_timestamp_seconds` fresh while `finished_at` goes stale — exactly the distinction that should trip the alert). `sweep_last_run_timestamp_seconds` stays what Renata's implementation note already says it is: a supplementary, `kubectl logs`-level debugging signal, not wired into any alert rule. The alert-rule-facing gauge `api-service` must derive and serve is the per-class `finished_at`/`oldest_surviving_at` pair read from `retention_sweep_run`, not this one.

**Also binding now, not previously known:** no metric or label name may contain the substring `health` (Filebeat silently drops matching log lines) — checked the existing metric names above (`rows_examined`, `rows_deleted`, `oldest_surviving_row_age_seconds`, `sweep_last_run_timestamp_seconds`) against this constraint: none contain it, so no rename is needed, but this is now a standing naming constraint for any future metric this project adds, not just today's set.

Flagged to Renata and Theo directly — this refinement doc's own acceptance criteria (04 side, metrics-sink and alert-rule entries above) already reflect the corrected mechanism; the code needs to catch up to match.

## Update — the persisted-metrics implementation, 03 side (Renata Cole)

**New `internal/sweepstore` package** implements amendment A7 (`05-data-ops/multi-db-strategy.md` §3d) end to end: `Store` writes `retention_sweep_run` twice per run (`StartRun` at the start, `FinishRun` at completion — matching §3d's own three-distinguishable-states design exactly), computes `missed_slots` per Priya's formula (`floor(gap/I) - 1`, zero when unknown/normal), self-prunes rows older than 30 days once per `Run()`, and reads the table back for `/metrics`. `internal/sweep.Run`/`runClass` gained a new `RunRecorder` interface (satisfied by `*sweepstore.Store`) and an `interval time.Duration` parameter — a `RunRecorder` failure is logged and otherwise ignored, never turning a real, successful deletion into a reported sweep failure.

**Migrations:** `migrations/{postgres,cockroachdb,sqlite}/000{03,03,02}_retention_sweep_run.sql`, per §3d's exact schema/constraint names, three files (not `shared/`, since this is DDL).

**Cross-backend timestamp handling — one real bug found and fixed by live end-to-end testing, not by any unit test.** Converting a pgx-native `time.Time` to a string via plain `RFC3339` (for the shared aggregation code path both backends go through) truncates sub-second precision; a `started_at`/`finished_at` pair a few milliseconds apart — the realistic case for a fast, near-empty sweep — could round to the same second or swap order, producing a small **negative** `retention_sweep_last_run_duration_seconds`. Every unit test I'd written used gaps of a second or more and missed this entirely; running the actual binary against a real database and curling `/metrics` caught it. Fixed with a fixed-width, full-nanosecond-precision layout (`preciseTimeLayout`) used everywhere this package converts a timestamp to/from a string — closes both the precision loss and (per §3d's own warning) the variable-width lexicographic-sort-order trap a naive `RFC3339Nano` would have reintroduced on SQLite. Pinned with a dedicated regression test (`TestLastRunDuration_SubSecondPrecisionNeverNegative`) plus Priya's own named-priority conformance assertion (`TestTimestampOrdering_SpreadAcrossAMonth`, spread over ~a month specifically, not a single-value round trip) — both pass on real Postgres and real SQLite.

**Metric set, reconciled against Naomi's later ruling (not my own first draft, which still had two mismatches with it):**
- `retention_sweep_last_finished_timestamp_seconds{class}` — the latest run's completion, **ungated on `Drained`** (a died-but-not-drained run still counts as "the sweep is reporting," per Priya's own framing — this replaces an earlier, wrongly-drained-gated `retention_sweep_last_success_timestamp_seconds`).
- `oldest_surviving_row_age_seconds{class}` — unchanged, drained-only, matching LT-44's own established rule.
- `retention_sweep_last_run_duration_seconds{class}` — the latest run's `finished_at - started_at`, agreed with Theo.
- `retention_sweep_missed_slots{class}` — the **latest run's own value only**, not a pre-summed total (my first draft built exactly the pre-summed `retention_sweep_skipped_total` Naomi's ruling above removed) — Theo's `RetentionSweepSkipping` rule does its own `sum_over_time()` across its rolling window from repeated scrapes, the standard Prometheus pattern.
- `rows_examined{class}` / `rows_deleted{class}` — unchanged, latest run, whether or not it drained.

`/metrics` served on its own port (`:9101`, Service port name `metrics`, agreed with Theo for his `ServiceMonitor`/`NetworkPolicy`, PR #68) — a fresh `prometheus.Registry` built from `LatestSnapshots` on every scrape, never a background poller, so a scrape always reflects the table's current state.
