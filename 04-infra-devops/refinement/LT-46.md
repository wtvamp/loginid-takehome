# LT-46 refinement — Story 2: secret delivery, re-scoped to Vault

**Product Owner:** Naomi Voss (01). **Research team:** Imogen Hale, Desmond Okafor, Tobias Lindqvist. **Engineering:** Theo Bergman (04, manifests); provisioning: Amber (Vault itself); review: Marcus Ilori (02, Vault policies).

**Who did the work:** Refined by Naomi Voss (PO); Warren's ruling on the re-scoped criterion.

## Why this changed

`backlog.md`'s original Story 2 criterion 5 required Kubernetes `Secret` resources encrypted at rest in etcd, enforced via cluster `EncryptionConfiguration` — a control-plane setting on Warren's own shared cluster (confirmed absent when checked directly: no encryption-provider config on the kube-apiserver). Escalated to Warren as accept-residual-or-enable-and-reverify; **his ruling: neither — move application secrets out of Kubernetes `Secret` objects entirely**, into the cluster's existing Vault, delivered via the Vault Agent Injector. This closes the original concern more completely than encrypting `Secret`s at rest would have (a Vault-delivered secret is never written to etcd as a `Secret` object in the first place, not merely encrypted once there) and reuses infrastructure that already exists on this cluster rather than requiring a control-plane change on a shared box outside this project's authority.

## Re-scoped criterion (replaces the original etcd-encryption line)

Application secret material is not stored in etcd; delivered by Vault Agent with per-`ServiceAccount` Vault roles. Enforcement site: Vault policy per role, plus a namespace check that none of the six application `Secret`s exist.

## The six application secrets this criterion covers (enumerated directly from the deployed manifests, not assumed)

1. `api-service-jwt-signing-key` — the JWT signing private key, currently mounted only into `api-service-issuer` (LT-32's F13 fix).
2. `postgres-superuser` — consumed only by the Postgres `StatefulSet` itself.
3. `db-migrator-credential` — the migration-runner credential (DDL rights), consumed by the migration `Job`.
4. `db-runtime-credential` — the runtime service credential (DML-only), consumed by `api-service`.
5. `issuer-db-migrator-credential` — the issuer's own migration-runner credential (client-store schema).
6. `issuer-db-runtime-credential` — the issuer's own runtime credential, consumed by `api-service-issuer`.

**Accepted platform exceptions, named explicitly rather than silently grandfathered in as Kubernetes `Secret`s:**
- `postgres-server-tls`, `loginid-takehome-tls` — both `cert-manager`-issued TLS certificates (a self-signed `Issuer`/`Certificate` for Postgres; the public Ingress's `letsencrypt-prod`-issued cert). **Excluded on a mechanistic basis, not just convention:** `cert-manager` mints and rotates the certificate content itself — there is no static credential value for Vault to inject, unlike the six secrets above, which are human-provisioned, out-of-band values. This is also the standard TLS-delivery pattern for every other app on this cluster (`decisions/deploy-path.md`). Named explicitly here so a reader isn't left wondering whether these two were simply missed from the count.
- **`qa-client-credential` — resolved (Theo + Marcus, jointly):** stays a Kubernetes `Secret`. It's ops/review tooling, never mounted into or consumed by any running pod — a human fetches it via `kubectl` to manually mint a review token — so the Vault Agent Injector pattern doesn't structurally apply to it at all. Confirmed no `ServiceAccount` has any Secrets-API grant (`deploy/rbac.yaml`), so its access boundary remains the existing operator trust boundary (`threat-model.md` Assumption 7), not a new gap this migration needed to close. Recorded in `handoff-04-secrets.md`.

## Acceptance criteria for this re-scoped piece

- [ ] All six application secrets above are delivered via Vault Agent Injector sidecar/init-container pattern, with a distinct Vault role per consuming `ServiceAccount` — matching the existing per-service RBAC-scoping discipline this project already applies to Kubernetes `Secret`s (never one shared credential across services).
- [ ] A namespace check (manual `kubectl get secret -n loginid-takehome` or a CI/audit script) confirms none of the six names above exist as Kubernetes `Secret` objects post-migration.
- [ ] Vault policies are scoped per-role to exactly the path(s) that role's service needs — no policy grants broader read access than the specific secret(s) that `ServiceAccount` consumes, mirroring the existing "no ServiceAccount can get/list a Secret it doesn't mount" discipline (`backlog.md`'s own criterion 3, unaffected by this change).
- [ ] The migrator/runtime credential separation (criterion 4, unaffected) is preserved under Vault — two distinct Vault paths/roles, not one shared secret with two consumers.
- [x] The `qa-client-credential` disposition is decided: stays a Kubernetes `Secret` (see above) — resolved, not ambiguous.
- [ ] **Added per Tobias's objection:** a pod whose Vault Agent init-container cannot authenticate or fetch its secret within a bounded timeout fails **visibly** — `CrashLoopBackOff` with a distinguishing log line or event, not an indefinite `Init` hang — matching the fail-loud discipline this project already had to add twice for the same underlying failure shape (`AUTH_JWT_ISSUER`/`AUTH_JWT_AUDIENCE`, then `AUTH_JWKS_URL`: "config the code needs but nothing wired," discovered live both times). This re-scope introduces a new runtime dependency every consuming pod didn't have before (Vault reachable and correctly policy-matched at every startup/restart/rollout, not just at scheduling time, and coupling to a shared-cluster service with its own maintenance windows) — the failure mode for that dependency not being met needs the same explicit treatment, not a silent gap this refinement would otherwise leave for a future live review to rediscover a third time.
- [ ] **Added per Amber's provisioning pass:** each of the five workloads (`api-service`, `api-service-issuer`, `postgres`, `db-migrate`, `idp-connector`) runs under its own named ServiceAccount, never `default`. Amber found `postgres` (`StatefulSet`), `db-migrate` (`Job`), and `idp-connector` (`Deployment`) declared no `serviceAccountName` at all and ran as `default` — binding their Vault roles to `default` instead would have let any pod on that SA assume any of the five roles (e.g., `idp-connector`, ruled to get nothing, could have assumed the widest role, `loginid-takehome-postgres`, and read `postgres-superuser`), inverting the least-privilege requirement while appearing to satisfy it. Enforcement site: `deploy/manifests.yaml` declares all five ServiceAccount objects and each workload's `serviceAccountName` explicitly; Amber's own denial matrix (`default` denied all five roles, `idp-connector` denied the `postgres` role, same SA name in a different namespace denied) is the evidence to re-run at review time, not re-derive.
- [ ] Marcus (02) reviews the Vault policies before this is called Done — same review discipline already applied to every other security-graded surface in this project.

## Non-goals

- No change to the TLS-certificate delivery mechanism (`cert-manager` → Kubernetes `Secret` stays as-is) — explicitly out of scope, named as an accepted platform exception above.
- No change to the CI runner's own RBAC (still zero grants on `secrets`, already correct and unaffected by where the secrets themselves live).
- No re-litigation of which secrets exist or what they're for — this story is a delivery-mechanism change, not a secrets-inventory redesign.

## Incident — first deploy (#56), 2026-09-13 ~10:44–11:00

`#56`'s initial deploy of Vault Agent delivery to all five workloads caused a database outage of roughly 16 minutes (healthz `db: down`, search failing) — the fail-loud criterion above worked exactly as designed during it (pods sat in `Init:CrashLoopBackOff`, nothing served stale data), but the outage itself is a real finding for this story. Two distinct root causes, both fixed in the `#58` hotfix:

1. **Namespace CPU-request quota exceeded.** Each of the five workloads gaining an injected Vault Agent container (sidecar or init) added that container's own default CPU/memory *request* on top of the application container's own — five simultaneous additions pushed the namespace over `requests.cpu` quota. `postgres-0`, a `StatefulSet` with no rolling-update slack, couldn't be (re)scheduled at all as a result. Fixed via explicit `vault.hashicorp.com/agent-limits-cpu`/`-requests-cpu` (and memory) annotations sized down from the injector's defaults, `agent-pre-populate-only: "true"` where a sidecar isn't needed after initial render (further shrinking the persistent footprint), and a namespace quota raise. Verified post-fix: `requests.cpu` at 350m/1500m, comfortable headroom (see acceptance review above).
2. **Wrong CA file path in the issuer's init container.** The `vault.hashicorp.com/agent-extra-secret: vault-ca-cert` annotation mounts the CA secret at `/vault/custom/`, not a subdirectory under it — the issuer's `vault.hashicorp.com/ca-cert` annotation pointed at the wrong path, so Vault Agent's TLS verification against `vault.vault.svc:8200` failed at startup. Fixed by correcting the `ca-cert` annotation to `/vault/custom/ca.crt` (confirmed today at that exact path on every workload's `extra-secrets` volume — see acceptance review above).

Added to the pre-deploy PO-script step (numbered 0, above): read the namespace quota *before* applying, specifically because a quota rejection and a Vault-auth failure present identically as `Init:CrashLoopBackOff` and are easy to conflate after the fact.

This confirms the hotfix actually fixed the quota interaction, not just relocated it.

**Step 6 (forced injector failure) — FAIL, a real gap, not a pass.** I ran this myself: a throwaway pod under the `api-service` ServiceAccount, annotated for Vault injection with `vault.hashicorp.com/role: loginid-takehome-postgres` (a role `api-service` is correctly denied — Vault itself returned `403 service account name not authorized`, confirming the policy boundary holds). But the pod did **not** reach `CrashLoopBackOff`. It sat in `Init:0/1`, `RESTARTS: 0`, for the full ~7 minutes I observed it — the `vault-agent-init` container's own process never exits; it retries authentication forever with a growing internal backoff (26.6s, then 46.55s, presumably continuing to grow), so Kubernetes never sees a container exit to restart. This is precisely the "indefinite silent `Init` hang" this criterion was written to rule out, and it's the actual current behavior, not a hypothetical: least-privilege is enforced correctly (the denial itself works), but the failure is invisible by the standard this story itself set — no `CrashLoopBackOff`, no distinguishing terminal state, just a pod that never becomes Ready and never signals why via pod status alone (the reason is in the container's logs, which nothing surfaces to `kubectl get pods`/alerting without someone already knowing to look).

**Disposition:** LT-46 stays In Test. This is not a blocking regression of anything already working (the denial/least-privilege behavior is correct, and the quota/CA-path incident is fully resolved) — it's the one acceptance criterion this refinement itself added that isn't yet met. Needs a fix to the Vault Agent's own retry behavior (e.g., a bounded max-retry count that causes the init container to exit non-zero — Vault Agent supports this via its auto_auth retry configuration, or an equivalent liveness-probe-driven kill on `Init:0/1` pods stuck past a timeout) before this can be called Done. Routing to Theo/Amber.

Test pod cleaned up (`kubectl delete pod lt46-injector-failure-test -n loginid-takehome`) — no lasting change to the cluster.
