## LT-45 acceptance criteria (restated from `backlog.md`, corrected for the real cluster)

- [ ] Both images build multi-stage (distroless final stage, non-root, read-only root filesystem) and contain nothing but the binary (+ CA certs for `idp-connector`). Enforcement site: the Dockerfile's final `COPY` list.
- [ ] Neither Pod can write its own root filesystem at runtime. Enforcement site: `securityContext.readOnlyRootFilesystem: true`.
- [ ] `idp-connector` is unreachable except from `api-service` — enforced by a **default-deny `NetworkPolicy`**, since the cluster's namespace default is allow, not deny; this is not optional hardening on a shared cluster. Enforcement site: the `NetworkPolicy` ingress rule scoped to `api-service`'s pod selector.
- [ ] The JWT signing private key is mounted only into `api-service-issuer`'s Deployment, never `api-service`'s own — enforcement site: `api-service`'s manifest carries no volume/mount referencing that `Secret`, verified by manifest inspection, not RBAC alone.
- [ ] All manifests target `namespace: loginid-takehome` (corrected from the design-phase placeholder `loginid-poc`) — enforcement site: every manifest's `metadata.namespace`, grepped for the old placeholder returning nothing.
- [ ] A namespace-level `ResourceQuota` caps total CPU/memory the whole take-home can consume, independent of any single manifest's own `resources.limits` — added specifically because this is shared production infrastructure, per `decisions/deploy-path.md` §3. Enforcement site: the `ResourceQuota` object itself, applied to the namespace.
- [ ] A public `Ingress` (class `nginx`, TLS via `letsencrypt-prod`) routes `/healthz` (and whatever path prefix 03 finalizes for the rest of the API) to `api-service`, and issuer-specific routes to `api-service-issuer`. `idp-connector` gets **no route** — never publicly reachable, per its own design. Enforcement site: the `Ingress` resource's path rules.
- [ ] The migration `Job` runs with `parallelism: 1` and is gated by the CI pipeline's concurrency mechanism (LT-47), not Kubernetes ordering alone.
- [ ] The GitHub Actions deploy step uses a **second, narrowly-scoped `AutoscalingRunnerSet`** registered specifically to `wtvamp/loginid-takehome`, with RBAC limited to the `loginid-takehome` namespace only (no cluster-scoped permissions) — **not** the cluster's existing shared runner set, per `decisions/deploy-path.md` §2's blast-radius reasoning. Enforcement site: the runner set's own RBAC manifest, scoped by namespace, reviewed independently of the take-home's application manifests.

## LT-47 acceptance criteria (restated from `backlog.md`, revised for real deploy per the agile-loop bar)

- [ ] A lint or test failure blocks merge — required status check, not advisory.
- [ ] A CockroachDB-specific SQL incompatibility surfaces at PR time via a dedicated CockroachDB testcontainer job.
- [ ] Only one migration run can reach the migrate stage at a time, across concurrent deploys — enforced by the pipeline's own concurrency group/mutex on the deploy environment.
- [ ] No secret enters a build log or image layer — `gitleaks` stage plus the Dockerfile's minimal `COPY` list (LT-45).
- [ ] **Revised — no longer "documented but not invoked":** this refinement adopts full auto-deploy on merge, given the agile-loop bar's own definition of done ("deployed and reviewable at a public URL"), with no design-side objection raised in `decisions/deploy-path.md` — the deploy stage actually runs: build → push images to GHCR → apply manifests via the scoped runner set → print the public URL and deployed commit SHA in the job summary. (Theo's agreement to this — no objection, no manual gate requested — is now recorded directly in `decisions/deploy-path.md` §5a.) This replaces the design-phase criterion that treated deploy as describe-only; that criterion predates the agile-loop bar and is now obsolete, not just superseded in emphasis.
- [ ] The PR-check workflow (lint, build, `-race` tests, `govulncheck`) requires no cluster access and runs on GitHub-hosted runners; only the merge-to-main deploy workflow uses the scoped self-hosted runner set — per `decisions/deploy-path.md` §6's sequencing, so a PR from an untrusted or draft branch never touches cluster credentials.
- [ ] The job summary on a successful merge-to-main run states the public URL and the deployed commit SHA explicitly, in plain text — this is what makes LT-34's PO review script (and every later story's) executable without a human hunting through logs.

## Non-goals

- No DNS management — the record's existence/correctness is Warren's call, flagged as an open item above, not something this track has credentials to fix.

- No change to other namespaces or other apps' Ingress/DNS on this cluster.

## Additional acceptance criterion — teardown procedure (added per Tobias's objection)

- [ ] A teardown procedure document exists in `04-infra-devops/` naming exactly what to delete: the `loginid-takehome` namespace (and everything in it), the second `AutoscalingRunnerSet` plus its GitHub registration (deregistering it from `wtvamp/loginid-takehome`, not just deleting the Kubernetes object), the `Ingress` and its DNS record, and any object this pair created outside the namespace (none are planned, but the doc states this explicitly rather than assuming it). Enforcement site: the document's own existence and completeness, checked against the actual manifest list in the merged PR.

This is a real, not cosmetic, gap on infrastructure of this kind: everything else in this pair is carefully isolated for launch, but nothing addresses end-of-life. A take-home interview evaluation is time-bounded; a live namespace, a self-hosted runner with cluster-facing RBAC, a public HTTPS endpoint, and a JWT signing key are not, unless something says otherwise. Without a named teardown procedure and owner, the realistic failure mode is exactly the one production infrastructure tends to accumulate: isolation gets audited once at launch and then the whole thing is quietly forgotten, while its attack surface persists indefinitely. The trigger condition itself (when teardown actually happens — a fixed number of days after Warren confirms the interview process has concluded, or on request) is Warren's call, not this track's or this refinement's to set unilaterally — flagged to the PM below for that specific decision; this criterion only requires that the procedure exist and name an owner, not that it fire automatically on a date this refinement invents.
