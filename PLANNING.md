## Service boundaries (owned by 03, read by 04)

Set by 03 during Phase 1 planning (full reasoning: `03-engineering-delivery/PLAN.md` §4).

- **Two binaries**, not one: `cmd/api-service` (Q1 DAO + Q2 REST API, client-facing, bearer-token auth) and `cmd/idp-connector` (Q3, outbound-only to vendors) — different threat models/auth surfaces per 02, independent scaling needs, mirrors the assignment's own Q2/Q3 split.
- **Package layout:**
  ```
  cmd/api-service/main.go
  cmd/idp-connector/main.go
  internal/dao/        # Repository composite interface (Profiles/Credentials/Methods) + postgres/cockroachdb/sqlite implementations
  internal/model/      # shared structs: UserProfile, UserCredential
  internal/api/         # REST handlers, router, auth middleware
  internal/connector/   # /auth, /identity client + handlers
  internal/config/      # env-var config loading, shared by both binaries
  internal/app/         # shared bootstrap (route registration, config wiring) both cmd/*/main.go wrap thinly
  ```
- **Config surface:** environment variables only (12-factor: config lives in the environment, not in checked-in files) — `DB_DRIVER` (postgres|cockroachdb|sqlite), `DB_DSN`, `DB_DSN_FILE` (file-mount path; takes precedence over `DB_DSN` when both are set, per 02's `handoff-04-secrets.md` S7 revision — a DSN's embedded password is as exposed by `kubectl describe`/crash dumps/env-in-child-process as any other secret in that inventory, so `DB_DSN` is now a transitional fallback, not a permanent equal option), `HTTP_ADDR`, `AUTH_JWT_ISSUER` = `https://auth.loginid-takehome.internal` / `AUTH_JWT_AUDIENCE` = `loginid-api-service` (literal values per `handoff-03-auth.md` — not secrets, safe to ship in config), `CONNECTOR_JWT_AUDIENCE` = `idp-connector-service` (the connector's own inbound audience, distinct from `AUTH_JWT_AUDIENCE` — `handoff-03-auth.md` v2 / `connector-security.md` §5, consistency-pass F15), `CONNECTOR_CLIENT_ID`/`CONNECTOR_CLIENT_SECRET` (api-service's own client credential for obtaining a `connector:identity-lookup`-scoped token to call idp-connector on a caller's behalf — a secret, added to `handoff-04-secrets.md`'s inventory as row 10 per F15), `APP_MODE` = `verifier` (default) | `issuer` (selects which of `api-service`'s two Kubernetes Deployments a given pod is — the issuer Deployment alone mounts the JWT signing-key Secret, per 02/04's F13 fix in `handoff-04-secrets.md`/`containerization-design.md`; confirmed spelling from Theo), `IDP_ABC_BASE_URL`, `IDP_ABC_CLIENT_ID`/`IDP_ABC_CLIENT_SECRET`. No flags, no config files.
- **DAO driver-selection mechanism:** a factory `dao.New(driver, dsn string) (dao.Repository, error)` chosen at startup from `DB_DRIVER`. `dao.Repository` is a composite interface — `Profiles() ProfileRepository`, `Credentials() CredentialRepository`, `Methods() AuthMethodRepository`, plus `CreateProfileWithCredential(ctx, p, c)` and `Close() error` directly on the composite — matching 05's now-accepted contract in `multi-db-strategy.md` §1/§3b, kept deliberately distinct (not one flat interface) because it's a load-bearing PII/credential-separation control per `05-data-ops/pii-governance.md`: a handler has to reach for the credential accessor on purpose. Each backend package returns one struct satisfying the composite. Factory signature and `DB_DRIVER` selection are unchanged.
- **Stable for 04 to build against:** the two-binary split, the `cmd/` entrypoint names, the env-var config approach and variable names above, and the `dao.New(driver, dsn)` factory signature. **05's contract has landed and is accepted** (consistency-pass F23 — this line previously said the composite's method set was "not yet stable" pending the contract; it has since landed, including `CreateProfileWithCredential` and `Close()` above). **Not yet stable:** internal DAO implementation details, ORM/query-builder choice, handler-package internals — those are implementation, not contract.
- **Note for 04, from the Go-layout three-hats ruling (`03-engineering-delivery/decisions/go-layout-debate.md`):** "two binaries" is a *process* boundary, not a claim about host/deploy placement — whether `api-service` and `idp-connector` land on the same node is 04's call, not implied by this section. If they're colocated, `idp-connector`'s outbound-call failure isolation from `api-service` depends on 04's resource limits, not just the process split. Separately, S4 now requires `context.WithTimeout` on every outbound vendor call and a bounded connection pool/backoff on token-refresh retries — not a 04 concern, but flagged here so 04 doesn't assume connector-side backpressure is handled elsewhere.
