# Threat Model

Owner: Marcus Ilori (`02-ai-security-architecture`). Scope per this track's `CLAUDE.md`: credential storage, PII exposure, and third-party `access_token` handling. Retention/lifecycle policy is `../05-data-ops/CLAUDE.md`'s call, not mine — I model exposure and access risk, not how long data should live.

## Assumptions, named explicitly

1. **Assets in scope**: `user_credential` (username, method, password — modeled by Priya/`05-data-ops` as a lookup-table `method`, not a native enum, so a given user can have more than one credential row, e.g. password + WebAuthn), `user_profile` (name, address, phone), and third-party `access_token`s obtained via the IDP connector's `/auth`.
2. **`method` is not "always password."** Priya's schema treats `method` as an FK into an `auth_method` table (`id`, `name`, `requires_secret`, `is_active`). That means "credential storage" is not one hashing problem — it's a family of them, one per method, and this document treats it that way rather than assuming a single password column.

### Concrete hashing decision, against the landed schema

Priya's prose schema in `../05-data-ops/multi-db-strategy.md` (the `.sql` files were deliberately wiped with the rest of the code on 2026-09-12; the prose contract is the source of truth until Warren's code go-ahead) gives `user_credential` three columns for this purpose: `secret` (nullable, bytes holding the PHC-encoded hash string — `BYTEA`/`BLOB`, Go `[]byte`; corrected by the cross-track consistency pass, F34 — this was previously described here as "nullable TEXT," which is wrong against the landed contract type; NULL where `auth_method.requires_secret = false`, e.g. passkey/WebAuthn), `hash_algo` (VARCHAR, e.g. `'argon2id'`), and `hash_cost` (INTEGER, the work factor at hash time). This track's concrete decision against those columns:

- **`hash_algo = 'argon2id'`**, per OWASP's current recommendation, consistent with NIST SP 800-63B Rev. 3's requirement of a memory-hard one-way key derivation function (800-63B Rev. 3, currently in force, requires a "suitable" memory-hard KDF without naming Argon2id specifically by name; Argon2id-by-name guidance appears in the SP 800-63-4 draft revision, not yet final — cited precisely rather than invoking "NIST recommends Argon2id" as if it were settled text). bcrypt is the documented fallback (`hash_algo = 'bcrypt'`) only if the Go implementation's Argon2id library support is unavailable in the chosen stack — a call for `03-engineering-delivery` to confirm, not a reason to default to bcrypt speculatively.
- **Salt handling**: no separate salt column is needed or wanted. Argon2id's standard encoded output (the `$argon2id$v=19$m=...,t=...,p=...$<salt>$<hash>` PHC string format) embeds a fresh random salt per row inside the `secret` column's own bytes — this is what makes the hash self-describing and rehashable without a side lookup. Do not add a `salt` column; it would be redundant with the encoded format and an easy place for an implementation to accidentally desync salt from hash.
- **`hash_cost` at minimum**: memory ≥19 MiB, iterations ≥2, parallelism ≥1 (OWASP's Argon2id floor) — recorded per-row (not just globally) specifically so a future cost bump can be applied to newly-created/rotated rows without forcing every existing row to rehash in lockstep, per the schema's own stated intent of supporting an in-place scheme upgrade.
- **`requires_secret = false` rows** (passkey/WebAuthn, `secret IS NULL`): no hashing question at all — the server holds only public key material for those methods, which is a different asset class (public, not secret) and does not belong in `secret`/`hash_algo`/`hash_cost` at all if/when a passkey method is actually added. Flagged here so `03-engineering-delivery` doesn't try to force a WebAuthn public key through the password-hashing path.
3. **LoginID's own business is passwordless/FIDO2-based authentication.** The assignment nonetheless asks for a `password` field in `user_credential`. I treat that as a deliberate test of whether the submitter still applies correct secret-handling discipline to a legacy-shaped requirement, not as license to under-engineer it. Noted once here; not re-litigated per section.
4. **Implementation is now under way (updated 2026-09-12 — Warren's implementation go-ahead, agile loop: PO Naomi → engineering → QA under Oren → DevOps → deployed to a public URL).** This document's findings graduate from design-time requirements to things that must actually hold in the running code as each story is built; the second-review discipline (S8's pattern) now runs on security-graded stories before they're called done, not only on design documents.
5. **The repository is public** (`https://github.com/wtvamp/loginid-takehome`), effective 2026-09-12 — updated from a private design-time assumption. This changes the severity, not the substance, of every "never in source or committed config" requirement already in this document and in `handoff-04-secrets.md`: those were always correct discipline; they are now a categorical requirement with no private-repo safety net, since anyone on the internet can read every commit, including history. No secret, real credential, or real PII may ever land in this repository, in any commit, including ones later reverted — a reverted commit is still in git history and still public.
6. **Trust boundary**: this service is the system of record for `user_profile`/`user_credential` and is a *client* of third-party IDPs (ABC/XYZ) for `/auth` and `/identity`. Those vendors are outside our control; we can only constrain what we do with what they return.
7. **Trust boundary — deployment operator (dated update, 2026-09-12: first deploy is live).** The deployment target is a **shared production cluster**, reached via a plain nginx Ingress + cert-manager on the cluster's shared LoadBalancer (DNS CNAME to `uplifttech.ddns.net`), public at `https://loginid-takehome.uplifttech.org` — no tunnel involved; 04 deploys with **direct `kubectl`** from a **repo-scoped GitHub Actions Runner Controller (ARC) runner authenticated via a GitHub App**. This is a real deployment, not a hypothetical: the trust boundary named below is now live, not a design-time assumption. Whoever can apply a manifest can read any Secret it mounts, so "secrets are safe once they are in the cluster" is an assumption about the operator (here, effectively the CI pipeline's own deploy identity), not a property of the design — consequence, set as a requirement in `handoff-04-secrets.md`: manifests carry Secret names, never values; values are provisioned out-of-band. **The CI deploy ServiceAccount itself is now a named instance of this trust boundary** (Tobias Lindqvist's finding): a namespace-scoped Role granting it Secret verbs for app-Secret management would, unless explicitly restricted, also let it read the JWT signing-key Secret — a path from "CI runner compromised" to "mint tokens" that this document did not previously name because there was no live CI deployer to name. Required controls in `handoff-04-secrets.md`: the signing key created out-of-band, and the deployer Role's Secret verbs scoped by `resourceNames` (or a separate namespace) to exclude it. **Because this cluster is shared, not dedicated to this project**, the operator boundary also now includes whoever else has rights on that cluster outside this project's own manifests — a fact worth naming rather than assuming the cluster's blast radius is scoped to this app alone; 04 owns whether that shared-tenancy risk needs any further narrowing (e.g., NetworkPolicy, namespace isolation) beyond what this document already requires.

9. **Ruling — `api-service`-to-Postgres connection requires TLS, not `sslmode=disable` (LT-52, 2026-09-13, Priya Nandakumar's question).** Traffic is pod-to-pod inside `loginid-takehome`, NetworkPolicy-scoped to `api-service` and the migration Job only, with no service mesh and an unknown CNI wire-encryption story. **`sslmode=disable` is not acceptable here, even at take-home scale — require `sslmode=require` with a cert-manager-issued server certificate on the Postgres StatefulSet.** Reasoning: `user_profile` PII crosses this connection in cleartext under `disable`, and this document already requires TLS for the identical asset at the client-facing hop (Asset 2, row above) — allowing plaintext for the same PII one hop later, on a network whose isolation properties are explicitly unverified ("no mesh, don't know the CNI's story," on a **shared** production cluster, not a dedicated one), would be an inconsistency in this track's own standard, not a proportionate scope cut. NetworkPolicy is the right control for a different property (*who may connect*) and doesn't substitute for encryption (*is the payload readable in transit*) — both controls are required together, not either/or. This is not the disproportionate-effort case (a service mesh, mTLS everywhere) that this document has declined elsewhere: cert-manager is already in place for the public Ingress, so issuing one more server certificate for the StatefulSet is a bounded, already-tooled task, not a new capability to stand up. `sslmode=require` (encrypts the connection) is sufficient; full certificate verification (`sslmode=verify-full`, requiring `api-service` to validate the server's identity against a CA bundle) is not required for this hop — NetworkPolicy already constrains which pods can reach the DB Service in the first place, so the additional value of verifying the server's certificate identity is marginal here, and skipping it avoids extra CA-bundle distribution complexity for a bounded, single-namespace connection. **Implemented and verified (Theo Bergman, 2026-09-13):** self-signed cert-manager Issuer+Certificate for Postgres (the public `letsencrypt-prod` issuer can't issue for an internal DNS name), `sslmode=require` in both the migrator and runtime DSNs, confirmed end-to-end in a disposable scratch namespace (`SHOW ssl;` returns `on`, migration ran successfully through it) before landing on the real cluster.
10. **Accepted risk — Deployment-write access is functionally equivalent to Secret-mount access, absent an admission controller (found by Naomi Voss/Desmond Okafor during LT-32 refinement, mitigation by Theo Bergman, 2026-09-12; re-scoped 2026-09-13 for the Vault Agent delivery mechanism, LT-46).** The CI deployer's Role correctly has no `secrets` verbs (Assumption 7), but it does hold `create`/`update`/`patch` on `deployments`, which the pipeline needs to function at all. Originally: a Kubernetes volume mount is resolved by the kubelet at pod admission, not gated by RBAC on the referenced Secret held by whoever applied the manifest — so a manifest PR adding a `volumeMount` for the JWT signing-key Secret directly into the verifying Deployment would apply successfully via deploy-write access alone. **Under Vault delivery (v3, `handoff-04-secrets.md`), the JWT signing key is no longer a Kubernetes Secret at all, so this specific attack shape (referencing a Secret object by name) no longer applies to it** — a real, structural narrowing, not just a relabeling. The equivalent risk re-manifests one level up, through a different field: Vault's Kubernetes auth ties a role to a specific ServiceAccount, and a pod authenticates to Vault using whatever ServiceAccount its own spec names — so a manifest PR that changes a Deployment's `spec.serviceAccountName` to one bound to a broader Vault role would achieve the same privilege escalation the old volume-mount trick did, and plain Kubernetes RBAC doesn't restrict which ServiceAccount a pod spec may reference (that requires an admission controller, still absent here for the same disproportionate-effort reason as before). No admission controller (Gatekeeper/Kyverno/OPA) exists on this cluster. **Accepted, stated explicitly rather than left silent, on the same three grounds as before, updated for the new mechanism:** structural property of any RBAC-only cluster with no ServiceAccount-binding admission check, applying to every workload's ServiceAccount assignment, not uniquely to the issuer's; the CI deploy identity is already this document's named privileged trust boundary; and the compensating detective control needs to change shape but still exists — the CI check should grep the manifest set for each Deployment's `serviceAccountName` against an expected allow-list per Deployment name, not for a Secret's name (which no longer appears in the manifest at all under Vault delivery) — flagged here as a required update to the existing check, not assumed to still catch the risk unchanged. This residual is judged acceptable *for this system* on those grounds, not treated as solved — and the Vault migration is a net risk reduction (the signing key itself is no longer reachable this way at all) even though the underlying structural gap (no admission control) persists in a different field.

11. **Confirmed correct, not merely acceptable — `Recreate` deployment strategy for both single-replica Deployments (`api-service`'s verifying Deployment and the issuer Deployment), ruled 2026-09-13.** This isn't only an availability trade-off (brief downtime on redeploy, fine for a take-home with no uptime SLA) — it's the right call for a security reason specific to this design: `GrantLimiter` (the token-endpoint brute-force control) is deliberately in-process, per-pod state (Helena Marsh's PR #34 review), accepted only on the stated condition that the issuer Deployment stays single-replica, since round-robining across replicas trivially bypasses per-`client_id`/per-IP backoff. `RollingUpdate` on a "single-replica" Deployment still briefly runs two pods simultaneously during rollout (that's the mechanism that makes it zero-downtime) — during that window, there would genuinely be two replicas, each with independent, unsynced `GrantLimiter` state, which is exactly the multi-replica bypass condition the single-replica acceptance was conditioned on never actually happening. Any other per-pod in-memory rate/counter state (the cumulative distinct-record-touch counter, if implemented in-process rather than a shared store) carries the same exposure. `Recreate` (terminate-then-create, never two replicas at once) keeps the single-replica invariant true at all times, not just in steady state, which is the actual reason to prefer it here over the general zero-downtime convenience of `RollingUpdate`.

12. **New trust boundary — Vault's Kubernetes auth method trusts the cluster API server's `TokenReview` result (2026-09-13, LT-46: Vault Agent Injector replaces raw Kubernetes Secrets as the delivery mechanism, `handoff-04-secrets.md` v3).** A Vault role granting any workload access is only as trustworthy as the guarantee that the ServiceAccount token presented to Vault genuinely belongs to the pod claiming it — Vault's Kubernetes auth backend validates this by calling back to the API server's `TokenReview` API. This is not an independent root of trust: it's built on top of the same cluster trust this document already relies on elsewhere (the CI deployer's RBAC, Assumption 7's operator boundary), stated explicitly rather than left as an implicit assumption that Vault is somehow a stronger boundary than Kubernetes itself. Consequence for Assumption 10 above: Vault access is gated by ServiceAccount identity, which is itself a Kubernetes-RBAC-adjacent field a compromised CI deployer could still manipulate (a Deployment's `spec.serviceAccountName`) — the two boundaries compound rather than substitute for each other. **Net effect of the migration, stated plainly: real improvement, not merely different.** Application-level secrets no longer sit in etcd's base64-not-encrypted-by-default storage at all (closed by removal); each workload's Vault role can now express exactly the KV paths it needs (a strictly finer-grained control than "mounts this Secret or doesn't"); and the rendered secret files live on an in-memory volume rather than whatever a Kubernetes Secret volume mount's storage backend happens to do. The underlying "no admission controller" gap (Assumption 10) isn't closed by this migration — it moves to a different field — but the blast radius of exploiting it is smaller now that the signing key itself isn't a Secret object an attacker can reference by name. **Vault's CA expires 2026-12-14** — a platform renewal item for Warren, not something this document resolves, named here so it's visible in the artifact rather than only in Amber's provisioning report.

13. **Pre-existing finding, surfaced by Amber's Vault provisioning but predating it — three workloads shared one identity (`default`), not scoped to their own least-privilege access, found 2026-09-13.** `postgres`, `db-migrate`, and `idp-connector` had no `serviceAccountName` set and ran as the namespace's `default` ServiceAccount. This was already a weakness under the pre-Vault, Kubernetes-Secret-only design — Kubernetes RBAC (Assumption 7's namespace-scoped Roles) is granted per-ServiceAccount, so three workloads sharing one identity meant any RBAC scoping intended for one of them was, in practice, granted to all three; it simply hadn't been named as a finding until Vault's per-role model made the shared identity visible as a blocker to provisioning distinct roles. **Fixed as part of this story, not deferred:** Amber created dedicated ServiceAccounts for all three and bound Vault roles to them specifically, then proved the fix rather than asserting it — `default` is denied all five roles, `idp-connector`'s ServiceAccount cannot assume the `postgres` role, and a same-named ServiceAccount in a different namespace is denied (confirms the role binding is genuinely namespace-and-identity-scoped, not name-matched loosely). This denial matrix is the evidence `handoff-amber-vault-provisioning.md` records; it's what Helena's review should re-run against the live roles, not re-derive from the document's own prose.

14. **Ruling — Vault client TLS verification is required; `tls-skip-verify` is not acceptable for this channel, even though it's a pattern used elsewhere in this deployment (2026-09-13).** Vault is now the delivery path for every application-level secret in the system (Assumption 12) — the single highest-value channel to intercept in this entire design, higher-value than the Postgres connection Assumption 9 already requires TLS for. Skipping certificate verification on that channel would mean any on-path attacker (the same shared-cluster, unknown-CNI-isolation conditions already named in Assumption 7) could MITM every secret this system delivers, silently. **Ruled: verify against the staged `vault-ca-cert`, not `tls-skip-verify`**, for every Vault Agent connection (init container and sidecar alike) — the "house pattern" of skipping verification elsewhere in this deployment does not extend to this channel given what flows over it. This is not a close call the way the health-endpoint build-id exception was; the value of what's protected and the value of what's disclosed by skipping are both too high here for the convenience trade-off that made sense elsewhere.

## Method: STRIDE per asset, attacker-centric

I'm using STRIDE (Microsoft, but the categories are now common vocabulary in the field — not claiming Anthropic or LoginID provenance for the framework itself) as the checklist, but organized by asset rather than by data flow diagram element, since that maps directly onto this track's ownership boundaries.

### Asset 1: `user_credential` (password + other auth methods)

| Threat | Scenario | Mitigation (this track's requirement) |
|---|---|---|
| **Information disclosure** — password store compromise | DB dump or SQL injection exposes the `password` column | Never store plaintext or reversibly-encrypted passwords. Argon2id (OWASP Password Storage Cheat Sheet current recommendation, memory-hard, GPU-resistant) with per-row random salt, tuned to ≥19 MiB memory / ≥2 iterations as a floor, re-tuned to the deploying hardware. bcrypt is an acceptable fallback only if Argon2id is unavailable in the chosen Go stack. |
| **Information disclosure** — non-password methods | A WebAuthn public key or TOTP shared secret is not a password, but the table conflates them under one `password` column name | Method-aware storage: WebAuthn credential public keys are not secrets and can be stored in the clear (they're public keys by design) but the associated counter and credential ID must not be attacker-writable — signature-counter and clone-detection semantics per W3C WebAuthn Level 2 §6.1.1; TOTP shared secrets ARE secrets and must be encrypted at rest (not hashed — the server needs to recover the value to verify), using envelope encryption with a KMS-held key, mechanics owned by `../04-infra-devops/CLAUDE.md`. |
| **Elevation of privilege** — credential stuffing / brute force | Attacker replays leaked username/password pairs against `/auth`-adjacent endpoints | Rate limiting and progressive backoff per username and per source IP, preferred over hard account lockout — NIST SP 800-63B §5.2.2 actively disfavors lockout as a self-inflicted denial-of-service vector against the legitimate user, in favor of throttling/backoff/step-up challenge. Never reveal via response timing or error text whether the *username* or the *password* was wrong (user enumeration). |
| **Tampering** | Attacker modifies `method` or the credential row to downgrade a user from a strong method (WebAuthn) to a weak one (password) they control | Method changes/additions require re-authentication with an *existing* registered method (step-up), never a bare authenticated-session write. |
| **Repudiation** | No record of who created/rotated a credential | Audit log of credential creation/rotation events (actor, timestamp, method type — never the secret itself). |

### Asset 2: `user_profile` (name, address, phone — PII)

| Threat | Scenario | Mitigation |
|---|---|---|
| **Information disclosure via the search API** | Question 2 asks for "search and retrieve." An authenticated-but-unscoped search endpoint is a PII enumeration engine — an attacker with any valid token can page through the entire user table by name/phone fragments | Search must be authorization-scoped (a caller sees only records it's entitled to, not the whole table) and rate-limited/paginated; see `api-auth-design.md` for the concrete authz model. This is the single highest-severity finding in this document, precisely because it's easy to build the search feature "to spec" and miss that spec implies a data-exfiltration primitive. |
| **Information disclosure in transit** | PII served over an unencrypted or downgradable channel | TLS 1.2+ mandatory (1.3 preferred where supported), HSTS, no plaintext fallback, per NIST SP 800-52 Rev. 2's server TLS configuration guidance. Mechanics of certificate issuance are `04-infra-devops`'s call; the requirement is this track's. **This requirement is not scoped only to the client-facing hop — it governs the same PII asset wherever it's in transit, including the `api-service`-to-Postgres connection (ruled explicitly, Assumption 9, after LT-52's `sslmode=disable` question).** |
| **Information disclosure via logs** | PII (address, phone) written to application logs, error traces, or APM breadcrumbs | Structured logging with an explicit PII-field denylist; log the *fact* of a profile access (who, when, which record id) never the field values themselves. |
| **Tampering** | Unauthorized profile field modification | Same authz model as read access; write operations additionally require the resource owner or an admin-scoped credential, not just "any authenticated caller." |

### Asset 3: Third-party `access_token` (from the IDP connector, question 3)

| Threat | Scenario | Mitigation |
|---|---|---|
| **Information disclosure** — token at rest | `access_token` from ABC/XYZ cached or persisted in plaintext | Treat it as a secret with the same bar as our own credentials: encrypted at rest if persisted at all, short TTL, never written to application logs (a full request/response log of `/auth` is an anti-pattern — vendor password *and* resulting token both land in the same log line). |
| **Information disclosure** — token in transit / replay | Token intercepted and replayed against the vendor or against us | Vendor calls over TLS only; tokens treated as bearer secrets — anyone holding one can act as us to the vendor, so token scope should be minimized to `/identity` only if the vendor's API supports scoped tokens. |
| **Spoofing** | A malicious or compromised proxy sits between us and ABC/XYZ | Certificate validation not disabled "for convenience" in any environment, including local dev — a design note the engineering track should carry into implementation. |
| **Denial of service via credential exhaustion** | Our own credentials to call ABC/XYZ (needed to obtain the `access_token` in the first place) are hardcoded or checked into source | Secrets management is `04-infra-devops`'s mechanism, but the requirement — never in source, never in a committed config file, injected at runtime — is set here. |

## What this track deliberately does not resolve

- How long a cached `/identity` result may be retained — that's data governance (`../05-data-ops/CLAUDE.md`).
- Which specific secrets manager or KMS product is used — that's `../04-infra-devops/CLAUDE.md`; I only require that one exists and that secrets never live in source or plaintext config.
- Whether the product should offer passwordless auth as the primary path (it should, per LoginID's own market position, and `../01-product-industry-research-design/CLAUDE.md` makes that case) — that's product framing, not a threat.
- **This API's own issued JWT bearer access tokens are not re-modeled as a fourth asset here** — they're `api-auth-design.md`'s asset, covered by that document's own token-lifecycle and scope-authorization sections. Named explicitly (S8 review, Helena Marsh) so the boundary between "the three assets this track's `CLAUDE.md` names" and "thorough" reads as a deliberate scope line, not an oversight.
