# Planning Approach: Claude-Architecture Recommendations for This Team

Author: Marcus Ilori (02-ai-security-architecture), synthesizing input gathered directly from all four other track owners — naomi-voss (01), renata-cole (03), theo-bergman (04), priya-nandakumar (05) — plus this track's own perspective and `research-claude-architecture-best-practices.md`. Where the tracks disagreed or emphasized different things, I say so rather than averaging them into a mush; where they independently converged (which happened more than I expected), I note that too, because five agents with separate contexts landing on the same answer is itself weak evidence the answer is right.

Throughout, I distinguish Anthropic-documented guidance from my own judgment applied to this specific project. Where I say "Anthropic recommends," that traces to a specific source in `research-claude-architecture-best-practices.md`. Where I say "my view" or "I'd recommend," that's this project's reasoning, not a citation.

## 1. Models and effort levels, by role

The knobs: model ∈ {fable, opus, sonnet, haiku}, effort ∈ {low, medium, high, xhigh, max}. Warren has already set the orchestrator (team-lead) to fable at high. My reasoning below takes that as fixed and reasons about everyone else relative to it.

**Orchestrator / PM (team-lead) — fable, high.** Confirmed correct, not just accepted. The orchestrator holds the only cross-track state that matters (scope boundaries, status, "who's blocked on whom") and makes judgment calls that propagate into every track if wrong — a boundary misjudged here (e.g., letting infra silently absorb a decision that was security's to make) costs five agents' worth of rework, not one. That's the single seat in this project where the highest model ceiling earns its cost. I would not go to xhigh/max for this role: xhigh/max effort spends more test-time compute on deeper deliberation per response, and orchestration work here is mostly reading condensed hand-offs and delegating — breadth of correct judgment across many small decisions, not depth on one hard problem. High is the right ceiling for that shape of work.

**Track owners (the five of us, in planning/design mode) — sonnet, medium-to-high, track-dependent.** This is my own judgment, and it's not uniform across tracks — the five tracks are not equally deep:
- Product/research framing (01, Naomi) is synthesis and judgment-call writing — Naomi herself recommended sonnet/medium for her own track, and I agree: the value there is scoping and narrative tightness, not deep technical reasoning, so paying for more depth than the task uses is waste.
- Security (02, this track) and the engineering track's design decisions (03) involve genuine multi-step reasoning with real correctness stakes — sonnet/high is the right default there.
- Data-ops (05, Priya) is the one track where I'd go above sonnet during *planning*, and Priya made the argument better than I would have: the schema and DAO interface contract is precision-heavy but low-volume, and the cost of a wrong nullable-vs-required field or a wrong interface signature ripples into both 03 and 04. That's asymmetric risk, not asymmetric size — one careful opus/high pass on that specific artifact costs little in absolute tokens and avoids a class of downstream rework nothing else in this project can prevent. This is the same "spend the expensive model where a wrong foundational call is costly to reverse" principle I apply to implementation below, just moved one step upstream to where the contract is actually decided.
- Infra (04, Theo) explicitly self-assessed low-to-medium, sonnet, and I agree with his reasoning: it's the smallest-surface-area track, it's consumer-not-producer during planning, and over-resourcing it during the planning phase is the same mistake as over-engineering the infra itself.

**Throwaway research subagents (fact-gathering, doc lookups, exploring existing code) — haiku, low, or sonnet/low if some judgment is needed.** Naomi's own workflow already does this (haiku/sonnet-low fanned out for industry facts, then one sonnet/medium synthesis pass) and it generalizes: per Anthropic's orchestrator-worker pattern, a subagent's exploration noise never re-enters the coordinator's context — only its condensed output does — so there's no reason to pay for a stronger model on a narrow, verifiable, throwaway task. Fan these out in parallel; that's where cheap-and-fast is unambiguously the right call.

**Implementation (writing the actual Go code — DAO, REST handlers, connector) — sonnet, medium-to-high; opus only for one narrow piece.** Renata, who owns this work, put it as sonnet/medium-high: once upstream contracts land, this is CRUD/REST/HTTP-client code against clear specs — not novel enough for opus, but not so trivial that low-effort stubs are acceptable when "reads as intentional engineering" is the grading criterion. Tests (table-driven Go, mocked DB/HTTP) are sonnet/medium. I agree with all of that, and it changes my earlier position: I had planned to reserve opus/high for implementing the DAO's multi-database interface, but if Priya delivers the interface as actual Go signatures (see hand-off structure, §2), the hard decision has already been made upstream at opus/high and implementing against it is sonnet work. That leaves the connector's token lifecycle logic (acquire, cache, refresh, never-persist-in-plaintext) as the one implementation surface where I'd still spend opus/high — the correctness bar is a security property, not just a passing test, and the assignment's question 3 is where a subtle bug most directly contradicts this track's own threat model. Anthropic's own internal eval (research doc §3) found an Opus-lead/Sonnet-subagent configuration beat a single-agent Opus baseline by 90.2% at materially higher token cost; the lesson I take is "spend the expensive model where a wrong foundational call is costly to reverse," not "use Opus everywhere."

**Review/verification passes — high effort always; independence scaled to stakes.** Two positions came in here, and they're compatible rather than contradictory. Renata wants a high-effort review pass on her own output before calling it done, same model — catching a busted interface boundary late costs more than the tokens. That's right for engineering surfaces. My addition, Anthropic-motivated but my own extension: their multi-agent paper's rationale for parallel independent subagents is that separation of concerns "reduces path dependency" — an agent reviewing its own output inherits its own blind spots. Resolving the two explicitly: Renata's same-session high-effort self-review is the *first* pass on everything she produces — it's cheap, it catches the interface-boundary class of bug she's worried about, and there's no reason to skip it. For the security-graded surfaces specifically (credential storage design, token handling, the auth/authz scheme, and the connector code that implements them), a *second* pass in a genuinely independent session is added on top, because those are exactly what LoginID said they're grading the reasoning quality of, and a self-review cannot by construction catch an assumption the author didn't know they were making. For everything else (infra sketches, product prose, routine handlers), the self-review alone is proportionate. This is a take-home POC, not a production deploy, and calibrating review independence to actual stakes is part of the "why," not corner-cutting.

**Fable reserved narrowly.** I would not spread fable across all five track-owner seats — that's five top-model seats purchased for a take-home whose own cited evidence (the Opus-lead/Sonnet-worker eval) argues for concentrating the strongest model at the lead and running capable-but-cheaper models at the worker tier. The one place I'd consider a second fable seat: a final cross-track consistency pass, run once near submission, checking the five tracks' finished deliverables against each other for contradictions (the exact class of problem Naomi flagged — two tracks independently deciding what `/identity` returns). That's a single, short-lived, high-value use of the top model, not a standing role.

## 2. Architecture pattern for planning-phase coordination

**Default: orchestrator-worker, not peer-to-peer mesh.** This is Anthropic's own documented pattern (research doc §3 — lead agent decomposes, spawns scoped subagents, subagents report back condensed findings, lead synthesizes) and Naomi independently converged on the same recommendation from the product side: five agents cross-talking as a full mesh during planning is more collision risk than value. Status and scope decisions should route through team-lead.

**Exception: direct track-to-track handoffs on a specific shared decision.** A pure hub-and-spoke model is wrong for one case — two tracks with a direct, narrow dependency on each other's specific decision. This track and data-ops already did this, and Priya asked that it be recorded here as the worked example: we coordinated directly on modeling `user_credential.method` as a lookup table rather than a native enum, because that's a two-party decision (her schema, my method-aware credential-storage design), not a project-wide one, and routing it through team-lead both directions would have added latency for no benefit. Renata, by contrast, explicitly doesn't want peer chatter with 01 or 04 — she wants clean hand-offs from 02 and 05 that she reads once and implements against. Both are right; the difference is whether a genuine two-party decision exists. The rule I'd formalize: point-to-point messaging is fine for a specific, bounded, two-track decision; it must still land in a durable file (see §3) as the source of truth, not live only in chat history; and it doesn't substitute for the orchestrator's overall view of status.

**Plan mode.** Narrower than I first drafted, after Renata's input. She doesn't want plan mode for her own track — the plan already exists in the assignment text, and if upstream tracks hand her concrete contracts there's nothing left to plan that a plan-mode pass would catch. I think that's correct *conditional on the hand-offs being concrete enough* (see next paragraph); if 05 hands her a prose strategy instead of interface signatures, plan mode before the DAO becomes necessary again because she'd be making design decisions that aren't hers. So the rule: plan mode gates decisions that constrain another track — API contract shapes, schema fields, token formats, the Go interface itself — at the track that owns the decision, before it's declared stable. It does not gate implementation against an already-concrete contract. For a track whose CLAUDE.md brief is already specific and self-contained (per the root file's own stated goal), formal plan-mode approval on top of that brief is redundant — the brief already is the approved plan.

**Fork vs. fresh scoped agent.** Fork when a task needs the current session's accumulated context and would lose something real by starting clean (e.g., resuming a security review with everything already threat-modeled in-session). Fresh scoped agent when the task is genuinely independent and carrying forward unrelated context would only dilute it (a documentation lookup, a track that hasn't started). This project's five persistent track-owner teammates are, at a coarser grain, already an instance of "fresh scoped agent": each seeded only with the root `CLAUDE.md` plus its own track file, not all five tracks' accumulated history — that's Anthropic's just-in-time retrieval principle (research doc §2, technique 4) applied at the team-structure level, not just the subagent level.

**Hand-off structure.** Per the research doc (§2/§3), Anthropic's own subagents target roughly 1,000–2,000 tokens of condensed findings passed to a coordinator — never a raw transcript. Concretely here: hand-offs happen through each track's `CLAUDE.md` Status section and named deliverable files, referenced by relative path, exactly as the root file already mandates ("cross-reference other tracks by relative path... rather than restating their content"). A `SendMessage` between tracks signals readiness or asks a targeted question — it is not the transport for the actual content, and Renata was explicit that she wants upstream decisions written somewhere durable, not relayed verbally through team-lead.

Priya then raised the bar on what "condensed" has to mean for a hand-off into implementation, and I'm adopting her standard project-wide: a hand-off is implementable only if the receiving track can act on it *without re-deriving the sender's reasoning*. For 05→03 that means the actual Go interface signatures (method names, parameter and return types, error semantics), the field-level schema per entity with types and nullability, and explicit notes on what is out of scope for the receiver (e.g., 03 must not invent its own PII/credential separation — that's already decided in 05's governance note). Priya's commitment is to bake that Go-shaped contract directly into `../05-data-ops/multi-db-strategy.md` so it's copy-pasteable, not descriptive. Prose strategy alone forces re-derivation, which is both wasted tokens and a drift risk. The same standard applies to this track's outbound hand-offs: 02→03 needs the token scheme and where it's validated, not a discussion of alternatives; 02→04 needs, per Theo's ask, an explicit secrets inventory (DB credentials, IDP credentials, signing keys) and a never-log list, because he implements delivery and does not set the requirement. Those two are follow-ups for this track once the planning pause lifts — the existing `api-auth-design.md` and `connector-security.md` contain the decisions but not yet in that receiver-shaped form.

The replies I got to my own bounded question were all in the 300–600 word range — the condensed-finding size the research doc describes — which is mild evidence the pattern holds when the question is scoped tightly.

**Context and cache management over a multi-hour project.** Two concrete disciplines, both sourced from the research doc's context-engineering section: (1) keep each track's `CLAUDE.md` stable within a working session — edit it at the start or end of a turn, not interleaved mid-task, because an edit to a file currently loaded in context invalidates that cached prefix (research doc §4/§5); (2) when a track's own work legitimately grows long across multiple similar passes (data-ops iterating across DB backends is the clearest case in this project), compact deliberately — write a short settled-decisions summary to a file and start the next pass fresh from that summary rather than carrying the full multi-turn history forward (§2, technique 1). Neither of these is exotic; they're the direct, mechanical application of Anthropic's documented "context rot" mitigation to this project's actual shape of work.

**Planning dependency order across tracks.** All five tracks described their dependencies independently and the graph they describe is consistent — nobody claimed a dependency someone else denied. Assembled:

1. **First wave, in parallel: product/research (01), security (02), data-ops (05).** None of the three blocks on another. Naomi's framing depends only on the assignment text; my threat model and auth design needed the assignment text plus the one bounded coordination point with 05 (already resolved); Priya states 05 does not block on 01 or 02. Two nuances worth naming. First, Naomi regards 01 as upstream of everyone, while Priya and Renata both say 01 can run "anytime, independently" — those reconcile: nothing *hard*-blocks on 01, but her `api-connector-design-rationale.md` should be designated the single source of truth for field/endpoint shape so engineering isn't re-deriving it, which is a soft dependency (read it before finalizing, not before starting). The assignment text already specifies the question-2/3 endpoint shapes fairly concretely, so the drift risk is real but narrower than a green-field API would carry. Second, 05 is the critical-path member of this wave — it hard-blocks 03 and partially blocks 04 — so if anything in the first wave gets priority attention, it's the schema and interface contract.
2. **Engineering (03) has a split start.** Renata drew a useful distinction: 05 is a hard blocker for the DAO code, but 02 is not a blocker for her early scaffolding — project structure, Go module layout, route wiring, stub handlers can begin while the auth decision is still settling, and she needs 02 only before finalizing the middleware. So 03 starts scaffolding as soon as the first wave is underway and starts the DAO the moment 05's contract is stable — "stable" meaning unlikely to be rewritten, not fully polished. Waiting for perfection would idle the track that owns the largest deliverable.
3. **Infra (04) is last**, exactly as Theo described his own role: reviewer/consumer during planning (read the other four tracks' files, flag anything infra-shaped so it isn't silently owned elsewhere), producer only once three specific things exist — 03's service topology, config surface, and DAO driver-selection mechanism; 02's secrets inventory and never-log list; 05's migration tool/approach. Building infra design against boundaries that don't exist yet is fiction dressed as a deliverable, in Theo's words, and I don't have a better way to put it.

## 3. Where the shared planning artifact lives

Three tracks offered a view and they converge. Naomi proposed a single root-level `PLANNING.md` with one section per track, each track editing only its own. Theo wants one owner per section, no shared free-text blob five agents edit concurrently, and suggested a single index file linking to each track's own planning notes — matching the existing directory structure. Renata wants upstream decisions in the owning track's `CLAUDE.md` or a shared design doc she reads once. The common thread is one-owner-per-unit and a thin index, and I'd adopt Theo's shape over Naomi's for two reasons: first, even with an "own section" discipline, five agents live-editing one shared file in a short window is still a collision surface that a table of independent rows avoids more cleanly than prose sections do; second, and more importantly, this project already has a durable decision-record layer — each track's own `CLAUDE.md` plus its deliverable files — and duplicating design content into a second file risks the two drifting apart, which is a worse failure mode than the collision risk it's meant to solve.

**Recommendation:** a root-level `PLANNING.md`, purely as a thin cross-track coordination board — one table row per track: status, blocking-on, blocked-by, pointer to that track's planning notes, last-updated — plus, per Theo's specific ask, a single "service boundaries" row or short section that 03 owns and 04 reads, so infra isn't polling engineering's `CLAUDE.md` for updates. Short, cheap to write, cheap to skim, genuinely low collision risk because each row has exactly one writer. The actual reasoning — the "why," which is most of what LoginID is grading — stays where it already lives, in each track's own files, referenced by relative path. This keeps the artifact consistent with the root `CLAUDE.md`'s existing rule (cross-reference, don't restate) instead of introducing a second place the same content has to be kept in sync.
