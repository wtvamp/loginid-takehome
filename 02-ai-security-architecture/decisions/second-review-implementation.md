### PR #26 — LT-39, search/retrieve handlers
**Reviewer:** Ingrid Solano. **Verdict: approve except one real gap.**
Confirmed: `authorize()` ordering (in-handler, after parse, before DAO — including the ordering that prevents a 404-vs-403 existence leak); masked/full serializer split is structural, no leak path; distinct-record touch counter counts distinct records and hard-denies at 429 per the ruling; cursor is opaque, no honored offset field (minor non-blocking note: an unrecognized `offset` key is silently ignored rather than rejected).
**Real gap found:** no audit-log emission existed anywhere in this PR, despite this hand-off's own acceptance criteria requiring `reason_code` and the scope/`authorize()` failure distinction to be "logged with the audit record." The client-side indistinguishability (identical 403 bodies) was done right; there was nothing on the log side to actually distinguish them for detection.
**Disposition — closed, verified directly against current `main` (2026-09-13, lead-verified by reading `internal/api/audit.go`/`handlers.go`, not a formal hire re-review).** `AuditScopeFailure` and `AuditPolicyDenial` events are emitted at every relevant denial point in `handlers.go`, deliberately identical in shape per `audit.go`'s own comment (matching the "distinct signals for detection, identical to the caller" requirement); `reason_code` is captured and passed into the `AuditPolicyDenial` event for `profile:read:any` specifically. The gap Ingrid found is fixed.

### PR #30 — LT-40, JWT verification middleware (three rounds)
**Reviewer:** Tomasz Wrede.
**Round 1 — initial review.** Pass: algorithm confusion (his own original S8 finding) closed for real, with a genuine forged HS256-with-public-key-as-HMAC-secret test, not just the easier `alg:none` case. Findings: **HIGH** — JWKS fail-open on fetch failure had no staleness bound, serving indefinitely-stale keys with no alert on a prolonged failure run; **MEDIUM-HIGH** — unknown `kid` never forced a refetch, so a freshly-rotated key could be rejected for up to the full calendar TTL, compounding the HIGH finding in the opposite direction; **MEDIUM** — `StopgapAuthorizer`'s deny path had zero test coverage.
**Round 2 — re-check at `03181f6`.** HIGH and MEDIUM findings closed clean, verified by tests that actually drive the failure condition (`TestJWKSCache_FailsClosedPastMaxStaleness`; a real allow+deny router test for `read:own`). The MEDIUM-HIGH fix (rate-limited refetch on unknown `kid`) introduced a smaller version of the same class of gap: the refetch gate was global, not per-`kid`, so an unauthenticated caller with a garbage `kid` (no valid signature required, since `kid` lookup runs before signature verification) could occupy the shared slot and starve a legitimate rotation.
**Round 3 — re-check at `a615dfa`.** Per-`kid` keying confirmed closed by a test reproducing the exact starvation scenario. New questions (exhausting the 64-distinct-`kid` cap; what happens to the 65th `kid`) answered: the cap fails toward **rejection**, not fetch-bypass — the issuer stays protected regardless of flood size, worst case is "wait for calendar TTL." Residual downgraded HIGH → LOW, ruled done for LT-40; full closure would need pre-auth request-volume throttling ahead of this whole path, named as a general (not JWKS-specific) follow-up for 04's ingress-level rate limiting, not a bespoke mechanism in this cache.

### PR #34 — LT-51, OAuth2 client-credentials token handler + Postgres client store
**Reviewer:** Helena Marsh. **Verdict: approve, two non-blocking follow-ups.**
Confirmed by code inspection and test, not just claim: timing-parity for `invalid_client` (unknown `client_id` / no-secret-set / wrong-secret all reach one `verifySecret` call, real hash or fixed-cost `dummyHash`, no early-return branch skips it); `GrantLimiter.Allow` gates before the client store and before any comparison; revoked-client-tokens-verify-until-TTL is structurally guaranteed (`NewJWTMiddleware`'s constructor takes no `ClientStore` argument, so a per-request status recheck isn't just unwired, it's impossible). Two non-blocking findings from her own read: (1) a request with no `Authorization` header bypasses `GrantLimiter` entirely, since `sourceIP`/`Allow` are only reached after the Basic-Auth-presence check; (2) `NewInProcessGrantLimiter` is per-pod state, ruled acceptable at single-replica scope (this ruling is what `threat-model.md` Assumption 11's `Recreate`-strategy confirmation is conditioned on), should be named as a scaling caveat if the issuer Deployment is ever scaled out.
**Disposition — verified directly against current `main` (2026-09-13, lead-verified, final consistency read).** Finding (1) is fixed: `GrantLimiter.Allow` now runs before the `hasBasicAuth` check, keyed on `sourceIP` (available regardless of whether any credential was sent), with the ordering explained in the code's own comment — a no-Authorization-header flood no longer bypasses the limiter. Finding (2) (`NewInProcessGrantLimiter`'s per-pod state) remains an accepted-not-fixed residual, correctly so — it's the condition `threat-model.md` Assumption 11's `Recreate`-strategy ruling depends on, not a defect to close; see the residuals table below.

### PR #36 — LT-51 infra half: issuer database, third migration invocation, QA-client runbook
**Reviewed in part by Helena Marsh** (replica-count finding, cited in the PR body and `threat-model.md` Assumption 11): `api-service-issuer` dropped from 2 replicas to 1, since `GrantLimiter` tracks failed-attempt state in-process, per-pod — two replicas behind round-robin would silently halve the effective threshold. Correctly implemented in the manifest (`replicas: 1`, with the reasoning stated inline in the YAML comment).
**Remainder (initdb roles/grants, NetworkPolicy, migration ordering, QA-client seeding runbook) — no formal hire review; short direct check by the lead (2026-09-13) rather than left unreviewed.** Findings: separate `issuer` database (not just a schema) genuinely makes a cross-database join to `user_profile`/`user_credential` structurally impossible, matching F8's reasoning; `issuer_migrator`/`issuer_runtime` role split mirrors the main database's existing migrator/runtime least-privilege pattern (migrator gets `CREATEDB`/schema-create, runtime gets `CONNECT` plus default-privilege-granted CRUD only); NetworkPolicy ingress correctly adds `api-service-issuer`'s pod selector, nothing broader; the issuer DB's DSNs carry `sslmode=require`, consistent with Assumption 9; the QA-client bootstrap runbook seeds out-of-band as required (never through a migration, never through the CI-applied manifest set, secret never printed or committed) and verifies the insert without re-exposing the hash. **One known, transparently-documented gap, not newly introduced by this PR:** `docker-entrypoint-initdb.d` scripts only run on first Postgres init, so the issuer database/roles were created by hand against the already-running instance rather than via the ConfigMap script, which now silently doesn't match live state if re-read naively — the PR's own comments name this drift risk and the long-term fix (an idempotent provisioning Job re-run on every deploy) rather than hiding it. **No new security gap found in this remainder.**

### PR #39 — LT-51 follow-up, PHC-string fix + verify-then-rehash + goose fix
**Reviewer:** Helena Marsh. **Verdict: approve, one gap to close before merge.**
Confirmed: PHC format is genuine and round-trip-parsed, not assumed (rejects malformed trailing-garbage cases); verify-then-rehash runs in-request with fail-open semantics on the storage write (a rehash-persist failure doesn't hold the grant hostage); pre-existing (old-encoding) hashes hard-break rather than silently degrade, documented in the runbook. **Gap:** the rehash-persist-failure path had no test asserting the token response still succeeds — flagged as needing a test before merge. **New finding, recorded as an accepted risk (`handoff-03-auth.md` v8, not a blocker):** self-describing per-row cost parameters create a narrow timing difference between an unknown client and a known client still on a stale cost profile — didn't exist before this PR, self-closes as clients rehash, accepted given the small client population, revisit if that population or cost-change cadence grows.
**Disposition — closed, verified directly against current `main` (2026-09-13, lead-verified, not a formal hire re-review).** `TestNewTokenHandler_RehashPersistFails_GrantStillSucceeds` exists, exercises `updateHashErr`, and asserts the 200 still issues while the stored hash remains unchanged (correctly not silently claiming a rehash succeeded when it didn't) — the exact gap Helena named is closed, explicitly citing her review in the test's own comment.

### PR #40 — LT-41, `idp-connector` `/auth`/`/identity` (three rounds)
**Reviewer:** Tomasz Wrede.
**Round 1 — initial review.** Pass: fresh-`Authorization`-header-per-request is structural (fresh `*http.Request` per call, nothing shared at client/transport level for concurrency to corrupt — his own original S3 finding, now verified in real code); the ~100ms timing floor matches `connector-security.md` §4's accepted-residual framing exactly, applied uniformly, not over-claimed. **Real gap:** `GrantLimiter` reuse for vendor-call rate limiting was missing the "per identity attempted" dimension `connector-security.md`'s own attack-tree row 5 already specified — keyed only on calling internal client and source IP, effectively one shared bucket regardless of which stolen identity was being tried.
**Round 2 — re-check at `5d67789`.** Original finding closed clean (`HMAC-SHA256(caller sub, attempted identity)` keying, both named attack scenarios directly tested). New finding: the 10,000-key bounded cardinality degraded toward **allowance** — past the cap, a brand-new identity got zero per-identity backoff, recreating most of the original weakness for an attacker willing to pre-fill the table (cheap: no valid vendor credential needed, rejected attempts count).
**Round 3 — re-check at `38a2bdd`.** Overflow-bucket fix (identities needing a new slot past capacity land in one shared, aggressive limiter instead of bypassing limiting) confirmed to close the pre-fill-then-attack scenario genuinely, by mechanics and test. New structural note, recorded as an accepted risk (`connector-security.md`, not a blocker): the shared overflow bucket resets entirely on any single success recorded through it, so one legitimate overflow success clears an unrelated attacker's accumulating overflow failures — accepted conditional on overflow staying the rare case, with a named revisit trigger (overflow-bucket hit rate under real traffic, a metric 04's observability work should expose but doesn't yet).
