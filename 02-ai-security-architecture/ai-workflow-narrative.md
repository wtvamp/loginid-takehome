# AI Tooling & Workflow Narrative

Owner: Marcus Ilori (`02-ai-security-architecture`). This is the full answer to LoginID's explicit ask ("describe any tool, framework, or AI used") — other tracks note their own AI usage briefly and point here for depth, per `../CLAUDE.md`.

This document states what was done, distinguishes what's independently documented by Anthropic from what this project composed on its own, and is deliberately precise about that boundary rather than overclaiming an official pattern that doesn't exist. Full source-by-source detail lives in `research-claude-architecture-best-practices.md`; this document is the applied summary a reviewer can read without the research doc.

## Tool

**Claude Code**, Anthropic's agentic CLI. Chosen because the deliverable itself is an exercise in demonstrating AI-architect judgment — using the tool that is itself the subject of the "how did you use AI" question, rather than a general-purpose chat interface, lets the workflow be inspected as part of the submission.

## Structure: a root brief plus five track-scoped briefs

The repository is organized as one root `CLAUDE.md` (the assignment text, track boundaries, cross-track working principles) plus five track directories, each with its own `CLAUDE.md` scoped to a distinct slice of the problem (product/industry framing, this track's security architecture, engineering delivery, infra/devops, data ops). Each track file is written to be self-contained enough that a fresh agent with no other conversation history can pick it up correctly given only that file plus the root file.

**What this composes, precisely:**

1. **The `CLAUDE.md` mechanism itself** is Anthropic's own, documented at https://code.claude.com/docs/en/memory — auto-loaded at session start, meant to be treated as living documentation, kept short and specific.
2. **The decision to fan that mechanism out per-directory, with a stable root file for cross-cutting state**, is this project's own application of a general principle Anthropic documents separately in "Effective context engineering for AI agents" (https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents): structured notes persisted to files outside the live context window, retrieved just-in-time rather than all loaded upfront, so a track's subagent carries only the ~1-2 files it actually needs rather than the whole project's accumulated context.

I'm stating this distinction explicitly because it matters to how this narrative should be read: Anthropic has not published a named "root CLAUDE.md + per-directory CLAUDE.md" pattern, and claiming they had would be exactly the kind of unsupported assertion this track's whole discipline argues against. What's true and defensible is narrower and still worth the credit — this is a reasonable, motivated composition of two things Anthropic documented separately.

## Orchestration: scoped subagents per track, not one long single-context session

Each track is intended to be worked by an agent (in practice here, a persona-bearing teammate agent per track — see each track's `profiles/` entry) that reads the root file plus its own track file and works within that scope, rather than one agent holding all five tracks' context simultaneously and switching between them. This follows the orchestrator-worker pattern Anthropic describes in "How we built our multi-agent research system" (https://www.anthropic.com/engineering/multi-agent-research-system): a coordinating layer decomposes work into distinct-objective, distinct-tool-scope units; each unit works its own trajectory; only condensed results cross back, not raw exploration. Anthropic's own internal figure for a subagent-to-coordinator handoff is roughly 1,000-2,000 tokens of distilled findings — the discipline this project applies at track boundaries is the same: a track's `CLAUDE.md` plus its finished deliverable files (this document included) are what another track reads, never a transcript of how those conclusions were reached.

Concretely for this track: the threat model, the API auth/authz design, and the connector security design (`threat-model.md`, `api-auth-design.md`, `connector-security.md`) are the condensed artifacts `03-engineering-delivery` needs to implement against. It should read those files, not need this track's reasoning replayed turn-by-turn.

## The org layer: personas, patterns, and debates (added after Phase 2 execution)

The structure above (root brief, five track briefs, scoped subagents) is the skeleton. What actually ran inside it, once Warren authorized hiring, was a second layer this project built on top of Anthropic's documented patterns rather than found in them: each of the five track leads hired a small sub-team of persona-bearing agents — this track hired four (Tomasz Wrede, an Adversary; Helena Marsh, a Principled Architect; Felix Adebayo, a Tinkerer and this lead's deliberate temperament opposite; Ingrid Solano, a Designated Skeptic) — and ran a small catalog of named orchestration patterns (red team/blue team, adversarial pair, structured written debate, independent second review, rotating devil's advocate, three hats) against specific design decisions, each ending in a durable decision file under `decisions/`. **This entire layer — the personas, the variance rules in `../CASTING.md`, the pattern catalog, the rule that every decision artifact records its own model/turn-count footer — is this project's own design, not an Anthropic-documented technique.** It's a deliberate, load-bearing extension built on top of the orchestrator-worker pattern (§"Orchestration" above), motivated by a specific risk Anthropic's own writing doesn't have to worry about but a five-lead org does: five track leads (and the PM) starting from the same base model land in the same temperament quadrant by default, and agreement between agents who all think alike is not evidence of a good decision.

### What the pattern catalog actually bought, honestly measured

This is not a claim that multi-agent debate produces better designs than a single strong session **in general** — that claim was itself put to a structured written debate in this track (S5, `decisions/ai-workflow-claim-debate.md`) and the ruling is reproduced faithfully below, including the position that lost ground. What can be stated and evidenced:

- **S3 (red/blue, connector token lifecycle):** Tomasz's red seat produced five ranked attack leaves, each shaped as "add a control" (encrypt the cache harder, bind the token, rate-limit more). Felix's alternatives seat — a role that exists specifically to ask "does the thing being protected need to exist" rather than "is the control sufficient" — proposed deleting two of those leaves outright by removing the token cache entirely (fetch-per-call instead of cache-with-a-TTL), rather than hardening it. That's a concrete design change this document can point to that would not have existed without a seat whose brief was structurally different from the seat before it. Tomasz's own rebuttal turn on the remaining three leaves then surfaced a *new* attack variant on leaf 1 (connection reuse attaching one request's token to another, unrelated to the cache Felix had just deleted) that Helena's blue answer hadn't addressed, closed with a new control; conceded leaf 2 cleanly with no new finding; and tightened leaf 3's accepted-risk boundary. **Corrected tally (cross-track consistency pass, F39 — the earlier count of "2 hits, 1 tightening, 2 null" undercounted the rebuttal turn's own catch): 2 leaves deleted by design change, 1 new variant surfaced and closed by the rebuttal turn, 1 boundary tightened, 1 null (leaf 2's clean concession).** The correction matters for exactly the reason this section exists — a narrative reporting its own evidence has to get the evidence right, including when getting it right makes the pattern's case stronger, not weaker.
- **S8 (independent second review, three security-graded documents) — the most valuable process evidence in this track, worth stating as a general lesson rather than just an incident report.** `PLAN.md`'s original static roster assigned Helena to review both `threat-model.md` and `api-auth-design.md`. By the time S8 actually ran, that assignment was stale: Helena had since become S4's Proposer and authored the very scope-vocabulary and policy content in `api-auth-design.md` that S8 was meant to check, and had also been S3's blue seat authoring the controls in `connector-security.md`. Reviewing either would have been an author re-reviewing their own work under the label "independent review." **The lesson: independence is a property that has to be checked at the moment a review actually runs, not a role assigned once at planning time and trusted to still hold** — a five-track org where the same small hire roster accumulates authorship across successive debates will decay its own independence guarantees exactly this way if nobody re-checks before each review. Caught here before running (Helena reassigned to `threat-model.md` only, a document she never touched; Tomasz — clean, no Phase 2 involvement in this document — took `api-auth-design.md`; Ingrid kept `connector-security.md`, unaffected), not after.

  With independence actually verified, the reviews earned their cost. **The concrete example worth leading with:** Tomasz found that the decomposition-resistant rate-limit counter S4 had just finished designing — specifically as Ingrid's own fix to her objection 4 in that same debate — was a silent no-op for `profile:read:any`, the scope with the broadest blast radius, because its exemption clause ("without a fresh `reason_code`") was unconditionally satisfied by a scope that already requires a `reason_code` on every call by design. Neither Helena (who wrote the fix) nor Ingrid (whose objection it answered) caught this, because both were reasoning inside "does this satisfy the objection as stated" — the same self-referential blind spot independent review exists to catch, now demonstrated on the review pattern's own prior output, one debate later. Ingrid's separate finding on `connector-security.md` — that a document entirely about protecting a vendor token's custody said nothing about who may call the connector holding it, or what the token authorizes once used — is a different class of question from the one the S3 red/blue run spent its effort on, for the same underlying reason: every S3 participant was already inside the "protect the token" frame. **Corrected tally (cross-track consistency pass, F40 — the earlier "4+4+2=10" undercounted `threat-model.md`'s own list of five items): 11 items across 3 documents — 10 defects plus 1 completeness note — 0 declined, 0 null reviews.** Both numbers belong in this document, not just the ones favorable to the claim.
- **Theo's Newcomer cold-read of `handoff-04-secrets.md` (04's track, not this one, but this track's document):** two real gaps (an undefined component's feature status, a trust-boundary reference that required reading a second track's file to parse) that survived this document's own author's review, caught by a reader with zero authorial investment. **2 hits — one review, two findings** (corrected, cross-track consistency pass F41 — this section previously said "1 hit" for an event it had itself just described as "two real gaps").

### What the S5 debate actually settled — stated plainly, including the losing position

Felix argued (Position A) that this evidence shows the pattern produces better designs than a single strong session would. Ingrid argued (Position B) that two data points, both produced by roles this project built specifically to produce exactly this kind of catch, are not evidence of a general effect — a single session working from an explicit checklist ("can this control's leaf be deleted instead," "get one cold read before shipping") could plausibly produce the same catches without four personas and a debate protocol, and nobody has run or estimated that comparison. The ruling (`decisions/ai-workflow-claim-debate.md`) went **against** the general claim and **for** a narrower one: the defensible statement is a structural/mechanism argument, not a statistical one — a seat holding a genuinely different optimization target, or a reader with no authorial stake, can surface a class of error that self-review structurally tends not to, because self-review interrogates the answer it already committed to rather than the frame that produced the question. That is not the same as asserting multi-agent design beats solo design as a population-level effect, and this document does not make that broader claim. Ingrid's insistence that null results (the S3 leaf conceded clean, S8's near-zero null rate by contrast) be counted in the same tally as hits was adopted outright and is reflected in the tallies above, not just the successes.

### The external operator agent: named, never contacted

A real external agent exists in this environment: an operator, human or automated, holding cluster-admin or namespace-admin rights on 04's design-only Kubernetes lab cluster, capable of applying manifests to it. This track's threat model names that operator as a privileged actor and trust boundary (`threat-model.md`, Assumption 6) — not a hypothetical, a real agent this project could technically reach. **It was deliberately kept out of scope for the entire duration of this project: never contacted, nothing deployed, no manifest applied.** This is stated here because an AI-workflow narrative that documents every agent this project *did* use would be incomplete, arguably misleading by omission, if it didn't also state plainly which real agent in the environment it declined to use and why — the boundary was a design decision (design-only reference target), not an oversight or a capability gap.

## What was AI-generated vs. human-directed

- **Human-directed**: the assignment itself (LoginID's), the five-track decomposition and ownership boundaries (the root `CLAUDE.md`), and every judgment call in this document and its siblings about *which* security mechanism to choose and why (e.g., OAuth2 client-credentials over static API keys in `api-auth-design.md` — a reasoned choice, not a default).
- **AI-generated, human-directed content**: the research pass that produced `research-claude-architecture-best-practices.md`, and the drafting of this narrative, the threat model, and the design documents themselves, all produced within this track's scope by an agent operating under this track's `CLAUDE.md` and persona brief.
- **Explicitly not claimed**: that any of this constitutes a validated, "certified" methodology. The research doc's §6 covers Anthropic's Claude Certification Program by name and is careful that its existence is not evidence this project's specific techniques are exam-validated — that would be a citation used to imply authority it doesn't carry.

## Why this discipline matters for this specific track
