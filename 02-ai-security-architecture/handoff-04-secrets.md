## Assumptions this hand-off makes

1. Deployment target is 04's **real Kubernetes cluster, reachable via a plain nginx Ingress + cert-manager on the cluster's shared LoadBalancer** (DNS CNAME to `uplifttech.ddns.net`, public at `https://loginid-takehome.uplifttech.org` — no tunnel; Warren's implementation go-ahead, 2026-09-12, updated from a design-only reference). **Delivery mechanism (updated 2026-09-13, LT-46): the Vault Agent Injector, not raw Kubernetes `Secret` mounts, for every application-level secret in the inventory below** — a Vault Agent sidecar, added via pod annotation, authenticates to Vault using the pod's own Kubernetes ServiceAccount token (Vault's Kubernetes auth method) and renders each secret to a file on an in-memory (`emptyDir`, `medium: Memory`) volume shared with the application container; nothing application-level is written to a Kubernetes `Secret` object, and therefore nothing application-level reaches etcd's base64-not-encrypted-by-default storage at all — this closes the etcd requirement below by removing the object from etcd entirely, not by enabling etcd encryption at rest. Amber (Vault operator) provisions the KV paths, Vault policies, and Kubernetes-auth roles that make this work; names only are visible in any transcript, never values. Every requirement below is written so it still holds regardless of mechanism; this is the mechanism 04 actually builds to now. **The repository is now public** (`https://github.com/wtvamp/loginid-takehome`) — every requirement in this document that says "never in source or committed config" is now categorical, with no private-repo safety net.

**`postgres-superuser` is Vault-delivered after all — v3's reasoning here was wrong, corrected rather than quietly patched over.** v3 argued a Vault Agent sidecar "doesn't help a database's own first-init bootstrap" because it's a pattern for pods already running and authenticating to Vault themselves. That's true of the *sidecar* pattern specifically, but conflates two different things: whether *Vault itself* exists yet (it does — an independent HA Vault, already running on this cluster, not something Postgres hosts or depends on existing) versus whether *this specific pod* has started yet. Vault Agent supports an **init-container** mode for exactly this shape of problem: it runs to completion *before* the main container starts, authenticates via the pod's own ServiceAccount token the same as the sidecar pattern, and renders the credential to a shared volume the main container then reads at its own startup — Postgres's official image already supports `POSTGRES_PASSWORD_FILE` (a file path) as an alternative to `POSTGRES_PASSWORD` (a literal value), so the init script reading from a Vault-rendered file instead of a `secretKeyRef` env var is a small, well-supported change, not a redesign. There was no actual chicken-and-egg here once Vault's own existence is independent of Postgres's — v3 treated "the database is bootstrapping" and "Vault needs bootstrapping" as the same problem when they aren't.

**Postgres gets its own Vault role, `loginid-takehome-postgres`**, reading `postgres-superuser` plus the four existing DB-credential paths (`db-migrator-credential`, `db-runtime-credential`, `issuer-db-migrator-credential`, `issuer-db-runtime-credential`) — five paths, the widest of any role in this system, since the Postgres StatefulSet's init script is what seeds all of them. This is the role deserving the closest look in Helena's policy review, precisely because it's the widest.

**Three named exceptions remain Kubernetes Secrets, not Vault-delivered:**

- **`postgres-server-tls`** — cert-manager's own `Certificate`/`Secret` mechanism (`threat-model.md` Assumption 9), consumed directly by the Postgres StatefulSet's TLS startup args. cert-manager already *is* a secure, automated, rotation-aware delivery mechanism purpose-built for exactly this (a server needing a TLS keypair) — routing it through Vault instead would duplicate a solved problem, not close a gap.
- **`loginid-takehome-tls`** — same reasoning, one level up: the public Ingress's cert-manager-issued certificate, consumed by the Ingress controller directly. Same native, already-secure mechanism; no benefit to re-routing through Vault.
- **The ARC GitHub App auth credential** (in the runner namespace, not this application's namespace) — a platform/CI-infrastructure secret belonging to the runner controller itself, not to `api-service`/`idp-connector`/the issuer. It authenticates GitHub's App to provision self-hosted runners; it's outside this application's own trust boundary and namespace, and this hand-off's scope is this application's secrets, not the CI platform's own.

The common thread across all three: each is either an already-native, already-secure Kubernetes-integrated mechanism (cert-manager) that Vault would only duplicate, or a platform-level secret outside this application's own namespace/trust boundary — not an ad hoc carve-out, and not "hasn't gotten to it yet."

**A fourth item, `qa-client-credential`, is a different category from the three above and stays a Kubernetes Secret for a different reason (ruled 2026-09-13, jointly with Theo Bergman): it's an ops/review-tooling artifact, not an application secret, and structurally cannot use the Vault Agent Injector pattern at all.** The Vault Agent mechanism delivers a secret into a *running pod's filesystem at startup* — `qa-client-credential` is never consumed that way; its only consumption pattern is a human running `kubectl get secret qa-client-credential -o jsonpath=...` directly to manually mint a review token, with no pod in between. There's nothing to inject into. Moving it to Vault would only relocate where a human types a fetch command (`kubectl` → `vault` CLI); it wouldn't close any actual exposure, since the exposure surface either way is "whoever can authenticate as a cluster operator." **Least-privilege confirmation, not just deferred:** checked against `deploy/rbac.yaml` directly — the CI deployer's Role has no `secrets` verbs at all, and no application ServiceAccount (api-service, issuer, idp-connector) has any Secrets-API grant either, since Vault handles their application secrets now. `qa-client-credential`'s actual access boundary is therefore "human operators with direct cluster access," which is Assumption 7's existing operator trust boundary — not a new, unstated exposure this migration should have closed and didn't.
2. Service topology is 03's published boundary (`../PLANNING.md`, Service boundaries): two binaries, `cmd/api-service` (Q1 DAO + Q2 REST API) and `cmd/idp-connector` (Q3), env-var configuration only. Variable names below are 03's; two are marked as pending this track's final scheme. **The token-issuing authorization-server function is a mode of `api-service`, not a third binary** — this take-home's scope doesn't justify a standalone authz server, and 03 has published no third `cmd/` entrypoint. **Corrected by the cross-track consistency pass (F13):** "a mode of the same binary" is not "the same Kubernetes Deployment," and the earlier text here was wrong to imply RBAC alone separates them — a Kubernetes Role restricting `get` on a Secret has no effect on a volume already mounted into a container, so if `api-service`'s one Deployment mounted the signing key, every replica (verification path included) would have it on disk regardless of RBAC. **The fix: the issuer runs as a second Deployment of the same `api-service` image**, selected by an environment variable 03 adds to the config surface (e.g. `APP_MODE=issuer` vs. the default, consistent with the surface's env-var-only, no-flags rule), with **its own ServiceAccount that alone mounts the signing-key Secret** (row #2) — the `api-service` Deployment serving verification/search mounts nothing from row #2. This is a request into 03's Deployment/mode surface, not a unilateral change on my part; flag to me if the mode-selection mechanism needs to differ.
3. An **external operator agent** — a human or automated actor outside this project, holding cluster-admin or namespace-admin rights on 04's real lab cluster, who applies Kubernetes manifests to it — is a privileged actor outside this service: anyone who can apply a manifest can read any Secret it mounts. Consequence for 04: manifests reference Secrets by name and never carry values; values are set out-of-band. This is a named trust boundary in `threat-model.md` Assumption 7, not a silent assumption; nothing further about who that operator is needs to be re-derived from 04's own files to act on this hand-off. As of this update, 04 has not yet made contact with that operator or deployed anything — `threat-model.md` carries the dated status.
4. **Updated 2026-09-12:** with Warren's implementation go-ahead, 04's build stories will deploy to and contact the operator of the real cluster named in Assumption 1 — this is no longer a hypothetical the document describes in the abstract. As of this update, that contact hasn't happened yet; `threat-model.md` Assumption 7 carries the current, dated status and gets updated the moment it changes.

## Kubernetes-specific requirements (04 implements; 02 sets)

- **Secrets at rest in etcd are base64, not encrypted, by default (updated v3.1): closed by removal, not by enabling etcd encryption, for all but four remaining Kubernetes Secrets.** Every application-level secret in this inventory, `postgres-superuser` included as of v3.1, is now Vault-delivered and never becomes a Kubernetes `Secret` object at all — there's nothing application-level in etcd's base64 storage to encrypt. Four items remain real Kubernetes Secrets and are still subject to etcd's default plaintext-at-rest storage: `postgres-server-tls`, `loginid-takehome-tls`, the ARC GitHub App auth credential (runner namespace), and `qa-client-credential` (ops tooling, row above) — if that residual matters enough to close for those four specifically, enabling etcd encryption at rest is still the mechanism, unchanged from v2; this track isn't aware of a reason it's been done, so it's named as still open for those four if 04 wants to close it, rather than assumed solved by the Vault migration.
- **Each Vault Kubernetes-auth role reads exactly the KV paths its own workload's secrets rows name above, nothing else — five roles, named explicitly (gap in this hand-off caught by Helena Marsh's review, fixed here):**
  1. `loginid-takehome-api-service` — row #1 (`db-runtime-credential`, not migrator) and row #10 (its own client credential toward the issuer). Does **not** hold row #4's credential (`issuer-db-runtime-credential`) — that path belongs to the issuer role only.
  2. `loginid-takehome-api-service-issuer` — row #2 only (a distinct role from `api-service`'s, since it's a separate Deployment/ServiceAccount per F13). Does **not** hold `db-runtime-credential` — the issuer has no legitimate reason to touch `user_profile`'s database.
  3. `loginid-takehome-idp-connector` — row #5, and **empty until a later story (LT-33 or after) actually gives it a secret to hold** — provisioning a Vault role with no paths granted yet, rather than skipping role creation until needed, is the right default: adding its first real secret later is a policy *addition* to an already-narrow role, not a first-time policy design done under time pressure.
  4. `loginid-takehome-postgres` — the five paths in row #11 (superuser plus both migrator and both runtime DB credentials), the widest role in this system, deserving the closest look — width here is a function of the StatefulSet's `initdb` script being the one component responsible for seeding all five, not an over-grant.
  5. `loginid-takehome-db-migrate` — the two migrator credentials only (`db-migrator-credential`, `issuer-db-migrator-credential`); correctly excludes superuser and both runtime credentials, since the migration Job never needs application-level read/write access, only DDL-provisioning access.

  This is the review this track (Helena Marsh) runs against all five Vault policies once Amber/Theo produce them, the postgres role first given its width. The principle to check against is exactly this one-role-one-workload's-own-paths shape, not a broader "seems reasonable" pass. **Denial matrix must include `api-service`'s role denied the issuer's role specifically** (caught by Helena's review as the one case the reported matrix omitted) — that overlap is the exact thing the F13 Deployment split exists to prevent, and it's the single most relevant test for this system, not an optional addition to the other three (default-denied-all-five, `idp-connector`-denied-postgres, cross-namespace-same-name-denied).
- **New trust boundary, named explicitly: Vault's Kubernetes auth method trusts the cluster API server's `TokenReview` result.** A Vault role granting `api-service` (or any workload) access is only as trustworthy as the guarantee that the ServiceAccount token presented to Vault actually belongs to the pod claiming it — Vault's Kubernetes auth backend validates this by calling back to the API server's `TokenReview` API, so a compromise of the API server's ability to answer that honestly (not a scenario this take-home's threat model otherwise reaches) would undermine every Vault-delivered secret at once, not just one workload's. This is a boundary worth naming rather than treating Vault as an independent root of trust from Kubernetes itself — it isn't; it's built on top of the same cluster trust this design already relies on elsewhere (the CI deployer's RBAC, the operator's manifest-apply rights).
- **The Vault Agent sidecar's rendered secret files live on an in-memory volume (`emptyDir`, `medium: Memory`), never a disk-backed volume.** This matches the existing "runtime-injected as a file" requirement's intent (never written to a persistent disk an attacker with node access could read after the pod is gone) more strictly than a plain Kubernetes Secret volume mount already did, since `tmpfs` content doesn't survive to swap or a node's disk in the way a written file might depending on the node's storage backend — a strict improvement over the mechanism it replaces, not a new requirement being traded against something else.
- **RBAC:** no service account may `get`/`list` Secrets it does not mount. The operator agent's apply rights are a documented trust boundary, not a hole to close in this take-home — but the design should note that its scope could be narrowed to a namespace.
- **Manifests carry references, never values.** Any manifest in the repository contains Secret *names*; values are provided out-of-band. This is what keeps assumption 3 honest.
- **File delivery, not env vars, is now the default rather than a preference** — Vault Agent renders every application-level secret to a file on the in-memory volume, so this is what the mechanism does, not a choice to remember for each row. #1 (`DB_DSN`) is the one exception still transitioning, per 03's `_FILE` convention adoption.
- **No secret in an image layer, build arg, or CI log.** CI redaction is 04's mechanism; the requirement is that a build log can be published without exposing anything in this table.
- **Audit/access logs (the output of the never-log list below) are readable only by an incident-review role, distinct from and narrower than general operator access.** `sub`, scope, record id, and timestamp are enough on their own to reconstruct who looked up whom — that log stream needs its own read restriction, separate from whichever service account can `get`/`list` the Secrets in this table. Mechanism (log-pipeline RBAC, a separate log sink with its own access control, etc.) is 04's call; the requirement is that "can read Secrets" and "can read the audit trail" are not the same grant.
- **The CI deploy ServiceAccount must not be able to read row #2's JWT signing key, whatever form that takes under the current delivery mechanism** — found by Tobias Lindqvist against the Kubernetes-Secret-era design, and the *principle* carries forward unchanged even though row #2 is no longer a Kubernetes Secret under v3: a namespace-scoped Role with broad Secret verbs (Kubernetes) or a Vault policy with broad KV read (Vault) is the same class of straight-line path from "CI runner compromised" to "mint arbitrary tokens." Under Vault delivery, this becomes: the CI deployer's own Kubernetes ServiceAccount must have no Vault Kubernetes-auth role bound to it that grants any path under this KV secret's location — the deployer applies manifests (including the pod annotation that triggers Vault Agent injection for other workloads), but is not itself one of the workloads Vault authenticates as, and has no policy of its own reading this path. Same two-part discipline as before, restated for the new mechanism: (1) the secret is provisioned into Vault out-of-band, never through the CI-managed manifest set; (2) least-privilege Vault policy, scoped per-role (the review point above) — no policy grants the CI deployer's own identity a path to this or any other application secret. If the deployer's Kubernetes ServiceAccount could still theoretically authenticate to Vault under some role, that role must not carry this path.

## Never-log list (applies to every component, every environment, every log level, including error paths and stack traces)

1. End-user vendor password (#9).
2. Vendor `access_token` (#6) — and any `Authorization` header value, inbound or outbound, in full.
3. PII field values from `user_profile` or from `/identity` responses: name, phone, `street_address`, `locality`, `region`, `postal_code`, `country`. Log the *fact* of access — caller `sub`, scope used, opaque record id, timestamp, status — never the values.
4. Raw vendor error response bodies (they can echo submitted PII or partial credentials). Log status code and vendor error code only.
5. JWT signing private key (#2) and any JWT in full — log `sub`, `aud`, `exp`, and `kid` if needed, never the token.
6. API caller `client_secret`s (#4), in plaintext or hashed.
7. `DB_DSN` (#1) or any connection string containing credentials.
8. Full request bodies of `POST /auth` and `POST /identity` — both contain items above by construction.
9. Search query parameters containing a name or phone fragment (`api-auth-design.md`, hardening) — they are PII; redact or hash before any access log, including proxy and ingress logs 04 controls.
10. **Database driver error messages and `DETAIL`/`Key (...)=(...)` text** (added by the cross-track consistency pass, F50 — the most probable PII-to-log path in the system and previously named by no item on this list). A Postgres CHECK or unique-constraint violation on a `user_profile`/`user_credential` write echoes the failing row's column values, or the offending key value, in its error `DETAIL`. Log SQLSTATE/result code and constraint name only — the sanitization happens in 03's error-translation layer (`error-semantics.md`) before the error is wrapped for logging, not after.
11. **Username** (added by the same pass, F50) — typically an email address, and previously ungoverned by this list even though it can appear in `ErrDuplicateUsername` driver detail (item 10) or in a log line correlating a failed login. Treat it with the same discipline as a PII field value (item 3): log a hash or an opaque identifier for correlation, never the raw value.

## What 04 does not decide (already decided upstream)
