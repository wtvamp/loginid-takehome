## Assumptions this hand-off makes

1. Deployment target is 04's **real Kubernetes cluster, reachable via a plain nginx Ingress + cert-manager on the cluster's shared LoadBalancer** (DNS CNAME to `uplifttech.ddns.net`, public at `https://loginid-takehome.uplifttech.org` — no tunnel; Warren's implementation go-ahead, 2026-09-12, updated from a design-only reference). Delivery mechanism is therefore Kubernetes-native `Secret` objects unless 04 chooses an external store; every requirement below is written so it still holds if the mechanism changes. **The repository is now public** (`https://github.com/wtvamp/loginid-takehome`) — every requirement in this document that says "never in source or committed config" is now categorical, with no private-repo safety net.
2. Service topology is 03's published boundary (`../PLANNING.md`, Service boundaries): two binaries, `cmd/api-service` (Q1 DAO + Q2 REST API) and `cmd/idp-connector` (Q3), env-var configuration only. Variable names below are 03's; two are marked as pending this track's final scheme. **The token-issuing authorization-server function is a mode of `api-service`, not a third binary** — this take-home's scope doesn't justify a standalone authz server, and 03 has published no third `cmd/` entrypoint. **Corrected by the cross-track consistency pass (F13):** "a mode of the same binary" is not "the same Kubernetes Deployment," and the earlier text here was wrong to imply RBAC alone separates them — a Kubernetes Role restricting `get` on a Secret has no effect on a volume already mounted into a container, so if `api-service`'s one Deployment mounted the signing key, every replica (verification path included) would have it on disk regardless of RBAC. **The fix: the issuer runs as a second Deployment of the same `api-service` image**, selected by an environment variable 03 adds to the config surface (e.g. `APP_MODE=issuer` vs. the default, consistent with the surface's env-var-only, no-flags rule), with **its own ServiceAccount that alone mounts the signing-key Secret** (row #2) — the `api-service` Deployment serving verification/search mounts nothing from row #2. This is a request into 03's Deployment/mode surface, not a unilateral change on my part; flag to me if the mode-selection mechanism needs to differ.
3. An **external operator agent** — a human or automated actor outside this project, holding cluster-admin or namespace-admin rights on 04's real lab cluster, who applies Kubernetes manifests to it — is a privileged actor outside this service: anyone who can apply a manifest can read any Secret it mounts. Consequence for 04: manifests reference Secrets by name and never carry values; values are set out-of-band. This is a named trust boundary in `threat-model.md` Assumption 7, not a silent assumption; nothing further about who that operator is needs to be re-derived from 04's own files to act on this hand-off. As of this update, 04 has not yet made contact with that operator or deployed anything — `threat-model.md` carries the dated status.
4. **Updated 2026-09-12:** with Warren's implementation go-ahead, 04's build stories will deploy to and contact the operator of the real cluster named in Assumption 1 — this is no longer a hypothetical the document describes in the abstract. As of this update, that contact hasn't happened yet; `threat-model.md` Assumption 7 carries the current, dated status and gets updated the moment it changes.

## Kubernetes-specific requirements (04 implements; 02 sets)

- **Secrets at rest in etcd are base64, not encrypted, by default.** Either enable encryption at rest for the `Secret` resource type, or source values from an external store that never writes plaintext to etcd. One or the other; the design must say which.
- **RBAC:** no service account may `get`/`list` Secrets it does not mount. The operator agent's apply rights are a documented trust boundary, not a hole to close in this take-home — but the design should note that its scope could be narrowed to a namespace.
- **Manifests carry references, never values.** Any manifest in the repository contains Secret *names*; values are provided out-of-band. This is what keeps assumption 3 honest.
- **Prefer file mounts over env vars** for #2, #5, #7, #8. #1 is env-var only because 03's config surface is env-var only; if 03 accepts a `_FILE` suffix convention, move it.
- **No secret in an image layer, build arg, or CI log.** CI redaction is 04's mechanism; the requirement is that a build log can be published without exposing anything in this table.
- **Audit/access logs (the output of the never-log list below) are readable only by an incident-review role, distinct from and narrower than general operator access.** `sub`, scope, record id, and timestamp are enough on their own to reconstruct who looked up whom — that log stream needs its own read restriction, separate from whichever service account can `get`/`list` the Secrets in this table. Mechanism (log-pipeline RBAC, a separate log sink with its own access control, etc.) is 04's call; the requirement is that "can read Secrets" and "can read the audit trail" are not the same grant.
- **The CI deploy ServiceAccount (`loginid-takehome-deployer`) must not be able to read row #2's JWT signing-key Secret, even though it holds Secret verbs to manage the app's other Secrets in the same namespace** — found by Tobias Lindqvist: a namespace-scoped Role with broad Secret verbs is a straight-line path from "CI runner compromised" (a real risk for a repo-scoped ARC runner with GitHub App auth in a public repo) to "mint arbitrary tokens." Two controls required together, not either/or: (1) **the signing-key Secret is created out-of-band**, in a one-time `bootstrap.yaml` applied outside the CI-managed manifest set (by a human or a separate, more privileged process) — so under normal operation CI never needs a verb on it at all; (2) **the deployer Role's `secrets` verbs are scoped with `resourceNames`** to an explicit allow-list of the app Secrets CI is meant to manage, which never includes the signing-key Secret's name. (1) alone is operational hygiene, not an enforced boundary — a broad, unscoped Role verb still reaches any Secret that exists in the namespace regardless of who created it; (2) is the actual RBAC control, and is the one to name as the enforcement site in a review. If maintaining a `resourceNames` allow-list becomes unworkable as the Secret count grows, the fallback is putting the signing-key Secret in a separate namespace the deployer Role has no grant over at all — 04's call which of the two shapes fits the manifest set better, but one of them must be in place before this is called done.

## Never-log list (applies to every component, every environment, every log level, including error paths and stack traces)

1. End-user vendor password (#9).
2. Vendor `access_token` (#6) — and any `Authorization` header value, inbound or outbound, in full.
3. PII field values from `user_profile` or from `/identity` responses: name, phone, `street_address`, `locality`, `region`, `postal_code`, `country`. Log the *fact* of access — caller `sub`, scope used, opaque record id, timestamp, status — never the values.
4. Raw vendor error response bodies (they can echo submitted PII or partial credentials). Log status code and vendor error code only.
5. JWT signing private key (#2) and any JWT in full — log `sub`, `aud`, `exp`, and `kid` if needed, never the token.
6. API caller `client_secret`s (#4), in plaintext or hashed.
7. `DB_DSN` (#1) or any connection string containing credentials.
8. Full request bodies of `POST /auth` and `POST /identity` — both contain items above by construction.
9. Search query parameters containing a name or phone fragment (`api-auth-design.md`, hardening) — they are PII; redact or hash before any access log, including proxy and ingress logs 04 controls.
10. **Database driver error messages and `DETAIL`/`Key (...)=(...)` text** (added by the cross-track consistency pass, F50 — the most probable PII-to-log path in the system and previously named by no item on this list). A Postgres CHECK or unique-constraint violation on a `user_profile`/`user_credential` write echoes the failing row's column values, or the offending key value, in its error `DETAIL`. Log SQLSTATE/result code and constraint name only — the sanitization happens in 03's error-translation layer (`error-semantics.md`) before the error is wrapped for logging, not after.
11. **Username** (added by the same pass, F50) — typically an email address, and previously ungoverned by this list even though it can appear in `ErrDuplicateUsername` driver detail (item 10) or in a log line correlating a failed login. Treat it with the same discipline as a PII field value (item 3): log a hash or an opaque identifier for correlation, never the raw value.
