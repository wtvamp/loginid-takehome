## Why this one, now

Every other story in this backlog is `curl`-verified — real, but nothing a first-time viewer (an interviewer, e.g.) can look at and understand without already knowing the API surface. This is the last story: a demo page that makes the working system visible, not a new capability.

## Constraints, not up for re-derivation (PM's ruling)

- **One static HTML page, embedded in the `api-service` binary via `go:embed`.** Not a separate service, not a separate deploy artifact.
- **Served at `GET /demo` on the verifier**, same origin as the API it demonstrates — no CORS work, and critically, **no secret is ever baked into the page itself**.
- **The visitor pastes a QA client id and secret** (the same QA clients already seeded for review, `qa-client-credential`) **that live only in the browser tab** — never persisted, never sent anywhere but this origin's own `/auth/token`.
- **The page mints a real token and drives the real endpoints** — no simulated/fake responses. Every action shows the request as a literal `curl` line next to the raw response.
- **Required panels/flows:**
  1. Masked search beside full read (the `read:own`/`read:any` scoping distinction, side by side).
  2. The two `403`s beside each other with a byte-equality check on the response bodies (demonstrating the anti-enumeration identical-content design).
  3. The `401` (no/invalid token).
  4. The `reason_code` enum: one accepted value, one rejected value, shown together.
  5. The rate limit tripping (a real burst against the real limiter, shown live, not staged).

## Acceptance criteria

- [ ] `GET /demo` serves a single HTML page embedded via `go:embed` in the `api-service` binary — no separate deploy artifact, no separate service.
- [ ] **Architecture stated explicitly, per Marcus's review (item 1):** the page's JS calls the real `/auth/token` and protected endpoints **directly from the browser** (same-origin `fetch`, using a token the browser itself obtained) — `api-service`'s server-side code never sees the plaintext QA secret at all; it only ever serves static content at `/demo`. This is the design, not an implementation detail left implicit — if any future change introduces a server-side proxy step instead, that handler would need its own never-log coverage on the request body specifically (a new criterion at that point, not assumed covered by "the page" the way this one is).
- [ ] The page never contains a secret value in its own source/markup/JS — the QA client id/secret are entered by the visitor into the page at runtime and held only in browser memory/DOM state for that tab, never written to `localStorage`/`sessionStorage`/a cookie, and never logged by the client-side JS to the console.
- [ ] **Marcus's seat, credential-handling criterion:** the page's own JS never sends the pasted client secret anywhere except this origin's own `/auth/token` endpoint, exactly once per mint, over HTTPS — enforcement site: read the shipped JS directly, confirm no other network call ever references the secret variable, and confirm the token (not the secret) is what's held and reused for subsequent calls.
- [ ] **Added per Marcus's review (item 2), a real gap — browser autofill/password-manager save prompts.** "Memory-only, never localStorage" covers what the application does, not what the browser's own chrome does: a plain credential-shaped `<input>` can trigger a "save this password?" prompt, putting the QA secret into the visitor's OS-level password store indefinitely — completely outside this design's control once that happens. Enforcement site: the secret input uses `type="password"`, `autocomplete="off"` (falling back to `autocomplete="new-password"` if a given browser ignores `off`, which some do), and a field `name`/`id` that doesn't pattern-match what password managers heuristically look for (avoid `password`/`secret` as the literal attribute value; something like `qa-token-input` is safer).
- [ ] `/demo` and its own requests are excluded from audit-log bodies — the page's own static-asset serving and the visitor's direct browser-to-API calls (per the architecture criterion above) shouldn't pollute the audit trail with demo traffic the same way a real caller's would, or should be clearly distinguishable if they do.
- [ ] The never-log lint (LT-49) covers this story's own new code paths, the same as everywhere else in this project — no exemption for "it's just a demo page."
- [ ] The static `/demo` handler sits behind the same rate limiters as everything else `api-service` serves — no special-cased bypass for the demo route.
- [ ] No authentication bypass anywhere in this story's own code — the demo page is a client of the real, fully-enforced API, not a backdoor or a relaxed-auth mode reachable only from `/demo`.
- [ ] All required panels/flows present and each drives the **real** endpoint, not a canned/fake response: masked-vs-full read, the two 403s with a byte-equality check shown in the UI, the 401, the reason_code accept/reject pair, the rate limit tripping live.
- [ ] **Added per Tobias's objection — the rate limiter's shared-identity blast radius must be stated, not silently discovered.** `internal/api.RateLimiter` is keyed **per client credential** (confirmed against `README.md`: 10 req/min for search, 60 req/min for read), and every `/demo` visitor pastes the **same seeded QA client id** — meaning one visitor's deliberate burst (the rate-limit panel's whole point) trips the bucket for **every other concurrent visitor and reviewer using that same QA client**, not just their own tab. The non-goal above correctly forbids special-casing the limiter for the demo (agreed — the demo should show the real system's real behavior), but that's an argument for stating this plainly, not for silence on it. Fix: the rate-limit panel's own copy (Imogen's, above) states this is a shared control, not per-visitor — e.g. "Note: this uses a shared test account, so tripping this may briefly rate-limit other visitors using the same demo login." Enforcement site: the panel's shipped copy.
- [ ] Every action displays the literal `curl` command alongside the raw response — a viewer could copy the `curl` line and reproduce the call themselves.
- [ ] Warren's visual criteria (palette/type scale, system fonts only, left-to-right request→response layout, highlighted masked fields, the six-color legend, responsive at phone width, no raw JSON, one-sentence-per-panel copy from Imogen) are all met — enforcement site: Warren's own visual review at the live URL, a precondition to the PO review, not a substitute for it.
- [ ] No CORS configuration anywhere in this story's diff — same-origin service of the page is what makes this unnecessary; if a PR adds CORS handling, that's a signal the page isn't actually being served same-origin as designed.
- [ ] Tests (Renata's, per the story's own engineering ownership): confirm `/demo` serves the embedded page, confirm the embed doesn't accidentally bundle any real secret file matching the never-log-list's field names, confirm the route exists in both `verifier`/default `APP_MODE` and doesn't get exposed on `issuer`/`sweep` modes (this is a demo of the search/retrieve/connector-adjacent surface, not the issuer internals).

## Forward note, not a blocker (Marcus's review, item 3)

An unauthenticated, publicly-reachable page whose whole purpose is pasting a real credential into a form is an unusual thing to leave running indefinitely. Fine for the review window this story serves; whether/how it's disabled or gated afterward (a feature flag, removed in a follow-up, left as-is with the QA clients themselves rotated/retired) is a decision for after the submission's review period, not something this story needs to resolve now — noted here so it doesn't just quietly stay live as a permanent oddity in the submission's final state.

## Non-goals

- No new API endpoints beyond what already exists — the demo page is a client of the existing surface, not new server-side capability.
- No user accounts, no persistence of anything the visitor enters — every session starts blank.
- No production/marketing polish beyond what's specified above — this is a technical demo for an interviewer, not a product landing page.
- No change to rate-limiting, scoping, or any other already-shipped security control to make the demo "work better" — the demo shows the real system's real behavior, including its real limits (e.g., the rate limit tripping is a feature of the demo, not a bug to route around).

## Research team review

**Imogen Hale — page copy:** Delivered seven sentences (page intro, credential-box explainer, one per panel), incorporated verbatim above. Written for a first-time, non-engineer viewer — states what each panel proves about the system's behavior, not what it mechanically does.

**Marcus Ilori (02) — credential-handling seat:** Reviewed the five originally-drafted criteria (memory-only/never localStorage, `/demo` excluded from audit-log bodies, never-log lint coverage, static handler behind the same limiters, no auth bypass) and found no objection to any as stated. Three additions, all applied: (1) the direct-from-browser architecture stated explicitly as a criterion, since it determines what "never-log" even has to cover (api-service's server code never sees the plaintext secret at all under this design); (2) a real, previously-unnamed gap — browser autofill/password-manager save prompts could persist the QA secret into the visitor's OS-level password store regardless of what the application itself does, fixed via `type="password"`/`autocomplete="off"`/a non-pattern-matching field name; (3) a forward note (not a criterion) that an unauthenticated public credential-paste page is unusual to leave running indefinitely — recorded for after the review window, not blocking this story.

**Tobias Lindqvist — objection:** Found the next real gap beyond Marcus's mechanics-focused review: `internal/api.RateLimiter` is keyed per client credential, and every `/demo` visitor pastes the *same* seeded QA client — so the rate-limit panel's own deliberate trip is a shared-identity event, not a per-visitor sandbox one. One visitor's burst can transiently 429 every other concurrent visitor and reviewer using that same QA client, including the PO's own subsequent panels in the same review session. Confirmed against `README.md`'s own documented limiter scoping (10 req/min search, 60 req/min read, per client credential) before applying the fix — not assumed. Fix: the rate-limit panel's copy states this is a shared control, and a PO-review step confirms a self-triggered trip clears before continuing to the next panel.

**Naomi Voss — ruling:** All fixes from both reviewers applied. This refinement is accepted and ready to hand off. The shared-identity rate-limiter risk Tobias caught is the same category as this project's very first live-review finding (LT-39's cross-replica rate-limiting bug) — a control that's individually correct but has an emergent, multi-actor interaction nobody names until someone actually runs concurrent traffic against it. Worth remembering for any future story that reuses a shared credential across multiple simultaneous actors.

## PO acceptance review — live pass against build cff7290, PASS

**Reviewer:** Naomi Voss (PO), 2026-09-13, via Playwright against `https://loginid-takehome.uplifttech.org/demo`. Three QA client credentials fetched fresh via `kubectl get secret qa-client-credential` at review time, never pasted into this doc or any message.

**Credential minting — PASS.** Minted all three (`profile:search`, `profile:read:own`, `profile:read:any`) by pasting each client id/secret in turn; each mint showed the real `curl` line (secret masked as `***`), a real `200`, and a genuine signed JWT with the correct `scope` claim. All three status chips flipped to "✓ live."

**Panel 1 (masked vs. full read) — PASS.** Real `POST /profiles/search` (masked: phone `***-***-0142`, region withheld) beside real `GET /profiles/{id}?reason_code=...` (full: complete phone/address/region/postal/country) for the same record id — the scoping distinction is genuinely visible, not simulated.

**Panel 2 (two 403s, byte-equality) — PASS.** Both records returned `{"code":"forbidden","message":"not authorized for this request"}`, and the page's own computed check read "PASS — both 403 response bodies are identical, 65 bytes each" — confirmed this is a real computed comparison, not a hardcoded string, by reading the actual response bodies myself in the snapshot: byte-identical.

**Panel 3 (401) — PASS.** No-Authorization request returned a real `401` with `{"code":"unauthorized","message":"missing or invalid token"}`.

**Panel 4 (reason_code enum) — PASS.** `reason_code=support_ticket` returned `200` with the full record; `reason_code=made_up_reason` returned `400` with `"reason_code is required for profile:read:any and must be one of the closed enum values"` — a real enum-validation rejection (400, not the panel copy's literal word "403," but "rejected" is accurate and that's what the copy says).

**Panel 5 (rate limit, run last) — PASS, and it demonstrates exactly what this project's own `README.md` documents.** Real burst: `#1`–`#9` returned `200`, `#10` returned a genuine `429` with `{"code":"rate_limited","message":"rate limit exceeded"}` — matches the documented `10 req/min` search cap exactly. Ran this last, per Tobias's ordering requirement, so no earlier panel was starved by it.

**Real finding, not a story-blocking gap: browser-extension password managers can still trigger a save prompt despite the correct mitigation.** Verified the secret input's actual DOM attributes directly: `type="password"`, `autocomplete="new-password"`, `name="qa-token-input"` — exactly Marcus's specified fix, correctly implemented. Yet my own Bitwarden extension still popped an "Update existing login" prompt when I filled the second credential (screenshot: `lt53-autofill-check.png`). This is a real residual of the mitigation, not an implementation failure — `autocomplete` hints are a request browsers/extensions may honor, not an enforceable control, and extension-based managers commonly use their own heuristics (field `type="password"` plus a nearby text field) independent of the `autocomplete` value. Recording this precisely rather than either ignoring it or treating it as a story-blocking defect: the criterion as written ("cheap fix... a field name that doesn't pattern-match") was implemented exactly as specified and closes the *native browser* autofill/save-prompt risk; it cannot close every third-party extension's own independent heuristics, and no client-side mitigation fully can. Worth one sentence in the retrospective's "what it looks like" section if space allows, since it's a genuine, interesting limitation of client-side credential hygiene, not a defect in this story's own execution.

**Storage/no-persistence — PASS.** `localStorage`/`sessionStorage` inspected directly via `page.evaluate`: the only keys present (`shopifySelectors`, `debug`, `__darkreader__wasEnabledForHost`) are pre-existing browser-extension artifacts unrelated to this page — nothing app-related, no secret, no token, in either store. No cookies set.

**No external assets — PASS.** Full network request log inspected: every `chrome-extension://` and `icons.bitwarden.net` request is my own local browser extension acting independently of the page; the page's own load is exactly one request (`GET /demo`) plus its own API calls, all same-origin. No external font/CDN/script request originates from the page's own markup.

**Warren's visual criteria — PASS**, confirmed independently at both widths (desktop 1280px, phone 390px): dark ground, system fonts (no external font request, confirmed above), request→response left-to-right within each panel, masked fields visually distinguished with a `masked`/`full` badge, no raw unformatted JSON (all responses rendered through the page's own formatted view), single-column responsive stack at phone width with no horizontal overflow. Imogen's copy shipped verbatim, one clear sentence per panel plus the intro/credential-box lines.
